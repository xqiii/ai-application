## 一句话总结

上下文分诊（感知×路由）把候选信息按 P0/P1/P2/P3 分级：**高优进 context、中优压缩成摘要、低优只挂 handle**——从高到低塞到 token 预算耗尽，像急诊室分诊护士一样在严重资源约束下做最廉价的优先级判断。

## 模式定位与原理

两个基本前提：大模型没有记忆（每次都是第一次认识世界）；认知窗口有限（无法塞下所有相关内容）。当信息总量超出窗口预算——生产级 Agent 的常态——就需要分诊。

双轴坐标：**感知 × 路由**。认知功能上决定 Agent 看到什么；执行拓扑上按优先级把信息分发到不同处理路径。

急诊室类比：分诊护士不需要是最聪明的模型（甚至不用模型），不需要诊断完才分诊——分诊本身就是那个快速判断。目标：下一步推理最需要的关键信息不被噪声淹没（与"多塞一点更保险"完全相反）。

## 三级处理策略

| 级别 | 内容示例 | 处理方式 | 目标 |
| --- | --- | --- | --- |
| P0/P1 | 当前需求、失败测试、错误堆栈、订单状态、核心接口定义 | 直接进 context（完整、靠前/靠后） | 当前推理不能缺的证据，缺失就判断错 |
| P2 | 较早对话史、背景文档、旧工具结果、日志趋势 | 压缩成摘要进 context | 不抢主舞台，提供背景坐标 |
| P3 | 整个仓库、全量日志、完整知识库、PDF 原文 | 只挂 handle（`repo://src/auth/*`、`log://payment/last_24h`） | 不提前消耗 token，保留可追溯性，需要时通过工具展开 |

**P2 压缩保留三样**：结论（说明了什么）、证据（关键字段/行号/时间点）、索引（原始材料在哪、怎么取回）。示例：不塞 15 轮对话全文，而是"历史摘要：用户目标 / 已确认 / 已排除 / 关键线索 / 原始日志 handle"。

**常见误区**：分诊不是"删材料"，是**控制信息和模型之间的距离**——P0 贴到眼前，P1 进 context，P2 压缩进入，P3 留在工具后面按需展开。context 窗口变成虚拟内存系统：热数据进 RAM，冷数据留磁盘。

登录 bug 修复示例分诊：P0=bug 描述/堆栈/失败测试；P1=auth.py、session.py 相关函数、最近 diff；P2=聊天史/旧 issue/日志趋势压缩；P3=整仓库/完整 git 史/全量日志挂 handle。

## 什么时候用 / 不用

- **用**：接入文件系统、知识库、日志平台，或任务连续跑超过几轮——分诊是基础设施而非优化项。
- **不用**：材料小且边界清楚（简单客服 bot、短文本 ETL），全塞更便宜更简单。
- 多塞的三个代价：关键证据被挤到上下文中间、注意力被稀释、token 成本拉高。

## 工程现场三切片（三种分诊来源）

| 路线 | 代表 | 优先级来源 | 适合场景 |
| --- | --- | --- | --- |
| 人写规则 | Claude Code 的 CLAUDE.md 层级（组织级/用户级/项目级/本地级） | 人告诉 Agent 什么重要 | 长期项目、固定团队、业务语义强 |
| 算法生成 | Aider 的 RepoMap（从代码结构提取符号骨架，按 token 预算放入） | 代码结构显示什么重要 | 陌生仓库、结构清晰、快速启动 |
| schema/middleware 强约束 | DeerFlow（ThreadState、Middleware Chain、Sandbox、RuntimeContext 结构化字段） | 系统 schema 强制什么必须存在 | 企业级、多租户、高风险、长任务 |

要点：
- CLAUDE.md 官方建议 200 行以内；@import 不省 token（启动时仍展开）——要省常驻 context 应拆 path-scoped rules 或按需工具读取。
- RepoMap 弱点：看得见结构重要性，看不见业务重要性。生产常混用：规则文件锁 P0 + RepoMap 提供 P1/P2 + 搜索/动态发现补路径。
- DeerFlow 式 schema 化：user_id/session_id/sandbox_mode 等字段不该让模型从自然语言里猜，应由 runtime 明确携带。安全、可审计、可测试。

8 框架横切结论：生产级 Agent 几乎没有"无分诊"路线，差别只在分诊发生在哪里——人写规则 / 算法排序 / 主循环裁剪 / runtime schema / hooks-middleware。**多租户场景 tenant_id/user_id/project_id 必须是强制字段，不是可有可无的 dict key。**

## 代码骨架（ContextTriage）

```python
class Priority(IntEnum):
    CRITICAL = 4   # P0: system prompt, 安全规则, 当前任务
    IMPORTANT = 3  # P1: 当前文件, 最近 tool 结果, 错误堆栈
    SUPPORTING = 2 # P2: 历史对话, 背景文档
    DEFERRABLE = 1 # P3: 不预加载, 通过 tool 取

# 关键机制：
# - 排序键 = (优先级, 错误堆栈加分 2.0, 内容长度)
# - 错误堆栈 is_error 强制保护：超预算也进 context，永不静默丢弃
# - P3 永远 deferred，不预加载
# - 每次分诊产出 TriageDecision（timestamp/budget/selected/deferred/dropped/tokens_used）
```

## 用户场景：多租户 SaaS 客服 Agent

200 租户 × 30 万 token/租户 = 6000 万 token，任何窗口都装不下。四层设计：

- **P0**（每 session 5-8K）：通用 system prompt + 安全策略（绝不泄露其他租户数据，P0 中的 P0）+ tenant_id/user_id 身份 + 当前用户消息。
- **P1**（20-30K）：该租户产品配置 snapshot、当前工单上下文、上次会话最后 5-10 轮。
- **P2**（10-20K 可压缩）：产品手册**目录索引**（目录+章节摘要 3-5K，不是全文）、近 3 个月相似问题聚类摘要。
- **P3**（每 handle ~30 token）：手册全文章节 `manual_section://[tenant]/[section_id]`、历史工单原文、通用 runbook——用 `read_manual(tenant, section_id)` 等工具按需取。

三个关键点：① tenant_id 是 P0 硬约束，资源加载前校验归属，不一致直接拒绝（不交给模型判断）；② P3 handle 带租户前缀（`manual_section://acme/billing` 比不带安全）；③ **P2 目录索引最值得打磨——索引好，一两次工具调用就命中；常常优化索引比改 prompt 收益更大**。

模式组合：P3 handle 接渐进发现；P2 摘要接语义压缩；配置 snapshot 接状态追踪；runbook 接复杂度路由。

## 分诊的可观测性

三个指标（看 p95/p99 而非平均值）：

1. **分诊压力**：budget_usage = tokens_used/budget；dropped_count、deferred_count 的 p95/p99。p99 dropped 突升 = 某类任务信息量压垮了当前分诊策略。
2. **关键层丢失**：p0_dropped_count（被丢通常是系统 bug）、p1_dropped_count（预算太紧或优先级错了）、protected_error_missing_count（错误堆栈不能静默消失）。
3. **P3 回取率**：p3_hit_rate = 实际读取/暴露的 handle 数。过低 = 挂了太多没用 handle；过高 = 本该 P2 的被降到 P3，Agent 多走几轮工具调用。

TriageDecision 要写成结构化 trace（trace_id/item_name/priority/decision/reason/tokens_used），出问题才能追：关键文件没进 context 是没被发现、被分诊丢、被压缩压没、还是挂 P3 没取。

## 关键要点（复习用）

1. P0/P1 直进、P2 压缩进、P3 挂 handle——分诊是控制信息与模型的距离。
2. 操作系统类比：P0=不可换出的热页，P1=工作集，P2=压缩背景页，P3 handle=页表项；调度器必须有性能计数器（trace）。
3. **上下文窗口是急诊室而非数据库**：数据库追求完整保存，急诊室追求优先处置。
4. 多租户下分诊和权限是一件事：身份字段是上下文入口的一部分。
5. 分诊写完代码不算结束：数据、问题、模型行为都会变，要靠 trace 持续检查"最小高信号集合"是否仍然高信号。

## 思考题（课程留题）

1. 800 行 CLAUDE.md 清理方案：分成必须保留 / 降级到 path-scoped rules / 挪到文档库作 P3 handle / 直接删除四类，各说明理由。
2. 500MB 线上故障日志分析：A 预过滤 / B sub-agent 分片摘要 / C P3 handles 按需读，三种策略适合什么场景、如何组合、如何避免乱搜。
3. 多租户 SaaS 客服 Agent 改造：P0~P3 各放什么、handle 长什么样、Agent 怎么知道哪些 handle 值得读、如何防串租户。
4. 上下文分诊的失效场景（至少 3 个）与防护手段。
