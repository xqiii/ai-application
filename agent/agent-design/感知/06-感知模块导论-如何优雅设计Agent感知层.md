# 06｜感知模块导论：如何优雅设计 Agent 感知层？

## 一句话总结

感知是 PRA 循环的**入口闸**：决定哪些事实能进入上下文、按什么顺序、什么颗粒度——它决定推理的上限；核心目标是 Anthropic 定义的"找出使下一次推理质量最大化的最小高信号 token 集合"，并用 Perception Trace 让信息流可观察、可调试。

## 感知 vs 记忆：都是 Context Engineering，为何分两组

两者边界有时模糊，但分开有助于思考深度：感知管"这次推理该看到什么"，记忆管"跨时间该保留什么"。（开场留的思考题，学完两个模块后再回答。）

## 为什么感知是核心架构问题

- 传统软件输入被 schema 严格定义；Agent 输入是自由文本 prompt——谁进、不进、按什么顺序、压缩到什么粒度，全是设计决策。每个进 prompt 的 token 都在花预算（attention、KV cache、API 计费）。
- 模型是在你喂给它的那一小块上下文里推理，不在真实世界里推理：**看不到的事实对它不存在；噪声太多会稀释真正重要的证据**。中等模型读干净的 30K，常常比最强模型淹在 180K 噪声里更可靠。
- PRA 循环：行动把决策变成世界影响，感知把世界压缩成上下文，推理只能加工已进入上下文的材料。失败案例的真相常是："Agent 不知道 X" = "X 存在但没进入视野"。
- 《Lost in the Middle》（Liu et al., TACL 2024）：模型对长上下文的开头结尾更敏感，中间关键信息易被忽略——窗口变长不会自动解决问题，只是把"没检索到"变成"检索到了但没用上"。

**反例 vs 正例**（退款问题）：粗糙感知 `search_docs(top_k=50)` 会混入旧政策、无关 FAQ、其他品类规则；好的感知按需组装结构化证据：订单状态、签收时间、退款历史、现行政策、SKU 特殊限制。

感知工程回答三个架构化问题：
1. 什么信息有资格进入上下文？
2. 什么信息应该被压缩、排序或丢弃？
3. 什么信息必须在推理前就被结构化出来？

## 四种感知模式（选 → 压 → 探 → 融）

| 模式 | 解决什么 |
| --- | --- |
| 上下文分诊 Context Triage | 哪些信息该进入上下文：按 P0/P1/P2/P3 分级放到最该出现的位置 |
| 语义压缩 Semantic Compaction | 进来之后怎么瘦身：长任务几十轮后历史/工具结果/日志膨胀，压缩但不能压没关键证据 |
| 渐进发现 Progressive Discovery | 一开始不知道信息在哪：像工程师一样先广扫、再精读、沿调用链深入 |
| 多模态融合 Multi-Modal Fusion | 图片/表格/日志/PDF/SQL 异类信息怎么进：保留为图 or 转文本 or 先过滤 |

**2025~2026 工业界四大争论**（后续四讲分别回应）：① RAG 还是 Agentic Search；② 窗口越大越好吗（长窗口≠可以不筛选）；③ 多模态保留为图还是转文本（取决于核心信号在空间关系还是文字内容里）；④ 分诊靠人写规则、算法自动，还是 schema/权限强约束。

## Perception Trace：Agent 的行车记录仪

调 Agent 的坏习惯：结果错了改 Prompt，再错换模型——但很多问题是 Agent 根本没看到关键材料。

Perception Trace 记录的不是模型最后说了什么，而是**推理开始之前经历了什么**：读了哪些文件、检索到什么、选中/丢弃了什么、压缩了哪些历史、调用了哪些发现动作、关键证据最终落在上下文什么位置。

对比：普通日志只有 `answer = "该订单已超过退款期限"`；Perception Trace 能显示"检索命中 47 条、进入 6 条、关键证据 refund_policy_v3.md 被排序到第 38 位未进入、实际进入的是 v1"——问题立刻清晰。

后续将介绍感知指标：budget_usage、dropped_count、compression_ratio、p3_hit_rate 等，都是 Perception Trace 的不同切面。**它不能让 Agent 更聪明，但能让工程师知道 Agent 当时到底看见了什么。**

## 感知工程不是新瓶装新酒

底层问题同一：资源有限时，把最有用的信息放到离计算最近的位置。

| 旧纪律 | Agent 对应 |
| --- | --- |
| 数据库查询优化（WHERE/JOIN/LIMIT 在库层过滤） | 上下文分诊：别把整个仓库塞进窗口 |
| 操作系统虚拟内存（RAM 放热数据，磁盘放冷数据） | P0/P1 直进上下文，P2 压缩后进，P3 留在工具/文件系统后面按需取 |
| CDN 缓存（热内容靠近用户） | 高频关键信息离模型近，长尾信息不占 prompt |
| 编辑工作（判断主线/证据/背景） | 替模型先把信息整理成适合推理的现场 |

Karpathy 类比：LLM 像 CPU，上下文窗口像 RAM，文件系统像磁盘——感知是一条完整的信息流 pipeline，不是 prompt 前的一点预处理。

**离模型越近的信息越贵，所以不能谁都进来。感知工程就是在决定谁有资格进入模型的工作记忆。**

## 关键要点（复习用）

1. 感知决定推理上限：它不是配菜，和数据建模、API 设计、容量规划一个量级。
2. 目标：最小高信号 token 集合，不是"多塞"。
3. 四模式口诀：选（分诊）→ 压（压缩）→ 探（发现）→ 融（多模态）。
4. Perception Trace 让感知决策变成可观察、可度量、可调试的工程对象。
5. 排查顺序：结果错 → 先拉 trace 看看见了什么，而不是先改 prompt / 换模型。
6. 感知层的错误会一路传导：数据源格式变化导致分诊规则漏文件，是常见的隐性故障源。

## 思考题（课程留题）

1. 系统提示词里有多少是"为完整性服务"的内容？砍掉 50% 关键任务表现会变好还是变差？
2. 找一个失败的 Agent 任务做 Perception Trace 复盘：关键证据在哪、有没有进上下文、进了在什么位置、没进是检索没命中/分诊丢弃/压缩压没、下一版怎么改感知 pipeline。
3. 实验设计：同一任务给不同长度 context（30K/100K/200K），观察成功率变化。
