# 09｜渐进发现：信息的觅食循环

## 一句话总结

渐进发现（感知×循环）= Agent 面对陌生信息空间时的**广扫 → 聚焦 → 深挖**三阶段循环（Pirolli & Card 信息觅食理论的 LLM 复刻），用最小探索成本找到最高信号区域——会找路的 Agent 比塞满上下文的 Agent 更强。

## 开场案例：15000 文件遗留代码库找 bug

订单确认邮件偶发混入其他客户订单条目。三种思路对比：

| 思路 | 结果 |
| --- | --- |
| 整库喂给 Agent | 800K token 超窗口；切 100 段并行喂，每段都说"没看到 bug"（看不到全局） |
| RAG 语义检索 | 召回质量不稳定：相关片段太多或根本没召回（bug 代码变量名是 merge_user_state，语义没命中） |
| Agent 自己 grep + read | grep send.*confirm → 30 候选 → 挑 5 个精读 → 发现调用链 MailerWorker → Cache.get_user → render → cache key 缺 customer_id → **4 轮探索，18K token，3 分钟** |

结论：**这个 bug 跟语义没关系，跟代码结构有关系**——只有 grep + read + follow imports 这种直接接触结构的方式才能找到它。

## 模式定位

- 双轴坐标：**感知 × 循环**。与分诊（Route 单点路由）、语义压缩（Chain 三层级联）的本质区别：**迭代式**，每轮带着前一轮的发现做下一轮决策。
- 背景：Anthropic 披露 2026 Q1 有 78% 的 Claude Code 会话涉及多文件编辑（2025 Q1 才 34%）——Agent 越来越频繁探索不熟悉的区域。
- 适用：陌生代码库 bug 调试、陌生客户合同审阅、陌生事故根因排查（代码/文档/工具/Skills 都可渐进加载）。
- 不适用：相关信息已预先索引好可一次性给（如分诊后的 P0/P1 材料）——不需要为探索而探索。

## Agentic Search vs RAG 之争

**切片一：Claude Code 放弃 RAG 转向 Agentic Search**（Boris Cherny 公开表态："agentic search generally works better...simpler, doesn't have the same issues around security, privacy, staleness, and reliability"）——反转了 2023-2024 "长 context 不够就上 RAG" 的行业常识。

RAG 链路多了一层**影子仓库**（vector db 副本），四个问题都出在这层副本上：
1. **安全**：代码/配置/商业逻辑多一层暴露面
2. **隐私**：向量存储带来额外数据治理问题
3. **过期**：代码每天提交，索引慢一步 Agent 看到的就是旧代码
4. **可靠**：召回依赖 embedding/查询表达/top-K/阈值，任何环节抖动结果就变；grep/read 朴素但稳定、可解释、可复现

不是 RAG 没用，而是**代码探索不能只靠语义召回**：bug 藏在变量名、调用链、缓存 key、配置、测试路径这些结构关系里。中小型代码库的 bug 定位/调用链追踪/陌生模块理解，grep + read 能解决 70% 的探索问题。

**切片二：Augment Code 持久化索引**——另一个极端：索引 400K+ 文件、45 秒增量更新、跨 repo 依赖追踪，还通过 MCP 暴露给 Claude Code 和 Cursor 用。超大代码库每次从零 grep 会变成分钟级延迟——**持久化索引把探索成本提前支付，换交互速度**。

| 场景 | 选择 |
| --- | --- |
| 中小型代码库、bug 定位、隐私敏感 | Agentic Search（现场探索） |
| 超大规模、跨 repo、强依赖追踪 | 持久化索引托底 |
| 灰色地带 | 混合（Cursor 路线）：能现场探索时现场探索，必须提前建图时提前建图 |

## 三阶段循环：Forage → Focus → Deepen

| 阶段 | 动作 | 判断指标（信息觅食理论） |
| --- | --- | --- |
| 广扫 Forage | grep/glob/find 低成本工具扫陌生空间，拿 30-50 候选（看文件名/路径/匹配行，不读全文，几千 token） | **information_gain**：单位成本拿多少信息；连续噪声就该换 query 换方向 |
| 聚焦 Focus | 挑 5-10 个最可能的文件完整读，建立局部理解（谁调用谁、主路径在哪） | **patch_quality**：哪个"信息斑块"（目录/模块/时间段/章节）平均相关性最高、值得精读 |
| 深挖 Deepen | 沿可疑链追被调函数/配置/测试/commit，只追一两条最有信号的链 | **marginal_value**：继续读还赚钱吗？边际收益下降就停、回退或换链 |

完整循环约 18K token；信号不够时带新关键词回 forage 开始第二轮。

**DiscoveryTrace（行车记录仪）** 记录每轮：phase、query、result_count、selected_count、为什么选、token 成本、next_phase。Agent 为什么从 47 个结果只选 5 个、为什么切换阶段，都应落到 trace 而不是藏在模型输出里。

可加第四阶段 **Verify**：用反例和边界条件验证有没有找错，形成闭环。

## 三条工程纪律

1. **工具要 atomic**：grep、glob、read、scorer 分开注入，不要封装成一个 search_codebase()——Agent 才能自己组合探索路径（同一套骨架可接本地文件系统、MCP server 或 Augment 类 Context Engine）。
2. **循环要有上限**：max_cycles = 3；三轮找不到通常说明关键词错、任务太泛或需要人介入，继续循环是白烧 token。
3. **单轮要有预算**：budget_per_cycle = 20K token；forage 候选过多必须立刻截断。

## 工业级三层实现

**最小骨架五对象**：Phase（FORAGE/FOCUS/DEEPEN）、Candidate（path/snippet/score/reason）、DiscoveryEvent（单次探索动作）、DiscoverySession（完整探索）、ProgressiveDiscoverer（执行器，组合 grep/read/scorer）。

**业务装配**（运维事故响应 Agent 例）：
- IncidentContext：incident_id、severity、alert_metric、affected_service、timestamp、sla_minutes_remaining。
- **keyword 推导是领域知识沉淀**：latency_p99 → timeout/slow query/circuit breaker；error_rate → Exception/5xx/FAILED；memory → OOM/GC；金融 → amount mismatch/settlement failure；医疗 → abnormal vitals。
- **先做空间裁剪再 forage**：运维日志按时间窗口（告警前后 15 分钟）、合同按章节、代码按目录模块——否则 token 爆掉。
- 产物不只是答案，而是 IncidentEvidence（suspect_logs/suspect_services/recent_deploys/config_files/correlated_traces）——**Agent 不一定要自己解决问题，先把路探出来、把人带到正确位置也是价值**。

**生产观测三指标**：
1. **cycles_to_success_p50**：找到答案要几轮，健康值接近 1；涨到 2-3 = keyword 推导变差或场景变了。
2. **forage_to_focus_ratio**：广扫 token/聚焦 token，健康区间 0.3-0.5；太高 = 关键词太宽，太低 = 关键词太窄。
3. **zero_signal_rate**：三阶段跑完毫无有效信号的比例，健康线 < 5%；突升通常不是模型变笨，而是工具出问题（grep 没查到、read 权限错、scorer 坏、索引过时）。

## 生产常见四坑

| 坑 | 应对 |
| --- | --- |
| Forage 关键词太宽（grep "login" "slow" 返回 5000 候选） | 用窄关键词（LoginController、auth_timeout）；先用轻量模型把用户描述翻译成 5-8 个精确关键词再 grep |
| Focus 挑错文件（scorer 把测试文件排在生产文件前） | scorer 加业务权重：生产文件 > 测试文件，核心目录 > 边缘目录，最近修改 > 长期没碰 |
| Deepen 追进死胡同（追到第三方库源码几百行无信号） | 设边界：不追第三方库（除非报告点名）、不追超过 2 跳的依赖 |
| Discovery 和 RAG 撞车（两边结果不一致 Agent 不知道信谁） | **先定主路径而非简单混用**：中小库/隐私敏感优先 Discovery，超大库优先索引；灰色地带混合但必须定义冲突时谁优先 |

8 框架横切三判断：① Agentic Search 已是 Coding Agent 主流共识；② 持久化索引是规模化的补丁；③ **深挖时不应污染主 Agent 上下文**——用 Sub-Agent/独立 search worker 负责广扫初筛，主 Agent 只拿回压缩后的发现、证据链和候选文件（长期运行 Agent 最怕把探索垃圾塞进主上下文）。

## 关键要点（复习用）

1. 渐进发现 = 会找路的 Agent：信息觅食理论的新形态——找斑块、有价值就深挖、边际收益下降就换地方。
2. satisficing（Herbert Simon）：不找理论最优解，在有限时间/token/上下文里找足够好的解。
3. 为什么 max_cycles / budget / atomic tools：探索要有纪律，"有纪律地看"不是越多越好。
4. Discovery 是侦探：给 Agent 原子工具 + 好的 keyword 推导 + satisficing 纪律，比塞整个代码库更重要。

## 思考题（课程留题）

1. 观察 Agent 的 keyword 推导逻辑：泛化任务 vs 精确任务的广扫 token 消耗对比。
2. 算团队代码库规模 + commit 频率，选 Agentic Search / persistent indexing / 混合？Discovery 触发条件和冲突优先级怎么定？
3. 设计 Discovery + Memory 协同：本次 bug 的 final_files + 证据沉淀到 procedural memory，下次怎么先查 memory、命中/未命中各走什么路径。
