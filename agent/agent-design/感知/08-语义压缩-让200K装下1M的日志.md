## 一句话总结

语义压缩（感知×链式）= 在长任务里维护 Agent 的工作记忆：分层逐级压缩（tool 输出清理 → 合并进 Anchor → 极限压缩），保护错误堆栈等反馈回路，让 Agent 不忘记自己为什么走到这一步、哪些路已经走不通。

## 模式定位

- 双轴坐标：**感知 × 链式**——压缩通常不是一步完成，而是一条逐级压缩链：tool 结果清理 → 对话/任务摘要 → 渐进式 summarize。每层接住上一层输出，越往后越短、越容易丢细节。
- 特德·姜"模糊图像"类比（《ChatGPT 是网上所有文本的模糊图像》）：暗房里反复翻拍照片，翻拍次数越多细节丢得越多——**多层压缩的语义漂移风险**。最稳策略：少压、分层压、保留证据、保留回退路径。
- 核心问题两个：**什么时候该压？压的时候必须保留什么？** 坏的压缩把关键证据压没（`ConnectionPoolExhausted pool_size=20, queue_depth=347` 压成 "a database error occurred" = 失去判断力，Agent 会反复调 pool size、加 retry）。

## 什么时候该压

会话超 20-30 轮；context 占用超 60-70%；tool 结果大量堆积；日志/diff/测试输出膨胀；Agent 开始重复问、重复查、重复试。

**错误信息不能被普通摘要吞掉**：错误堆栈、失败测试、异常日志、关键数字、文件路径、行号是 Agent 的反馈回路。短错误栈原文保留；长错误栈保留异常类型、关键数字、路径、行号、首尾几段 + 原始日志 handle。已失败的方案要进工作记忆锚点（anchor）。

## 工程现场三切片

### 切片一：Claude Code 自动压缩
内置 auto-compaction，接近上限时自动压。启发：压缩不能只看"窗口满没满"——等到接近满再压，Agent 已在注意力变差的状态，低质量历史压进摘要会污染下一轮。重度用户主张 **60%~70% 主动压缩**："不要等 Agent 变笨之后再压，要在它还清醒的时候整理历史"。**短任务可以晚压，长会话、高风险任务应该早压。**

### 切片二：Factory 锚定式迭代摘要
普通摘要每次重写 → 摘要的摘要 → 越来越模糊（复印件反复复印）。Factory 维护持续更新的 **anchor**，新信息增量合并进去。Anchor 五问：
1. Intent：用户要什么
2. Changes made：已改了什么
3. Decisions taken：做了哪些判断
4. **Excluded approaches：排除了哪些方案**（作者建议加的字段——很多 Agent 反复试错不是不会推理，是忘了哪些路走不通）
5. Next steps：下一步做什么

### 切片三：OpenHands 可配置压缩器（condenser）
不同任务不该用同一种压缩。可选策略：不压 / 只留最近事件 / LLM 摘要 / **ObservationMasking（观察遮蔽）** / 渐进遗忘。

ObservationMasking：历史分 Action（做过什么）和 Observation（世界返回什么）；把早期 Observation 替换成占位符但保留 Action——"你不需要记住每一屏输出，但必须记住自己走过哪些路"。若 token 主要花在日志/SQL 结果/API 响应上，而推理更依赖"做过哪些动作"，ObservationMasking 比通用 LLM 摘要更稳，省 token 且减少语义漂移。

**三条工程原则**：自动（师承 Claude Code）、演化（师承 Factory）、分治（师承 OpenHands）。

## 8 框架横切结论

1. Compaction 是取舍：Claude Code 简单、OpenHands 灵活、Aider 透明、OpenCode 解耦——没有全场景最优。
2. 不做 Compaction 也是选择，但只适合短任务。
3. **Compaction 和 Memory 要分清**：Compaction 管当前 session 怎么续命（窗口压力），Memory 管跨 session 经验沉淀（长期记忆）。

选型问句：会话多长？工具输出多大？错误密度多高？翻车成本多大？——短问答轻量处理；长调试必须有 anchor；大量日志适合 ObservationMasking；跨会话复用进 Memory。

## 工业级最小骨架（三个对象）

```python
@dataclass
class Turn:
    role: str; content: str; tokens: int
    is_error: bool = False   # 错误是反馈回路，不按普通文本压缩

@dataclass
class CompactionAnchor:
    intent: str = ""
    changes_made: list[str]
    decisions_taken: list[str]
    excluded_approaches: list[str]   # 最重要
    next_steps: list[str]

@dataclass
class CompactionEvent:   # 没有它，压缩就是黑盒
    level: int
    tokens_before: int
    tokens_after: int
    error_traces_preserved: int
```

三层压缩：**L1** 清理冗长 tool 输出（非错误替换占位符）→ **L2** 旧历史抽取五要素增量合并进 Anchor → **L3** 极限压缩（退场信号：多次触发 = session 太长，应交接/开新 session/转人工）。

## 业务实战：长会话客服 Agent（2-4 小时、50-150 轮）

业务版 compactor 三能力：
1. **按业务识别错误**：客服看 timeout/5xx/Traceback；金融看 AML flag/insufficient funds；医疗看 abnormal vitals/contraindication。
2. **按风险调阈值**：P1 工单/金融/医疗 50-55% 早压；内容生成/短代码 65-70% 晚压。SLA 越近越应准备人工交接。
3. **导出交接上下文 handoff summary**：ticket_id/severity/intent/changes_attempted/decisions/excluded_approaches/next_steps/sla_deadline——工程师看了立刻知道：客户是谁、多严重、试过什么、哪些路别走、下一步查哪、SLA 还剩多久。

压缩节律（4 小时 P1 工单三段走）：前期不压（信息收集期原始细节最重要）→ 中期轻压（清 tool 输出，保错误堆栈/最近对话/关键决策）→ 后期沉淀（合并进 anchor）；进 L3 = 准备交接，不是"再压一次"。

## 可观测性三指标

1. **level_3_trigger_rate**：L3 占比——每次 L3 都意味着信息漂移；反复进 L3 要查原因。
2. **avg_compression_ratio**（after/before）：健康区间约 0.30-0.50；低于 0.20 = 过度压缩（关键信息丢失概率高）；高于 0.60 = 没压够（很快又得压）。
3. **error_traces_preserved_per_event**：与真实错误数对齐，任何未保留的错误都应报警；零保留 = 错误识别 patterns 漏了，Agent 下次遇到同一个 bug 仍然没记忆。

进阶：把 anchor 演化轨迹记入 trace（哪些项加入/覆盖/丢弃），事故复盘时能回答"为什么 Agent 在第 N 轮忘了 X"。

## 关键要点（复习用）

1. 压缩不是摘要，是**工作记忆维护**：意图、改动、决策、排除方案、下一步。
2. 错误信息是反馈回路，不能被普通摘要吞掉。
3. 压缩分三层，越往后越激进、越要小心语义漂移。
4. 压缩必须可观测：每次压缩留 CompactionEvent。
5. Martin Fowler 类比：重构的安全感来自测试覆盖率，**压缩的安全感来自关键证据（尤其是错误堆栈）的保护**——把错误堆栈压成一句模糊结论 = 重构时顺手删测试。
6. 好的压缩本身就是一种认知：Agent 选择保留什么，决定它接下来能想清什么。

## 思考题（课程留题）

1. 你的业务需不需要压缩？怎么设计的，为什么。
2. ObservationMasking token 实验：完整历史 vs mask N 轮前普通 Observation vs 保留 Action+错误 Observation，对比省 token 量、答案质量、动作记忆。
3. 敏感数据场景：用合成数据验证压缩后 PII/PHI/权限标签/错误标签是否保留、tenant_id 是否保留，给出 compactor 规则。
4. anchor 更新记录到 trace 总线：设计最小日志结构 + 3 个能落到指标上的监控问题。
