# 选学｜DeepSeek Harness (dsh)：全插件化架构的组合、执行与记录

> 来源：极客时间《Agent 设计模式之美》黄佳 · 反思：省身之美（选学，时长 20:33）
> 原文链接：https://time.geekbang.org/column/article/1007075
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

dsh（DeepSeek Harness，2026-08-13 开源）走全插件化路线：**没有承载全部 Agent 行为的特权内核**——模型适配器、工具注册表、会话日志甚至 Agent Loop 都是平等插件（134 个条目），由薄装配内核 Cordis 组装。三层结构：组合层（Profile/Bundle/Patch→插件树）、执行层（Turn/Step→工具流水线）、记录层（Session Log→一切派生）。

## 各家 Harness 的构建路线对比

| Harness | 起点 |
| --- | --- |
| LangGraph | 先画状态图 |
| OpenAI Agents SDK | 先给出 Agent + Runner |
| Claude Code / Codex | 先交付完整产品，再开放 Skills/MCP/hooks/SubAgents |
| **dsh** | **一棵插件树，连 Agent Loop 都可替换——开放的是组装层** |

普通框架有"特权内核"（主循环/工具调度/上下文管理写死在核心）；dsh 没有不可替换的中心——严格说它仍有 Cordis 这个**很薄的装配内核**（管插件加载/卸载/依赖），没有的是特权行为内核。**普通框架的插件在运行时外面加能力；dsh 的运行时本身就是插件装起来的。**

## 三层运行结构

```
组合层：Profile（房型）+ Bundle（功能模块包）+ Patch（局部改动）→ Cordis 展开成插件树
执行层：Turn（一轮完整处理）→ Step（一次模型推进）→ 工具执行管线
记录层：Session Log（仅追加事件日志）→ 派生模型历史/UI/恢复/遥测
循环：插件树组装运行时 → 运行时产生事实 → 事实重建下一步上下文
```

**组合层要点**：
- 最小插件只导出 `apply(ctx)`；ctx 是运行时"配电箱"（服务是插座、事件是信号线）。`inject = ['tools']` 声明依赖——**Cordis 等 tools 服务就绪才执行 apply()，加载顺序由依赖关系决定，不由 YAML 行数决定**（把隐含顺序变成显式依赖）。
- **卸干净比装上重要**：Fiber = 插件的"施工单"（装了哪些工具/监听器/连接都记录在案），卸载按施工单逐项撤销；加载失败回收半套能力；定时器/连接等放 `ctx.effect()` 提供清理函数。热更新后同一段逻辑执行两遍 = 旧监听器没移除——这条纪律决定插件树能否长期运行、动态重组、安全热更新。
- Bundle/Profile/Patch 类比装修：Bundle 是功能模块包（基础设施/Web 工作台/无头运行），Profile 是完整房型，Patch 是局部改动（换模型/关插件/本地执行切远程沙箱）。`dsh --profile web --dump-config` 打印叠加后的真实插件树。开发环境 Patch 成 Mock 模型、生产换远程沙箱——上层插件不需要知道服务背后实现换过。
- 与 VS Code Extension Host 类比不能混同：Cordis 先解决组合/依赖/生命周期；VS Code 还强调运行位置和进程边界。**dsh 的新意是把成熟软件工程思想搬进 Agent Harness——插件处理的是模型请求、上下文注入、工具调用、子代理调度和 Agent Loop。**

**执行层要点**：
- **Turn ≠ 一次模型请求**。Step = 一次模型请求及其工具调用；一个 Turn 可含零或多个 Step（模型还在调工具/工具结果需交回/还有引导信息待注入，Turn 就继续）。
- 治理动作有明确挂载点：agent/pre-step（这轮是否允许开始/调整消息）、agent/request（修改最终请求）、agent/turn-stopping（决定是否再推一步）——比在主循环加 if 清晰。
- **工具执行公共管线**：tools/pre-execute（门岗：允许/拒绝/转人工审批）→ **monotonic guards（不能被后续插件推翻的最终防线，一旦拒绝后面不能改回允许）** → tools/execute（真实执行，加超时/取消/重试/指标）→ tools/post-execute（检查返回值，阻断/替换/补充上下文）→ finalizeContent → tools/result（归一化不可再改，适合审计遥测）。
- 类比：工具是手术刀，管线是手术室制度——Bash 工具不需要理解每家公司的审批制度；换掉工具实现，权限/超时/审计仍留在稳定公共路径。

**记录层要点**：
- 常见病灶：聊天界面一份消息、模型请求代码一份数组、工具系统偷偷注入上下文——压缩/恢复/重试后几份状态漂移。
- dsh 方案：Session = 类型化**仅追加事件日志**；模型历史由 deriveMessages() 从日志投影（Event Sourcing 思路，且更进一步——**Model-visible means logged：只要模型能看到，就必须进日志**，这是运行时不变量）。Agent Loop 请求前重新从日志派生消息并与即将发送的做结构化比较，不一致直接 fail（log-reconstruction desync）——**把"最好留下记录"从开发规范变成系统约束**：插件不能让模型看到日志之外的内容。
- **Compaction = 给旧账做摘要索引**：选较早历史生成摘要、追加带替换语义的新节点；下次请求读压缩后的"会话表面"，**原始事件仍留在仅追加日志**——把"模型要短聚焦上下文"和"审计恢复要完整事实"两个冲突需求分开。
- 同一份 Session Log 派生 Web UI/Fork/Resume/transcript/持久化/遥测——减少"模型、界面、恢复各自相信不同事实"。

## 评价一套 Harness 的四个问题

1. **可重建性**：模型这轮看到的完整内容，能否从持久化事实重建？
2. **执行一致性**：所有工具是否经过同一条受控执行路径？
3. **副作用消除**：插件卸载/升级失败时，已注册的副作用能否清理？
4. **治理完备性**：生产配置能否证明关键权限、审计和停止条件已挂载？

比统计"支持多少工具、接了多少模型"更能暴露运行时质量——**功能数量容易增长，运行纪律需要从架构开始设计**。

## 现状提醒

当前版本仍是 developer preview——适合学习架构、验证接口、做实验；生产成熟度有待验证。

## 学习动作建议（课程布置）

三个小实验：① 打印实际启动的插件树；② 动手挂一个依赖 tools 的插件；③ 替换或移除一个策略插件，观察工具调用和 Session Log 的变化——把"新能力应该挂在哪里"从架构图上的抽象问题变成可亲手验证的工程判断。
