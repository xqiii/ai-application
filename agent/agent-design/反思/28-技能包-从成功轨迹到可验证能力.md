# 28｜技能包：从成功轨迹到可验证能力

> 来源：极客时间《Agent 设计模式之美》黄佳 · 反思：省身之美
> 原文链接：https://time.geekbang.org/column/article/1006058 （时长 23:51）
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

技能包（反思×路由★）= 把跑通的方法整理成可复用能力，但**一次成功只能产生候选技能（TRIAL）**，通过独立验证（黄金题）才取得调用资格（VERIFIED）——发布管线（蒸馏→验证→晋级/降级）与调用管线（发现→路由→加载→回写）分开，**一次成功经历没有机会给自己颁发生产通行证**。

## 模式定位：与工具/知识/SOP 的区别

| 构件 | 回答 |
| --- | --- |
| 工具 Tool | 能执行哪个原子动作 |
| 知识库 | 当前判断依据哪些事实 |
| SOP/工作流 | 一类工作按什么顺序完成 |
| **技能包** | Agent 何时加载哪套做法，它凭什么仍可使用 |

技能包还要回答发现、依赖、验证、路由和退出——是一份可被发现、按需加载和执行的方法，有明确版本和适用边界、经独立验证、由运行时决定调用、复用结果反哺资格。

**风险与普通错误不同**：一份月报写错只影响当前产出；一套带错误假设的技能进入正式路由会被反复调用——**错误一旦固化进程序性能力，就可以在没有模型再次判断的情况下稳定传播**。

双轴坐标：**反思 × 路由**。发布管线体现反思（回看成功轨迹→候选→外部结果决定晋级/降级/退役）；调用管线体现路由（新任务从已获资格的技能中选择）。拓扑核心是从多个可用能力中做一次选择。

## 两条管线

1. **能力发布管线**（管发布权）：轨迹收集 → 候选蒸馏 → TRIAL → 验证 → 晋级/降级/退役
2. **运行时调用管线**（管调用权）：任务进入 → 技能发现 → 路由选择 → 按需加载 → 受控执行 → 结果回写

分工：蒸馏器提出候选，验证器签发资格，路由器只消费当前有效的资格。

理论脉络：产生式系统（Newell & Simon，条件-动作规则）→ ACT-R（陈述性知识"知道什么" vs 程序性知识"怎样做"）→ Voyager（技能库）→ Agent Skills（开放目录格式，渐进式披露：启动只加载名称描述、命中再读正文、脚本按需打开——**格式不会自动证明技能正确**）→ Hermes（程序性记忆）→ SKILL-DISCO（多轨迹提取参数化控制流编译成技能）。

## 候选蒸馏：成功轨迹只是原材料

distill_from_trace 明确要求 succeeded=True、min_calls=5、min_unique=3（教学确定值，非通用标准）——**返回的仍是 TRIAL：蒸馏挣得的是存储，绝不是信任**。

一条成功轨迹混着三类内容：
1. 可跨任务复用的稳定步骤
2. 当前任务独有的日期/ID/路径/租户状态
3. **这一次碰巧没暴露的隐藏假设**（实验中的 fetch_policy:2025——六月能跑通不代表七月正确）

多轨迹抽取、参数归一化、留出任务验证，都是为了把稳定做法从偶然条件中分离。

## 验证与资格管理

状态三类：**TRIAL**（已存不可路由）/ **VERIFIED**（过全部黄金题可路由）/ **RETIRED**（退役留审计）。**所有技能入库即重置为 TRIAL——人写的也不能直接 VERIFIED：徽章来自验证，不来自作者身份**。

**黄金题（Golden Questions）** = 技能的验收用例：边界值、已知正确样例、对账结果、结构断言。正确答案来自业务规则/确定性测试/人工确认，**不能由被测技能自己生成**。

**复验先撤销旧资格**：复验一开始旧 VERIFIED 就撤销——空验证集不能保留旧资格；复验失败路由器立即看不到它；新资格重新开启复用观察窗口（新版本不能用旧版本的成败数据——否则要么被旧失败拉回 TRIAL，要么被旧成功长期掩护变差不被发现）。

**验证状态绑定版本与环境**：完整的说法是"技能版本 v 在验证集 e、政策快照 p、工具契约 t、运行环境 r 下于时间 d 通过验证"。**VERIFIED 不是技能的固定属性，而是技能版本与一组外部条件之间的关系**。SkillCredential 能力凭证（设计蓝图）：skill_digest/version/suite_version/policy_snapshot/tool_contract_digest/runner_version/issued_at/expires_at。可路由 = 已通过验证 ∩ 环境兼容 ∩ 来源可信 ∩ 权限允许 ∩ 凭证仍有效。

**复用结果反哺资格**：只有 VERIFIED 且真被路由选中的技能才记录复用（record_use）；样本达标后成功率低于阈值 → 撤回 TRIAL 待重验。一次复用成功由对账一致/审批完成/测试转绿/用户采纳等**外部结果**判定——Agent 说"执行成功"只是叙事态。

**生产验证五方面**：结果正确性（边界值/类型/金额/不变量）、激活正确性（该命中的命中、不该的误触发）、流程正确性（步骤顺序/异常分支/补偿路径）、相对收益（vs 无技能或旧版本的质量成本时延）、新鲜度（政策/工具/环境变化后旧凭证能否及时失效）。确定性规则可一次验证；含模型判断的端到端技能要重复运行看成功率波动。

## 机械状态守住业务边界

东方屹腾早期把 API 写成工具+技能里写调用顺序，模型仍会跨步/漏步/拿错业务对象。后来参数的产生/消费/来源进统一状态平面：**技能负责说明怎么做，结构化运行时负责保存业务对象 ID/租户/版本/权限/参数绑定**。技能可以描述业务做法，业务不变量不能只靠叙事文本维持（"先创建快照再导入失败时恢复"可写进技能；快照 ID 属于哪个租户、来自哪次调用、当前步骤能否消费，由机械状态和执行器保证）。

## 软件供应链治理

技能可携带脚本/Shell 命令/资产——**加载技能 = 给 Agent 接入一段新的程序性行为**。项目级技能可能来自刚克隆的不可信仓库。企业技能至少记录：来源（谁/哪些轨迹生成）、版本与依赖（哪版政策/工具/模型/Schema）、权限（读写调用什么）、验证证据（哪套评测哪个环境通过）、停用能力（风险时怎样暂停降级退役）。**开放格式让技能更易迁移，也让危险脚本更易传播——互操作性越强，信任边界越要清楚。**格式校验只说明包装得像技能，不能代替业务结果验证。

## 工作台实验：旧政策技能的边界暴露

六月结算轨迹（6 次调用/4 种工具）蒸馏成候选，但第一步写死 `fetch_policy:2025`：
- **黄金题**：mid-band passthrough（12000，不碰上下限）PASS；over-cap clamp FAIL（算出 22311 应为 24402）；under-floor clamp FAIL → **stays TRIAL**
- 修复 fetch_policy:2025→2026、版本 +1、重验 → 三题全过 → **PROMOTED to VERIFIED**
- 中间档一直通过的原因：12000 没碰政策上下限，两版政策结果相同——**只有边界题才能暴露写死的年份假设**

**第二幕路由**：路由器只看 VERIFIED（settlement-hotfix 触发词重合多但 TRIAL 不进候选集）；没有合适技能 → 显式回退 fallback: from_scratch——**"还没有可用技能"是有用的运行信号**；路由器悄悄挑相近技能顶上 = 把能力不足伪装成正常执行。

**跳过验证对照**：旧政策技能直接入路由 → 800 员工中 **209 条模拟计算出错**，但每一步都报告成功、工具没报错、调用链完整——只是用了错误年份的政策。运行时甚至不需要再问模型；模型知道是 2026 也不会自动改掉技能里的 2025。

生产升级方式：不原地修改正式技能——发布新的不可变版本 → 保留旧版本和旧验证回执 → 新版过验证 → 原子切换路由别名（避免并发任务读到半新半旧的技能）。

## 指标

1. 验证结果：多少技能过验证，失败集中在哪些题目和边界
2. 激活效果：命中/误触发/无技能时明确回退
3. 真实增益：vs 无技能或旧技能的质量/成本/时延
4. 复用与过期：各版本真实成功率；政策工具变化后旧资格多久被发现撤销

没有统一健康线——报表排版和付款技能的错误代价不同，阈值要与风险、可逆性、人工复核能力一起设。

## 关键要点（复习用）

1. 一次成功 = 候选（TRIAL），验证通过才有调用资格（VERIFIED）——徽章来自验证，不来自作者身份。
2. 蒸馏器提名、验证器签发、路由器消费——成功经历不能自己给自己发通行证。
3. VERIFIED 是版本与外部条件的关系，不是固定属性——政策/工具/环境变化，关系就失效。
4. 技能描述做法，机械状态守住对象/版本/顺序/权限——业务不变量不能只靠叙事文本。

## 思考题（课程留题）

1. 团队反复复用的 Prompt/SOP/脚本，距离技能包还缺发现/验证/版本/权限/退出机制中的哪几项？
2. 为真实技能设计三道结果题两道激活题：几道真正碰到业务边界？
3. 技能昨天过验证、今天 API Schema 变了：系统怎样撤旧资格、怎样阻止并发任务继续调旧版本？
4. 哪些做法可写进技能？哪些对象 ID/版本/步骤顺序/权限必须进结构化执行平面？
