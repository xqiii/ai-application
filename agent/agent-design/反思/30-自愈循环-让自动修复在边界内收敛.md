# 30｜自愈循环：让自动修复在边界内收敛

> 来源：极客时间《Agent 设计模式之美》黄佳 · 反思：省身之美
> 原文链接：https://time.geekbang.org/column/article/1009607 （时长 20:11）
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

自愈循环（反思×循环）四字诀：**修、验、停、退**——确定性红灯启动修复，Agent 诊断提补丁，策略闸控制范围，独立验证器重跑测试；同错误+同修法重复、影响面扩大、轮数耗尽时停止并回滚交人。**自愈的本事不在能不能修好，而在能不能及时停手。**

## 模式定位

不完整的最简版本：`while tests_are_red: patch = agent.fix(error); apply(patch); rerun_tests()`——只知道"红就继续改"，不知道原地打转怎么发现、修复引出新错误怎么回退。

与 27 讲生成评审的区别：生成评审一次只审一份版本产生一次裁决就结束；**自愈的起点已是明确红灯**，要处理到转绿或明确停止恢复现场。

历史：Erlang/OTP 监督树（进程挂了重启，短时间连续挂很多次就停止上报）、Kubernetes 控制器（期望 3 实例少于就补）、TDD/CI。共性结构：发现问题→做一次修改→再检查→决定继续或停止。**大模型带来的变化是"做一次修改"这步突然变强；新风险是 Agent 不知道什么时候该停**——更危险的是修复器还能改测试：不去修代码，把测试标准改松让红灯变绿。

与 20 讲迭代假设验证同属循环，但检验信号来自确定性检查（test/CI/业务对账），不是模型的自我判断。**自愈不能靠 Agent 自己觉得"应该修好了"——每轮都要让外部检查重新告诉它问题有没有变小。**

## 故障签名与补丁指纹

**故障签名（FailureSignal.signature）**：给错误一个"身份证"。`totals off by 19200 / 471833 / 1088412` 三个报错数字不同，问题可能完全一样（付款总额与账本不一致）——只看整段错误文字会当成三次不同故障继续扩大修改范围。归一化：优先机器可读错误码；没有就正则把数字替换为 `#`（`totals off by #`）再哈希。薪酬实验用两个错误码：PAYROLL_REVERSED_IN_PAYOUT、PAYROLL_STALE_DEPARTMENT_BINDING。类别要稳定，不同问题不可合并为同一类。

**补丁指纹（Patch.fingerprint）**：给修法一个稳定身份（description + 排序后的 touches 哈希；生产可绑 diff 哈希/仓库版本/依赖变化）。**故障签名相同 + 补丁指纹相同 = 准备对同一问题再用已失败的同一种修法 → 判定"没有进展"**。

## 四种必须停手的情况

1. **补丁本身不该被应用**：不改业务代码反而改测试期望值；诊断只涉及一个文件补丁却要改十几个目录。
2. **没有进展**：`(failure.signature, patch.fingerprint)` 已出现过 → 回滚 + ROLLED_BACK_NO_PROGRESS——同错误同修法再试一次不会带来新信息。
3. **越修越大**：原来一个文件报错，补丁后新故障扩散到三个五个文件 = 制造回归。radius_limit = baseline_radius × max_radius_multiplier；生产还考虑严重程度/依赖关系/负责人/金额/安全风险。
4. **轮数耗尽**：StabilityPolicy(max_rounds=3, max_radius_multiplier=2.0)。**模型每轮都觉得"再试一次就能成功"，但有没有资格继续由外层 Harness 决定。**

五种结束状态：**FIXED**（重新验证全过，保留补丁）/ BLOCKED_BY_CRITIC（补丁越权或降低验收标准，不应用）/ ROLLED_BACK_NO_PROGRESS / ROLLED_BACK_REGRESSION / MAX_ROUNDS_HUMAN_HANDOFF——**只有 FIXED 保留补丁，其余都要恢复基线交人**。

## 绿灯必须由独立检查器给出

修复器不能通过修改测试获得绿灯（critic 拦截：`patch weakens the test; the code it guards is unchanged`；补丁触及文件数超过诊断命名的范围也拦）。**不是测试永远不能改**——需求变化时测试和生产代码可以一起调整；问题在没有新需求证据、没有人工批准时，同一修复器不能一边改实现一边降验收标准。**测试像考卷：学生答错可以改答案；同时把标准答案也改了，满分就没有意义。**

权限分开：修复器提修改，验证器判断是否满足标准。跨模型评审增加视角，但最终仍需测试/业务不变量/人工审核等可复核信号。

## 回滚以后真的回去了吗

`baseline_restored` 检查回滚顺序 = 应用顺序的逆（applied [c1,c2] → rolled_back 必须是 [c2,c1]）——证明提交账完整。**还不证明真实文件/数据库/部署已恢复**：生产要回滚后重新读取现实状态 → 与基线比较 → 生成恢复证明。回滚本身也可能失败（Git 冲突/补偿超时/旧版本取不到）→ 更高优先级失败状态，停止所有自动操作立即交人。

> **回滚命令执行完只能说明系统尝试退回；重新核对现场，才能说明它真的回来了。**

概念区分：**Saga** 定义失败后的补偿路径；**幂等性**保证补偿动作可安全重试；**恢复验证**最后看一眼现实世界是否真的回到基线。

## 代码恢复 vs 业务恢复

代码/配置/部署制品：基线清楚（commit/依赖/配置内容），回到原版本重跑测试即可确认。

业务世界麻烦得多：数据库已写入、消息已发出、付款已完成——**不会因为 git revert 自动消失**。代码退回去了钱还在对方账户；配置恢复了发出去的通知收不回。本讲实验停在 CI 阶段（只改脚本定义无真实副作用），所以恢复代码就够；生产涉及外部世界要靠幂等键/效果账本/补偿动作/冲正/人工处置。

自愈适合：边界清楚、能验证恢复结果的对象——沙箱里的代码配置、未发布的计划工作流、可快照恢复的部署单元、已设计好补偿路径的受控状态。**越接近不可逆动作，自愈越应该早点停下来交人。**

## 工作台实验

**失控循环对照**：无约束版本连跑 9 轮改了 8 个文件（含原本没问题的）、7 类不同故障——但稳定签名揭示第 1/6/9 轮是同一个对账故障（差额 19200→471833→1088412，原问题一直没消失）。**失控修复：修改越来越多、报错越来越丰富，系统却没接近目标。**受控版本第二轮发现影响范围超初始 2 倍 → 停止第三轮，按 c2、c1 逆序撤销——**没修好但及时停下、现场退回起点，比继续改 8 个文件安全得多**。

**标准场景**：两个确定性缺陷，CI 每次只报第一条红灯（第二个被第一个挡住）。c1 修 PAYROLL_REVERSED_IN_PAYOUT（只改 payout.py）→ 验证后暴露 PAYROLL_STALE_DEPARTMENT_BINDING → c2 修（只改 batch.py）→ CI 转绿 FIXED。**第一轮修好后又出红灯 ≠ 第一份补丁制造回归**——第二个问题本来就存在，且影响范围仍在允许内。

**改测试补丁**：`raise expected total in reconcile test` 触碰 tests/ → 应用前被拦 → BLOCKED_BY_CRITIC，无提交应用、baseline_restored: true——**补丁审查要发生在应用以前**。

## 相似策略辨析

| 处理方式 | 例子 | 系统做了什么 |
| --- | --- | --- |
| 重试 | 网络抖动接口超时 | 原动作再执行一次 |
| 重规划 | 主支付通道不可用 | 改走另一条合法路径 |
| **自愈** | 打款脚本过滤条件写错 | 修改代码再重新测试 |
| 补偿 | 工资已经打错 | 发起冲正等反向业务动作 |

自愈适合代码/配置/可回滚系统状态（baseline_restored 确定回滚）；涉及已发生的外部副作用还需幂等/业务账本/补偿事务/人工处置。

## 反思契约六问的回答

反思谁：出问题的代码/配置/工作流版本；回到哪里：原始目标 + 修复前确认过的干净状态；拿什么对照：test/lint/build/CI/业务对账等可重复运行的检查；允许改变：白名单内、出问题能撤销的代码和配置；怎样验收：每次补丁后重跑原检查，修复器不能顺手改检查标准；何时停：转绿停并保留，否则撤回本轮所有修改回基线交人。

**自愈比前几种反思多一层要求：不只要会改，还要知道什么时候停、失败以后怎么回去**（生成评审失败可留原稿、技能不过留 TRIAL、经验无效可归档——自愈已经真的改过代码，失败要撤回并确认现场恢复）。

## 反思模块收官：四模式对照

| 模式 | 改变对象 | 主要结果信号 | 怎样结束 |
| --- | --- | --- | --- |
| 生成评审 | 当前产出 | 对账、字段结构、规则 | 当前版本通过或退回 |
| 技能包 | 可复用能力 | 黄金题和复用结果 | 准入、降级或退役 |
| 经验回放 | 跨任务经验 | 采用证据和后续结果 | 保留、归档或转化 |
| 自愈循环 | 代码、配置和工作流 | test/lint/build/CI | 转绿，或恢复后交人 |

## 思考题（课程留题）

1. 系统里有没有一直重试或修补的流程？什么情况下会停？
2. 同一错误只改了数字/行号/时间戳，系统还能认出是同一类问题吗？
3. 你的回滚能证明什么？记录上撤销了，还是文件/数据库/外部状态都恢复了？
4. 反复出现的故障：继续自愈循环、提前做成守卫，还是风险太高直接交人工？

## 下一模块预告

感知、记忆、推理、行动、反思构成单个 Agent 的基本闭环。下一模块协作：任务超出一个 Agent 的上下文/权限/专业能力后，怎样分工、怎样汇合、怎样避免多个局部正确拼成整体错误。
