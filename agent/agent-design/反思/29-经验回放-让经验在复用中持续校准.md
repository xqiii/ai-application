# 29｜经验回放：让经验在复用中持续校准

> 来源：极客时间《Agent 设计模式之美》黄佳 · 反思：省身之美
> 原文链接：https://time.geekbang.org/column/article/1006667 （时长 25:48）
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

经验回放（反思×层级）= 跨任务反思：记录轨迹→蒸馏教训→分层保存→召回候选→注入上下文→执行→**回写外部结果**→留存/归档/转化。三问自检：**想起来了吗？照着做了吗？做了以后真的更好吗？**——只做到"想起来"顶多算会查历史记录的系统。

## 模式定位：经验是待验证的假设

技能包保存相对稳定、可命名、可执行、可独立验证的做法；有些经验还没成熟到能封技能——如"把员工绑进部门付款批次以前，先按 HR 记录核实当前部门"（专家隐形知识）。

脉络：Lin 1992（经验回放提出）→ DQN 2015 → LLM Agent 时代回放从训练样本进入推理上下文（AgentRR/CER 等）。**工程难题没变：真正难的都不是存下历史，而是确认它有没有被使用、结果该不该算到它头上。**

双轴坐标：**反思 × 层级**——经验跨任务长期存在，位于当前任务上方提供背景；结果回写经验层影响下一次召回，不在本轮内形成无限循环（层级而非循环拓扑的原因）。

> 一条经验被写进经验库 ≠ 系统学会了它——它只是取得了一个继续接受观察的机会。**经验不是结论，是待验证的假设。**

## 迷信经验（Superstitious Experience）

优先处理的风险：**把时间先后误当因果关系，从真实经历中得出错误结论**。

例："June closed clean because the report was exported twice before paying"（六月结算顺利是因为付款前把报表导出了两遍）——两件事都真实发生过，因果关系却没被证明。**它不是凭空编造的假记录**：有真实轨迹、有具体动作、能讲出完整故事，光看文字很难和真经验区分。

两个数字分开记录：retrieval_count（被召回多少次——可能只因关键词常见或排序偏爱）与 reuse_outcomes（进入后续任务后结果如何）。**被召回一百次但没有采用证据和结果改善 = 没有证明价值。**

## 三层经验结构

| 层 | 保存内容 | 进入上下文 |
| --- | --- | --- |
| L0 | 简化原始步骤与轨迹来源 | 否，只留引用 |
| L1 | 一次任务蒸馏出的一条教训 | 是，主要召回对象 |
| L2 | 多条同类 L1 归纳出的规律 | 是，随相关任务类型进入 |

解决两个相反问题：每次召回塞完整轨迹（上下文被历史淹没）vs 只存无出处摘要（失去追查能力）。**越往上越短越易复用，越往下越具体越易审计**。render() 只把 L1/L2 摘要装进上下文；生产系统把原始事件存不可变 Trace Store，经验里只留轨迹 ID。

## 三道关卡：召回、采用、归因

### 第一关：召回后要准入过滤

相关 ≠ 可进入当前任务。教学用关键词重叠确定性召回（相关度相同时 effectiveness 高者优先）。生产还要过滤：任务相关度 / 经验有效性 / **政策与工具版本 / 租户与数据权限 / 新鲜度与失效时间 / 当前任务风险等级**——另一家企业的薪酬经验、旧政策下的操作、依赖已下线工具的教训，语义再像也不该进上下文。

**与 RAG 的区别**：RAG 取回事实/文档/证据（治理=来源版本引用，典型问题"这条事实从哪来"）；经验回放取回历史做法/失败/教训（治理=采用/复用结果/生命周期，典型问题"这条经验复用后有没有用"）。可共用向量库检索器重排器，但不能混成同一种记忆。

### 第二关：进入 Prompt ≠ 被采用

retrieval_count 统计的是**曝光次数，不是采用次数**——出现在上下文里只说明有机会看到。生产需要**回放凭据（Replay Receipt）**：candidate_ids（进过候选）/ injected_ids（真进上下文）/ applied_ids（**改变了计划或动作**）/ action_evidence（工具调用/字段读取/决策差异）。

本讲实验中较强的采用证据：动作轨迹中真的多出一次 HR 当前归属检查。**模型自我报告只能作线索，可靠采用记录要落在可观察的计划变化和动作差异上。**

### 第三关：信用分配（Experience Credit Assignment）

EMA 更新有效性（`0.7 × old + 0.3 × signal`）：把判断权从"Agent 觉得有用"移到后续任务的外部结果——比纯自评前进一大步，但**明显边界：传入的每条经验都拿到同一个任务结果**。一次注入五条经验、任务成功 → 五条都加分，分不清哪条被采用、哪条同场出现、哪两条互相冲突。

补齐三类证据：**采用证据**（计划动作是否落实了经验）、**对照证据**（有经验 vs 无经验结果差多少）、**局部结果**（经验对应步骤/字段/约束是否真的改善）。

## 反馈的两个方向

1. **归档**：长期无效/过期/制造噪声 → effectiveness 低于健康线且复用达标 → archived
2. **能力转化（毕业）**：hard_guard_eligible + effectiveness ≥0.7 + 复用达标 → graduation_candidates

| 成熟形态 | 适用条件 | 去向 |
| --- | --- | --- |
| 稳定的多步做法 | 可执行可验证可反复调用 | 技能包 |
| 确定性的禁区或前置条件 | 可写成机械断言 | **硬守卫**（护栏三明治 PRE 候选——不再依赖模型每次想起，运行时强制执行） |
| 稳定的业务事实 | 需要查询引用版本管理 | 知识库/RAG |
| 过期或长期无效 | 复用效果差、环境已变 | 归档 |

> **经验池不是知识的终点，而是软知识的试验场**——未经证明的教训在这里接受复用检验；成熟后进入技能/守卫/知识库，转化仍要经过对应模式自己的测试审批发布流程。

## 反馈规则本身要校准（ValidatorPolicy 层）

EMA 为什么 0.7/0.3？健康线为什么 0.5？为什么至少复用 5 次？——这些值不是自然规律，要根据业务风险/结果延迟/样本量/误判代价来定。**有效性分数是运行时记账；健康线、EMA 系数、转化门槛的设置属于 ValidatorPolicy，需要有人持续校准。**阈值过松错误经验长期占上下文；过紧有效经验没积累够样本就被提前归档。

**经验 vs 机械态分工**：E0012 的员工编号/当前部门/租户状态是机械真值，应从 HR 系统实时读取；经验层只提醒"跨部门批次前要核实员工当前归属"。**如果把 E0012 属于 Engineering 直接固化成长期经验，旧状态会被当成当前事实稳定带进后续任务**——经验负责提醒查什么，机械状态负责回答现在是什么。

## 工作台实验

**Scene 1（召回改变决策）**：不读六月经验 → 800 员工进 5 批次、账全平，但 E0012 按旧数据错绑 Finance（HR 最新是 Engineering）——**没报错、账对平，业务做错**。带经验回放 → 上下文注入教训（failure + heuristic 两层），Agent 多做一次 HR 检查，E0012 改绑 Engineering → mis-bound: []。**经验不能只是被检索出来，还得真正改变做法**（明确的动作变化比"Agent 说参考了历史"可靠）。

**Scene 2（一次有效 ≠ 永远有效）**：六个月确定性结果——membership lesson 六连胜 effectiveness 升到 0.94；report ritual（迷信）忽高忽低降到 0.30 → **archived**。第一个月两条都是 0.65 看不出差别，**使用次数增加后差别才显现**。

**Scene 3（关掉结果回写 = 假学习）**：六个月后 ritual 停在 0.50（neutral），第七个月还在被召回；membership lesson 也停在 0.50、reuses=0——**没有资格毕业成守卫**。每天保存新经验、每次检索出旧经验，但从不问"后来帮上忙了吗"——坏经验退不出去，好经验长不大，经验库变成"越来越长的意见墙"。

完整链路：想起经验 → 放进当前任务 → 真的照着做 → 看任务结果 → 判断有没有帮助 → 决定下次还要不要用（召回→注入→采用→执行→外部结果→信用分配→生命周期更新）。

## 反思契约六问的回答

反思谁：带来源和版本的经验；回到哪里：当前任务原始目标；拿什么对照：采用后下游结果+局部动作证据+对照基线；允许改变：后续任务的经验上下文/召回排序/生命周期状态；怎样验收：下一次复用的外部结果（一次 EMA 更新只是记账）；何时停：单次任务结束即停，本次结果只影响后续召回；误归档时原始轨迹和 reuse_outcomes 仍可按 ID 取回复核由人工决定恢复。

## 指标与六个失败模式

五组指标：召回精确率与采用率 / 相对无经验基线的回放增益 / 按任务版本时间窗的有效性 / 过期发现时延与上下文成本 / 能力转化撤销回滚率。**单看召回次数奖励关键词常见的经验；单看最终成功奖励碰巧同场出现的经验**——都要与采用证据和对照结果一起看。

| 失败模式 | 对策 |
| --- | --- |
| 相关性幻觉 | 版本、权限、新鲜度和风险过滤 |
| 错误归因 | 复用结果与对照证据 |
| 经验过期 | 依赖记录、衰减和转化后退役 |
| 上下文拥挤 | 分层、去重和预算控制 |
| 信用污染 | 回放凭据、采用证据和局部结果 |
| 跨租户泄漏 | 租户隔离、脱敏、权限过滤和审计 |

**经验条目不断增加 ≠ 系统能力在增加**——只有能被正确召回、留下采用证据、接受外部结果检验、拥有退出机制时，经验库才不会变成历史意见堆。

## 思考题（课程留题）

1. 团队复盘文档里哪些只是经常被提起、哪些有复用后的结果证据？
2. 找一条"我们一直这样做"的口诀：设计最低成本对照，判断它是有效经验还是错误归因。
3. 一次任务注入五条经验并成功：保存哪些动作和局部结果，避免五条全记满分？
4. 一条成熟经验更适合转技能/硬守卫/知识/留在软背景层？判断依据是什么？
