# 01｜范式之变：GoF 的崩塌和分布式的血脉进化

> 来源：极客时间《Agent 设计模式之美》黄佳 · 范式觉醒

## 一句话总结

三代设计模式的演进（GoF → 分布式 → Agent），根因是**决策权从开发者的设计时迁移到模型的运行时**；于是工程重心从写功能逻辑转向设计 Harness——在不确定性下约束模型决策的边界结构。

## 三代演进脉络

> GoF 解决"代码怎么组织"；分布式解决"服务怎么存活"；Agent 解决"模型怎么被约束地行动"。

| 代际 | 时期 | 核心问题 | 前提假设 | 协作对象 |
| --- | --- | --- | --- | --- |
| 第一代 GoF 23 模式 | 1994 起 | 代码怎么组织 | 单进程 / 共享内存 / 同步调用 / 确定性失败 | 对象协作 |
| 第二代分布式模式 | 2010 年代 | 服务怎么存活 | 不可靠网络：网络分区 / 异步消息 / 部分失败 / CAP 三选二 | 服务协作 |
| 第三代 Agent 模式 | 2024 起 | 模型怎么被约束地行动 | 高强度不确定性（输出 / 行为 / 环境） | 模型协作 |

- GoF 23 模式分创建型、结构型、行为型三类；模式语言思想源自 1977 年建筑学家 Christopher Alexander 的《A Pattern Language》——好的设计是从一组反复出现的好模式中涌现的。
- GoF 的工程价值：① 提供共同词汇（Singleton、Factory、Observer、Strategy 用了 20 年）；② 把工业实战的编码经验抽象成可复用解法。
- 分布式模式参考 Michael Nygard《Release It!》；共同特征是把"不确定性"作为首要关注点——GoF 假设失败是 Exception，分布式假设失败是 default。
- **三代是推进关系，不是断裂**：旧模式没有过时，而是被"抬高了一个层次"。

## 四个 GoF 模式在 Agent 时代的断裂

| GoF 模式 | 经典假设 | 断裂原因 | Agent 时代的替代 |
| --- | --- | --- | --- |
| Singleton | 状态持久全局共享 | 上下文窗口有限、对话重置，全局配置可能丢失 | 分层记忆架构（工作 / 短期 / 长期 / 程序性四层记忆） |
| Factory | 产品类型编译期已知 | MCP 让 Agent 运行时动态发现新工具，动作空间开放 | 语义工具路由（按自然语言意图匹配工具描述） |
| Observer | 推送可靠且廉价 | DOM 树 / 高频日志流会撑爆上下文窗口 | 主动感知（Agent 自己决定看什么、何时看、看多久） |
| Strategy | 开发者在设计时选策略 | 修复 bug 的每一步策略切换都是 LLM 运行时自己决定的 | Strategy 被搬进 Agent"脑子"，由 LLM 每步动态切换 |

**根因**：GoF 所有模式假设架构师在设计时做出所有结构性决策（编译期决策 + 运行时执行）；Agent 系统要求系统本身在运行时、不确定环境下做出决策（运行时决策 + 运行时执行）。决策权搬家，模式随之失重。

代码层面的映射：
- GoF Singleton → MemoryArchitecture（记忆模块 · 4 层记忆）
- GoF Factory → SemanticToolRouter（行动模块 · 工具调用和 MCP 语义匹配）
- GoF Observer → ActivePerception（感知模块 · Agent 自己决定看什么）
- GoF Strategy → LLM 在 reason() 里每一步自己挑

## 血脉进化：分布式模式的延续

从第二代到第三代不是"新旧替换表"，而是承载问题的对象变了：第二代处理服务世界的不确定性，第三代处理模型决策的不确定性。例：分布式"长事务补偿"进化为 Agent 的"规划—执行"——以前补偿的是数据库状态，现在补偿的是任务推进路径。

## 三种不确定性（Agent 时代的新前提）

1. **输出不确定**：同一 prompt 跑十次可能十种答案；LLM 调用重试不幂等，可能引出全新行为分支。熔断器、幂等键等经典模式需要重新设计。
2. **行为不确定**：Agent 自己决定是否调工具、先调哪个、要不要追问；ReAct 循环的长度和内容在设计阶段无法预测。
3. **环境不确定**：Agent 操作的世界本身在变——网页布局会改、Codebase 会被同事改掉。

传统软件工程把不确定性当边缘情况（try-catch / retry / timeout），这套思路治不了 Agent 系统；Agent 工程必须把不确定性当作**默认运行条件**来设计。

## 真正的新地基：Harness

- 工程师的工作重心从写功能逻辑转向**设计边界条件**：模型在什么上下文下思考、能看到哪些信息、能调哪些工具、什么条件下必须停、做错后如何拉回、做过什么谁来留痕审计。
- Harness 在模型思考之前、之中、之后立边界、留痕迹、做审计；它不替代模型思考。
- 核心工程判断：**Agent 架构，就是在不确定性之下设计有界资源的分配**（Agent architecture is the design of bounded resource allocation under uncertainty）。口语版："模型负责花钱，Harness 负责管账"——token、context、工具调用、时间、用户信任、不可逆动作的风险都是"钱"。
- 调 prompt 是局部修补（这次别犯）；做 Harness 是把局部错误上升为系统纪律（以后都别这么犯）。后者才是工程与调参的分界线，也是新一代工程师的最高杠杆。

## 双轴正交框架：这一代的"GoF 词汇"

Agent 模式的核心张力是"**资源花在什么地方 × 资源怎么被花出去**"，所以不能用 GoF 的创建/结构/行为三分法。作者提出的坐标系：

- **认知功能轴**（资源花在哪里）：感知、记忆、推理、行动、反思、协作、治理
- **执行拓扑轴**（资源怎么花出去）：链式、路由、并行、编排、循环、层级

课程要讲的 28 个模式都回答同一个问题：当模型开始在运行时自己做决定，工程师该怎样搭框架，让这些决定仍然**稳定、可审计、可复用、可进化**？

## 关键要点（复习用）

1. 三代模式一道道往上推进：对象协作 → 服务协作 → 模型协作。
2. 决策位置迁移（设计时 → 运行时）是模式变迁的根因。
3. 不确定性是 Agent 时代的默认运行条件，不是边缘情况。
4. Harness 不创造智能，它约束智能的开销与后果。
5. 双轴框架 = Agent 时代的共同词汇。

## 思考题（课程留题）

1. 三代设计模式演进、Agent 时代模式变迁根因的论述是否到位？有何深刻与不足？对展望未来 Agent 架构有何启发？
2. GoF 自检：项目里用得最多的 3 个 GoF 模式，各自的核心假设是什么？
3. 分布式自检：微服务系统用过哪些经典分布式模式？哪些生产不可或缺？
4. GoF 断裂自检：项目里最关键的类（配置管理器、连接池、事件总线、策略容器等）改造成 Agent 版本会先碰到哪种断裂？
5. Harness vs Prompt 优先级：1 周时间提升 Agent 可靠性，选调 prompt（这次别犯）还是改 Harness（永远没机会犯）？为什么？

## 精选留言亮点（作者回复中的干货）

- **环境同步机制四分法**（回应"Agent 被动用过期信息"）：Pull-on-demand 懒拉取 / Periodic refresh 定时刷新（TTL）/ Event-driven invalidation 事件驱动失效 / Hybrid 混合（按数据冷热分层：热数据走事件、温数据走定时、冷数据走按需）。
- **GoF 与 OODA 环同构**（读者发现，作者认可）：观察者→Observe、单例→Orient、策略→Decide、工厂→Act；从 OODA 到 ReAct 到 Agentic Loop 是一条进化线。
- **规则从软到硬五级**（回应"模型总忽视 AGENTS.md 规则"）：L1 写 AGENTS.md → L2 移进每轮重注入的 P0 区 → L3 给工具加返回硬上限 → L4 pre-tool-use hook 拦截 → L5 干脆不向主 Agent 暴露工具（内部 spawn 子 Agent 读原始数据、只回传摘要）。
- **三代是叠加而非替代**（读者观点，作者认同）：Agent 底层仍跑在分布式设施上，代码仍用 GoF 组织；Agent 越复杂，传统工程能力（容错、监控、日志、审计）反而越重要。
