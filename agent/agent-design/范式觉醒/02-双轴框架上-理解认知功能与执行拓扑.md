# 02｜双轴框架（上）：理解认知功能与执行拓扑

## 一句话总结

双轴正交框架 = **认知功能轴（What，Agent 在做什么）× 执行拓扑轴（How，数据与控制怎么流动）**；纵轴七脉本质是七种资源预算，横轴六式本质是六种错误传播路径。

## 框架的由来

- 分布式时代是"问题 → 模式"的见招拆招（网络会挂→熔断、事务失败→补偿），因为问题高度可命名。
- Agent 时代组合密度更高：一个生产级 Agent 同时用上下文分诊、分层记忆、复杂度路由、工具调度、生成评审、审批门控、可观测性——它们是**互相影响的预算系统**，不是并排零件。
- 没有坐标的架构评审会退化为松散术语："加 reflection"说不清是生成评审、自愈循环还是经验回放。
- 作者的顿悟：选型时其实同时在问两个问题——What（让 Agent 做什么）× How（怎样组织 Agent 行为），两者交叉后 Why（为什么这个场景需要这个模式）才浮现。**术语表不够，Agent 时代需要的是能给术语定位的坐标系。**

## 业界分类的三个盲区

业界现有分类（Lilian Weng 数模块、Anthropic 数 Workflow、Andrew Ng 数常见设计模式、Chip Huyen 数工程角色）像给同一立体物画三视图，各有盲区：

1. **感知盲区**：多数分类默认 input 已是正确 input，但生产系统最先死的往往是 input——200K 装不下 codebase、检索 chunk 大半是噪声、日志流刷屏。感知是注意力预算的第一道闸，不是前处理小步骤。
2. **反思盲区**：Reflection 常被折进 Reasoning，但它是把"一次性回答"推进到"可迭代改进"的关键机制，应独立成脉：Reasoning 生成方向，Reflection 纠偏方向。
3. **治理盲区**：Demo 可以没有治理，工程不能没有。能改代码、发邮件、操作云资源的 Agent 没有审批门控、爆炸半径控制、审计追踪就是事故候选。治理必须和行动能力一起设计。

三个盲区共同指向：行业太关注模型"里面"，太少系统化讨论模型"周围"——Model spends, harness budgets。

## 纵轴：认知功能七脉（三个圈层）

| 圈层 | 认知功能 | 定位 |
| --- | --- | --- |
| 内圈·核心认知 | 感知、记忆、推理、行动 | 没有这四件事，Agent 退化为聊天机器人或固定脚本 |
| 中圈·元认知 | 反思 | 把上一步产物变成下一步的对象；从"生成答案"进入"审查答案" |
| 外圈·系统智能 | 协作、治理 | 协作让单体扩展成组织，治理让能力展示变成可上线系统 |

**建设顺序**：内圈让 Agent 能用，中圈让 Agent 可靠，外圈让 Agent 能上线。很多团队败在顺序反了：内圈还没跑顺就搞多智能体集群——错误涌现，不是智能涌现。可以暂时不实现某一脉，但不能假装它不存在。

**七脉 = 七种资源预算**：

| 认知功能 | 预算类型 | 核心问题 | 失控表现 |
| --- | --- | --- | --- |
| 感知 Perception | 注意力预算 | 什么信息进入模型 | 看到太多 = 什么都没看见；token 失控 |
| 记忆 Memory | 连续性预算 | 跨时间保留什么 | 每次像初见没成长；全当永久事实被旧信息拖死 |
| 推理 Reasoning | 不确定性预算 | 从前提怎么走到结论 | 让所有问题都深度思考是浪费；判断失控 |
| 行动 Action | 不可逆预算 | 能对世界做什么 | 推理错了可重答，行动错了可能不可补偿 |
| 反思 Reflection | 校正预算 | 刚才做得对不对 | Self-Critic 自我合理化、Loop 过度修补；错误失控 |
| 协作 Collaboration | 分工预算 | 一个 Agent 装不下怎么拆 | 大家知道一切 = 大家被噪声淹没；规模失控 |
| 治理 Governance | 信任预算 | 能力如何被限制、记录、审计 | 强能力没有边界就是强事故；信任失控 |

判断标准：**架构缺哪一脉，就在哪一类资源上失控**。

## 横轴：执行拓扑六式（六个动词：传、选、撒、协、转、分）

| 拓扑 | 动词 | 含义 | 关键点 | 失败模式 |
| --- | --- | --- | --- | --- |
| 链式 Chain | 传 | 上一步输出 = 下一步输入 | 链越长中间格式越重要 | 错误级联：节点输出走偏，下游把错包装得更漂亮 |
| 路由 Route | 选 | 先分类再交给对应处理器 | 核心是分类器质量 | 错误分派：路由错后面难救 |
| 并行 Parallel | 撒 | 多路展开再合并 | 关键在 merge 不在 fan-out | 错误聚合：没有好的 merge，并行只是把噪声并行化 |
| 编排 Orchestrate | 协 | 中心节点拆解、分发、汇总 | 适合中心能理解全局的复杂任务 | 错误分解：拆错边界（该链式的拆成并行等） |
| 循环 Loop | 转 | 生成、评估、修订直到停止条件 | 核心是停止条件、评估信号、每轮改动幅度 | 错误复合：越改越忙，越忙越偏 |
| 层级 Hierarchy | 分 | 多层委派，父管目标子管局部 | 与 Orchestrate 区别：一层中心 vs 多层责任分解 | 错误放大或隔离：父级上下文泄漏、权限继承太宽、低层失败向上雪崩 |

**关键洞察**：横轴不是流程图轴，而是**错误传播路径轴（failure propagation axis）**——选择拓扑就是在选择错误如何移动。

业界框架对照：Anthropic 的 Prompt Chaining/Routing/Parallelization/Orchestrator-Workers/Evaluator-Optimizer、Google ADK 的 Sequential/Parallel/LoopAgent、OpenAI Agents SDK 的 Handoffs/Guardrails/Tracing、LangGraph 的有向图——都在回答"流怎么走"，是这条轴的局部呈现。

## 关键要点（复习用）

1. 双轴 = What（认知功能，资源花在哪里）× How（执行拓扑，资源怎么流）。
2. 七脉分三圈层：内圈核心认知（4）+ 中圈元认知（1）+ 外圈系统智能（2）。
3. 七脉是七种预算：注意力、连续性、不确定性、不可逆、校正、分工、信任。
4. 六式是六种错误传播：级联、分派、聚合、分解、复合、放大/隔离。
5. 建设顺序不能反：先内圈、再反思、最后协作治理。

## 思考题（课程留题）

1. 你的 Agent 系统最容易失控的是哪一类资源（感知/记忆/推理/行动/反思）？
2. 你熟悉的 Agent 工作流主要采用哪种执行拓扑？错误沿什么路径传播？
3. 为什么"用了几个 Agent、接了几个工具"不足以说明系统设计好坏？用七脉×六式重新描述它。

## 精选留言亮点（作者回复中的干货）

- **Route vs Orchestrate 的区别**：① 路由选"走哪条已知的路"（从固定菜单挑），编排决定"把任务拆成哪些子任务"（菜单临时生成）；② 路由的分支设计时固定，编排的分支运行时由输入决定；③ 路由一次决策就退场（fire-and-forget），编排全程在场并回收结果做综合。
- **六式 × 错误传播的推导**：大部分人看 Workflow 只看控制流；但 Agent 系统最终失败 90% 不是模型不会推理，而是错误在系统里扩散了。工业设计师画 Workflow 时想的是：Chain 错误会不会一路传下去、Route 会不会分错队、Parallel 多个错误如何汇总、Orchestrate 拆解会不会错、Loop 错误会不会自我强化、Hierarchy 错误被放大还是隔离。
- HATEOAS 风格接口下的 Agent 工作流（读者案例）：拓扑不是固定链式，而是状态驱动的 Route + Loop——每步读取服务端当前状态和可用动作再决定下一步；错误沿"错误分派"路径传播，且外部状态一旦改错，后续所有可选路径基于错误状态展开（stateful agent 的根本风险）。
