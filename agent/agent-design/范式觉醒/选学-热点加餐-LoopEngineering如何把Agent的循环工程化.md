## 一句话总结

Loop Engineering 就是 Harness Engineering / Agent 设计模式的工程化落地：不再手写每个 Prompt，而是设计一套循环替你去 Prompt——以"到店吧"点餐 Agent 为例，讲透执行型 Agent 的三平面架构、机械状态平面、护栏与循环边界。

## Loop Engineering 是什么

**一句话讲透**：你不再一句句手动写 Prompt，而是写一个程序、设计一套循环，让这套循环替你去 Prompt。

- 热词演进一脉相承：Prompt Engineering（关注一次调用的结果）→ Context Engineering（上下文窗口的提炼构造，即感知模式设计）→ Loop / Harness Engineering（关注多次迭代的整体循环）。
- 主语变了：以前是"我做 Prompt，模型给答案"；现在是"系统做 Loop，我得到结果"。不介意模型一次做错，关键在于能否通过循环定位问题——**从错到对的轨迹比一次答对更重要**。
- 价值的单位变了：从"模型的单次回答"变成"循环完成任务的轨迹"。
- 结论：Loop Engineering 从第一天就没创造新概念，它就是工程化本身——模型早就不是瓶颈，**瓶颈在循环的设计**。

## 执行型 vs 内容生成型 Agent

| | 内容生成型 | 执行型 |
| --- | --- | --- |
| 任务 | 做报告，无对错标准 | 订餐、下单、支付，有真实交付 |
| 失败代价 | 打 8 分还是 10 分 | 付错钱要投诉索赔 |
| 最小闭环 | 简单 ReAct 就够 | ReAct 会崩在：跨步漏步、参数漂移、**虚假成功**（讨好型人格：内部失败却说"已完成"）、死循环、上下文爆炸 |

没有治理的循环 = 把程序设计交给运气。工程化循环要求每个环节明确管控：感知给对、失败日记记录、行动轨迹存档、可观测呈现、机械状态记录、治理与停止条件、出错 Rollback。

## 三平面架构（二元论 → 三元论)

- **叙事平面**：自然语言、语义、"人话"——负责**发散**，承载可能性和 Loop 迭代的意义。
- **控制平面**：离散信号（对/错、订单 ID）——负责**收敛**，驱动程序分支和真实调用。Agent 时代之前只有机械控制平面；叙事平面是大模型出现后才有的。
- **调度平面**：Workspace / Orchestrator，各节点状态、工作流执行进度。

一个完整的 Agentic Loop 由三平面配合产生。

## "到店吧"四层运行时

用户入口层（小程序发起委托）→ 协议层（意图识别、小程序 MCP 连接、Skill 选择、策略路由）→ 能力层（Skills/MCP/原子接口/原子组件/UI 卡片）→ 状态治理层（编排器、Workspace、DAG、机械状态平面储存、Payment、可观测 Tracing）。

关键设计：
- **意图收敛**：一句话 → Task: BuyFood, FoodCategory: 火锅, Budget: 150, Time: 今晚6-9点, Confidence: 0.93。
- **Orchestrator**：MessageHandler 只收发消息；Orchestrator 拿控制信号交给 ReAct 做事；做错不从头再来，按状态机回滚到断点重试。
- **机械状态平面**：UserID、StoreID、电话、地址、SKUID、Cart、CouponID、PaymentSession、OrderID、Ticket 全部清晰存储。**参数的记录和传递不能完全交给模型，确定性值必须由程序机械掌控**。
- **Provenance 坐标**：每个参数要有可审计来源——谁生成、何时生成、传给了谁。Agent 越 Loop，这些痕迹越是审核依据。
- **任务状态机**：每个委托是有状态节点，可追踪、可回退、可验收。
- **原子卡片聚合**：产品约束（确认不能太多）→ 把门店/套餐对比/订单确认几个原子卡片集成为一次确认。
- **设计思想**：**让计划活在代码里，让创意活在上下文里**——点餐要确定性（代码），科研要灵活性（上下文 + Skills 积累）。
- **审批门护栏**：支付必须用户确认；产品约束下审批门不超过 2~3 次。
- **可观测玻璃罩**（梁博的手表比喻）：手表正面是用户看到的清晰结果；背面玻璃罩里是齿轮般的工具调用、推理行动、ID 流转——开发人员全程可见。

## 三本书的哲学底座

1. **凯文·凯利《失控》造物九律 × Agent 循环**：分布式状态（多 Agent/子代理）、自下而上控制（机械平面自治 + 固定工作流编排）、递增收益（技能复利：积累越多 Agent 越强）、模块化生长、边缘创新、**礼待错误**（失败日记模式：错误是避免重犯的必要条件）、不求单一最优解（反脆弱）、持续不均衡（从设计固定系统到设计不停演进的 Agent 生态）、变自生变（每 Loop 一次沉淀新 Skill，下一轮 Loop 跑在积累的 Skills 上——科研智能体案例：几千科研人员的对话沉淀三个月后系统就开始"会做科研"）。
2. **侯世达《GEB》怪圈理论**：意义从无意义符号的循环中涌现；**不要在循环里自己给自己打分——对循环的验证必须来自循环外部**（机械平面真值、用户验证、跨模型互验如 Claude 与 GPT 互相校验）。
3. **《有限与无限的游戏》**：有限游戏在边界内玩，无限游戏玩的就是边界。一单火锅是有限游戏；把 Agent 看成循环生态是无限游戏——它越来越懂主人，最后每天下午 6:30 自动订火锅。**用无限游戏的心态去设计有限游戏的边界。**

## 核心判断清单

1. Loop Engineering 就是 Harness，就是工程化本身。
2. 先分执行型还是内容型；执行型 × 长程组合才值得上重循环。
3. 模型思考是叙事平面，机械执行是控制平面；机械状态平面的数据准确性和 Provenance 是重中之重。
4. 计划活在代码里，不被上下文束缚；要有清晰的 DAG。
5. 边界和停止条件是循环本身的一部分。
6. 支付/企业级 SaaS 边界严格，研究场景越发散越好。
