# 开篇词｜把一千个真实工程问题凝结成 28 个设计模式

> 来源：极客时间《Agent 设计模式之美》黄佳 · 开篇词
> 原文链接：https://time.geekbang.org/column/article/980705 （时长 22:28）

## 一句话总结

全部 28 个模式回答同一个问题：**不确定性下，有限的资源该怎么分配**——Agent 的价值取决于能不能沉淀经验，而不是今天有多聪明；模型负责花，Harness 负责控制预算（The model spends; the harness budgets）。

## 从一千个真实工程问题里长出来的判断

2026 年上半年作者至少回复一千多个真实工程问题，来自专栏留言（《Claude Code 工程化实战》587 条留言/539 条回复）、行动营、群聊私聊、知识星球。工程师真正卡住的地方：

- Claude Code 能写代码，为什么一进公司仓库就乱？
- SubAgent 开了 5 个，为什么答案更多了决策反而更差？
- CLAUDE.md 写了很多规则，为什么 Agent 还是会忘？
- MCP 工具都接上了，为什么工具越多越容易选错？
- 代码审计 Agent 发现了问题，为什么下一次还踩同一个坑？
- 跑了两小时的长任务，为什么跑着跑着就偏离目标，甚至越权？

**残酷的事实：很多团队缺的不是工具，是设计语言。**一个 Agent 不稳定，最后只剩模糊判断（模型不够强/prompt 还要调/上下文没给够/工具有点多/加个 Workflow）——都可能对，但粒度都太粗。类比传统后端：不会只说"代码不够好"，而是追问事务边界、缓存失效、消息幂等、限流、索引、服务拆分、观测指标——**成熟工程领域都有自己的问题语言，Agent 工程也必须有**。

本课目标：把真实工程问题 + 市面上 Harness 架构（Claude Code、CodeX、OpenCode、Aider、OpenClaw、Hermes、OpenHand、DeerFlow）背后的**公共结构**抽出来，沉淀成可讨论/可实现/可组合/可上线/可复盘的 Agent 设计模式。

## 核心判断：Agent 的价值是它累积的经验

> Agent 的价值，取决于它能不能沉淀经验，而不是它今天有多聪明。

Demo 阶段漂亮的 Agent，三个月以后呢？——有没有记住踩过的坑？知道团队过去怎么做审批？学会仓库评审最常见的三类问题？把成功流程沉淀成 Skill、失败调用写进失败日记？处理过 100 个 PR 后比第 1 个更懂仓库？**如果没有，它只是一个每天重新入职的聪明新人**——聪明的新人当然有价值，但你不会把公司的关键流程交给一个每天都忘记过去的人。目标是**会成长、会沉淀、会被治理、会被复用、会变老练**的 Agent 系统。

## 范式变化：工程师设计决策边界

传统软件：工程师在设计时决定控制流（下单流程：校验库存→计算价格→扣款→发通知），输入一样输出基本一样。Agent 系统：控制流的一部分被交给模型在运行时决定（先看什么、查什么、调哪个工具、要不要重试/问人/派子 Agent）。**过去工程师写逻辑；现在更重要的工作是设计决策边界。**

四个反直觉现象：看 200K token 不一定更聪明、可能只是更乱；给 40 个工具不一定更强、可能混乱迷失；开 8 个 SubAgent 不一定更全面、可能只是让主 Agent 拿到 8 份无法合并的噪声；给完全自主权不一定更像专家、可能只是更快把错误扩散到外部世界。

> Agent 时代的架构设计：**在不确定性里设计边界，在有限预算里分配注意力，在可积累的轨道上沉淀经验。**

## 第三代模式语言

| 代际 | 解决 |
| --- | --- |
| 第一代 GoF | 对象复杂度（确定性对象之间怎么协作） |
| 第二代分布式模式 | 网络、状态和失败复杂度（不可靠服务之间怎么协作） |
| **第三代 Agent 设计模式** | 运行时决策、上下文注意力、工具副作用、经验累积、多 Agent 协作和治理边界（概率智能在工程系统里怎么可靠工作） |

不是 GoF 过时——用 GoF 模式很难描述"Claude Code 修 bug：感知上下文→形成假设→调 grep/read→改代码→跑测试→根据失败调整"这样有感知/推理/行动/反思/工具调度/失败学习/权限边界的过程。

## 四层结构

1. **7 个认知功能**：完整智能系统闭环——感知是入口、治理是动作出去前的闸门；记忆解决跨时间状态、协作解决跨空间状态；推理负责做决策、反思负责审计决策；行动是智能对现实世界的真实改变。
2. **6 个执行拓扑**：一步步走=链式；多路同时看=并行；从多条路里选=路由；试了再改=循环；主 Agent 拆给子 Agent=层级；Agent 之间统筹协调=编排。
3. **28 个工程模式**（第一模块打地基：范式危机、双轴框架、逆向五步法；后八个模块探讨模式主体）。
4. **工程实现**：源码剖析 + 代码案例（上下文分诊如何实现、失败日记的业务场景、技能包实操、扇出汇聚多子 Agent 评审、可观测回放）。

**坐标系是"思维参数"**：讨论 Agent 系统时先问"它主要在解决哪类认知问题"（感知不准/记忆断裂/推理成本太高/工具调用失控/协作治理），再问"这个能力应该怎样被编排"。

## 28 个模式不是 28 个技巧

> 本质上都在回答同一个问题：**不确定性下，有限的资源该怎么分配。**

示例：上下文分诊管注意力分配（有限窗口里谁应该进入）；语义压缩做有损压缩（哪些能压、哪些永远不能压——如错误堆栈）；工具调度解决行动路由中的工具分配/风险/状态刷新；生成-批评体现生成和评估的不对称性（**找 bug 比写出没有 bug 的代码容易**）；经验回放把经验资产变成下一次任务的可用上下文；审批门控承担信任分级。

共同点：都在处理某种稀缺资源——感知分配注意力、治理分配信任，中间几层各自分配时间、成本、风险、经验和角色。

双轴：Y 轴认知功能（WHAT，花什么资源）× X 轴执行拓扑（HOW，怎么花）。底层判断：**Agent architecture is bounded resource allocation under uncertainty**——不是让模型自由发挥，而是让有限的注意力/记忆/工具/权限/信任资源被花在最值得花的地方。

## 你会锻造三种能力

1. **看穿系统的能力**：一个 Agent 不稳定，除了"模型不够强"还会问——看错上下文？没有记忆？推理档位不对？工具太多？没有反思？多 Agent 上下文污染？治理层缺失？**从使用者到设计者。**
2. **组合模式的能力**：真实业务是混合问题——金融研报 Agent 需要多模态融合（PDF 图表）+RAG（历史报告）+复杂度路由（控成本）+生成-批评（事实核查）+审批门控（防直接发客户）+可观测性（引用链）。**单个模式只是零件，适配组合才是架构。**
3. **设计成长机制的能力**：做错留失败日记、做对沉淀技能包、做过一批任务经验回放、长任务进度追踪、多人协作交接产物、治理层回放记录——**Agent 才会从第 1 天的聪明，长成第 365 天的老练。**

## 收尾

软件工程过去几十年的稳定主题：**把偶然成功变成可重复成功**。今天很多 Agent 成功是偶然成功（模型刚好看到对的信息、选对工具、没跑偏、格式符合预期、没触发安全问题）——工程师要把"刚好成功"背后的结构找出来、命名它、约束它、复用它、组合它。

不需要一直追最强模型、不需要押宝某个框架、不需要背下 28 个模式，而是学会设计一种系统：一开始也许只是 50 行 PRA 循环，但**每次执行留下痕迹、每次失败变成材料、每次成功有机会变成技能、每次协作形成工件、每次上线能被治理和回放**——这样的 Agent 才值得托付。

> 编辑小新老师总结：**记失败、存经验，价值始聚；知进退、懂组合，系统方生。**
