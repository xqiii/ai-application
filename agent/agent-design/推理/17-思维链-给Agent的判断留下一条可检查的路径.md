# 17｜思维链：给 Agent 的判断留下一条可检查的路径

> 来源：极客时间《Agent 设计模式之美》黄佳 · 推理：演化之美
> 原文链接：https://time.geekbang.org/column/article/994287 （时长 20:46）
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

生产级 CoT 不是"写出思考过程"的提示词技巧，而是**推理结构**：用一条主路径把复杂判断拆成若干**可验证命题**（一步一个 ClaimStep），每个命题绑定证据、依赖和验证器，形成 claim DAG，最后由 Decision Gate 决定放行——普通 CoT 说"我认为合理"，生产 CoT 说"S6 依赖 S3/S4/S5，各自来自计算器、政策 v7、审批验证器，所以可放行"。

## 模式定位

CoT 处理推理分诊台的**中间路线**：问题需要拆解，但还没复杂到要同时维护多条分支。在推理契约中回答两问：
- **采用哪种拓扑**：一条主路径，前一步输出是后一步输入，不并行投票、不迭代闭环。
- **由什么验证**："P 的 6 月应发比 5 月高 18%""增量主要来自季度奖金""该租户规则要求涨幅超 15% 核查审批"——这些不是模型自说自话，而是可被工具/数据库/规则引擎/人工独立检查的对象。

看起来像推理 vs 真的能用：加一句"请逐步思考"会输出读起来很完整的分析，但要追问——查的是哪张考勤表？有奖金审批单吗？生效月份系统确认了吗？**CoT 每一步都要能落回证据，形成能对账的判断**。

思想谱系：波利亚《How to Solve It》（1945，解题可拆开复述检查）→ GPS（1957）→ Scratchpad/CoT/Zero-shot-CoT → Self-Consistency/Tree of Thoughts/ReAct → 推理模型时代。共同点：把复杂问题拆成中间状态。**模型越会想，系统越要会记账。**

## 一步只表达一个可验证命题

不合格的一步："综合分析员工 P 的工资、奖金、政策和历史记录，判断变化是否合理"——把观察/拆解/计算/核对/查证/判断全塞一步，系统不知道核心是什么、用哪个工具验证、错了影响哪些下游。

**三问检查每一步**（答不上来就不该进正式 Trace）：
1. 有没有明确的命题（立论）？
2. 能不能被工具/规则/数据库/人独立检查？
3. 这个命题错了，下游哪些步骤受影响？

18% 薪资异常的正确拆法：
- S1（OBSERVE）：P 的 6 月应发比 5 月高 18%——证据：两期薪资快照
- S2（DECOMPOSE）：拆成三个子问题：增量来源/规则触发/审批匹配
- S3（DERIVE）：增量主要来自季度奖金——工具 payroll_delta_calculator，观察 basic=0/allowance=0/bonus=8400
- S4（VERIFY）：租户规则要求涨幅超 15% 核查审批——证据 policy:payroll_anomaly:v7
- S5（VERIFY）：审批单存在且金额/审批人/生效月份匹配——验证器 approval_validator，passed
- S6（DECIDE）：属于有审批支撑的季度奖金，可自动放行——闸门 payroll_release_gate，passed

**CoT 五步法**：观察 Observe → 拆解 Decompose → 计算/推导 Derive → 验证 Verify → 决策 Decide。

## 工程实现六层

1. **Step Schema 限制"什么叫一步"**：ClaimStep 含 kind（OBSERVE/DECOMPOSE/DERIVE/VERIFY/DECIDE）、claim、subject/predicate 结构化命题、depends_on、evidence_refs、validator、status（DRAFT/PASSED/FAILED/NEEDS_REVIEW）。最关键的是 kind——类型分开，程序才能对不同步骤施加不同约束。
2. **原子性闸门（Atomicity Gate）**：静态检查（一句话出现 ≥2 个"并且/同时/因此/所以/可以判断/综合来看"即疑似承载过多）+ 类型约束（OBSERVE 必须有证据且不依赖派生步骤；DECOMPOSE 必须依赖已观察问题、输出子问题而非外部证据；DERIVE 必须有依赖和工具；VERIFY 必须有证据和验证器；DECIDE 必须有依赖和决策闸门）。
3. **验证器注册表（Validator Registry）**：把谓词绑定到确定性验证器。**Validator 不一定是另一个 LLM**——金额一致性给计算器、政策生效给规则引擎、审批人权限给权限系统、工资重复发放给数据库查询。LLM 适合拆解问题、生成检查计划、解释结果，不适合独自承担所有判断。
4. **依赖图防错误一路传下去**：最终决定不依赖自然语言上下文，只依赖已通过验证的上游节点。**失效传播**：S4 政策版本验证失败 → S5/S6 不是"低置信度"而是"依赖已断"，必须一起作废。
5. **追踪运行器（Trace Runner）**：不"替模型思考"，只执行结构化步骤、检查依赖、运行验证器、决定停止——形状错误/依赖未过/验证失败都会即时停止并给出 stop_reason。
6. **LLM 只输出步骤草稿（StepDraft）**：模型负责提出"下一步想表达什么命题"及类型；程序（ClaimCompiler）负责补证据引用、调工具、绑验证器、查依赖，把草稿编译成 ClaimStep。**LLM 提出候选命题，程序编译成可验证节点**——因为 LLM 不该自己决定"我已经有证据了"，证据要来自 RAG/数据库/工具/规则/人工确认，validator 来自系统注册表。

## 三道闸门（CoT 的停止条件）

1. **证据闸门**：没证据的判断不能进入最终决定，只能留在草稿区。检查证据存在、来源权威、版本正确、有效期覆盖、**属于当前租户和员工**——企业系统里跨租户误用证据比推理错误更危险。
2. **确定性验证闸门**：能用确定性程序验证的不交给模型自评。LLM 可以解释验证结果，但不替代验证器。
3. **升级退出闸门**：CoT 适合一条主路径能走通的问题。触发升级：证据缺失/冲突、规则版本不唯一、验证器失败、关键依赖无法确认、模型连续两次改写同一事实、工具结果与模型解释不一致——升级到并行探索、迭代假设验证或人工复核，不要让 CoT 硬编。

## Provider state vs Application trace

跨轮问题必须分清两种状态：

| | 供应商侧推理状态 | 应用侧审计轨迹 |
| --- | --- | --- |
| 是什么 | API 层的推理续接状态（previous_response_id / 加密推理项） | 系统自己维护的结构化记录 |
| 目标 | 让模型下一轮接着想 | 让业务事后可复盘 |
| 局限 | **不是业务审计记录**——不能指望加密推理项告诉审核员为什么放行了某人的工资 | 任务 ID/推理模式/每步主张/证据/验证器/停止原因 |

> **Provider state 帮模型续想，Application trace 帮系统负责。**

注意：不要只保存最终答案，也不要把原始长篇 CoT 全量长期保存；长期经验复用要经过验证、脱敏、蒸馏后再写入记忆层。

## 关键要点（复习用）

1. CoT 工程定位：用一条主路径把复杂判断拆成可验证命题，为 Validator 放行做准备。
2. 一步一个命题，三问自检（有立论吗/能独立检查吗/错了影响谁）。
3. 能确定性验证的交给计算器/规则引擎/权限系统/数据库，不交给模型自评。
4. 失效传播：上游验证失败，下游不是低置信度而是依赖已断，必须作废。
5. 该用才用：简单任务被硬塞推理又慢又贵又啰嗦——这是设计思想不是万能法则。

## 思考题（课程留题）

1. Agent 是否所有请求都默认"逐步思考"？按推理边界分四档（不开思考/浅想/结构化推理/高风险推理），多少请求其实可以不开思考？
2. 最近一次有争议的 Agent 决策：能拆成观察/规则核对/查证/决策并每步挂证据吗？挂不上的地方就是 is_accountable() 该拦下的地方。
3. 给 trace 加上 claim 和 evidence_refs，找一个跨三轮工具调用的任务观察。
