# 16｜推理模块导论：让 Agent 想得清楚，也想得起来

> 来源：极客时间《Agent 设计模式之美》黄佳 · 推理：演化之美

## 一句话总结

推理不是把思维链写得更长，而是**调度一条最短、充分、可验证的决策路径**——一座"分诊台加三个诊室"：复杂度路由先判值不值得深想，CoT/并行探索/迭代假设验证分别管"想清楚对账""多口径择优""顺根因深挖"；核心是让概率系统持续产出可控、可复现的决策。

## 模块定位

感知让 Agent 看见此刻，记忆让 Agent 留住过去，推理回答：**面对眼前的信息和过去的经验，接下来该相信什么、该选择什么、该做什么**。（18% 涨薪案例：证据取回来了，但它是正常调薪、混入一次性奖金、重复计算还是用错规则版本？该放行、转人工还是拦截？——都是推理的活。）

## 来龙去脉：缝合两个时代

- 传统推理脉络：生存经验（乌云→下雨）→ 亚里士多德三段论 → Logic Theorist（1956）/GPS（1957）/STRIPS（1971）/专家系统 MYCIN——核心是"规则清楚、过程可解释"，程序即推理、代码即证明。弱点：规则人工编写、维护成本高（80 年代专家系统没带来真正 AI 的根源）。
- LLM 推理：概率生成，把模式和启发式压进权重——灵活但概率性、不透明、不稳定（同输入不同路径；prompt/采样参数/上下文顺序/工具返回都可能改变结论）。
- **给 LLM 多写业务规则 ≠ 可靠推理系统**。要分清三个东西：
  1. 模型内部推理（可能不暴露）
  2. 系统组织的外部慎思（提假设、查工具、比证据、调验证器）
  3. 供工程师审计的决策记录（看过哪些证据、为何升级、什么规则放行）
  
  **不能把一段看起来有条理的自然语言当成模型真实计算过程的证明**——Anthropic 研究发现模型生成的 CoT 并不总是忠实披露实际影响答案的信息。

> LLM 给了一个很会猜的推理器，Harness 要做的是给它装上**边界、仪表盘和刹车系统**——把传统 AI 的状态、目标、证据、搜索、验证、停止条件重新装回来。

## 推理已变成运行时资源

两股力量改写了推理：① 被训练进模型（o1、DeepSeek-R1 靠 RL 把"会想"压进权重，涌现长链推理和自我验证）；② 被产品化成运行时资源（reasoning_effort、GPT-5 实时 router、adaptive thinking——"想多深"成了调用参数）。

核心问题从"怎么让 Agent 多想几步"变成"**让 Agent 自己判断如何推理**"：值不值得深想？一条路还是几条路？给多少 token/时间/工具调用？证据够了何时停？推不出何时升级？

四个薪酬问题对应四种推理策略：
| 问题 | 策略 |
| --- | --- |
| 小冰几号发薪（查日历即可） | 直接回答 |
| 咖哥应发高 18% 该不该放行（拆工资组成核对审批） | 链式分解 CoT |
| 小雪命中两版奖金政策按哪版算（多口径比较） | 并行探索 |
| 月底总账差 37 万缺口在哪（提假设查数据缩小范围） | 迭代假设验证 |

## 快慢思考与推理契约

Kahneman System 1/System 2：快自动低耗（直接生成/小模型/缓存/规则）vs 慢刻意高耗（结构化分解/并行搜索/反复验证/强模型）。

**推理契约（Reasoning Contract）五问**：
1. 是否启动深入思考？（直接回答够吗）
2. 采用哪种推理拓扑？（链式/并行/循环）
3. 投入多少预算？（token/时间/模型调用/工具调用）
4. 由什么验证？（单元测试/业务规则/外部数据/人审/另一个模型）
5. 什么时候停止？（达到什么证据标准输出，什么情况升级或放弃）

**计算预算控制**（test-time compute 是可显式管理的维度）：

```python
@dataclass
class ReasoningBudget:
    max_thinking_tokens: int = 8000
    max_latency_ms: int = 12000
    max_model_calls: int = 4
    max_tool_calls: int = 8
    max_parallel_paths: int = 3
```

答案稳定后就别再消耗推理 token。

## 四种推理模式（一座分诊台加三个诊室）

| 模式 | 拓扑 | 经济学选择 |
| --- | --- | --- |
| 复杂度路由 | 分诊台 | 用轻量判断，换整体成本和延迟下降 |
| 思维链 CoT | 链 | 用一定 token，换问题分解和中间产物 |
| 并行探索 | 并行 | 用更多计算路径，换对单一路径偏见的抵抗 |
| 迭代假设验证 | 循环 | 用更多轮次，换未知环境中逐步逼近真相 |

控制链：**先路由再推理，推理之后要验证，验证不通过就换路，达到停止条件才输出**。没有一种方式永远最好——在准确率、成本、延迟、风险、工程复杂度之间找适合业务的点。

## Reasoning Trace：记录决定，不记录脑内独白

不要把模型 thinking 字段的整体"内心戏"直接当记录——**记录外部可核验的决策事件**：ReasoningStep 一步一记 hypothesis（要验证的命题，不是私密思维）/ evidence_refs（实际引用的可追踪证据）/ action / observation / decision / confidence（要做 calibration）；ReasoningTrace 记 mode、route_reason（为什么分到这个 mode）、budget、validator（谁放行）、stop_reason、escalated_from（从哪个更轻的 mode 升级）。

**四个健康指标**（按任务类型分桶建基线和 SLO）：
1. **验证通过率**：最终结论通过业务规则/测试/执行/人审的比例
2. **首次路由命中率**：第一次选的模式是否够用——大量直接请求升级到迭代 = 低估难度；大量低风险查询进高成本并行 = 过度推理
3. **单位验证成功成本**：获得一个通过验证的正确结果平均要多少钱、多少延迟（便宜模型反复失败重试升级可能更贵）
4. **推理漂移率**：长任务中目标、约束、已验证事实是否被逐渐遗忘或改写

## 关键要点（复习用）

1. 推理工程 = 用最少的充分计算得到可验证的正确决定，不是想得最多。
2. 推理契约五问：是否深想、什么拓扑、多少预算、谁验证、何时停。
3. 三样东西分清：内部推理、外部慎思、审计记录——自然语言的条理 ≠ 计算过程的证明。
4. 四模式是四种经济学选择，先路由再推理。

## 思考题（课程留题）

1. 你的 Agent 是不管难易都用同一个模型吗？用 30 天账单估算"单用顶配" vs "便宜档+顶配档路由"差多少钱。
2. 回想一次拿到足够信息却绕很远才给答案的情况：真的需要推理，还是缺一个明确的规则/流程模板？
3. 长任务跑到第十步还记得第一步的约束吗？在 trace 里加 hypothesis 和 evidence_refs，看事实和规范何时被悄悄改写。
