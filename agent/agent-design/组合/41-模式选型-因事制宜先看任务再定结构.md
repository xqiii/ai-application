# 41｜模式选型：因事制宜，先看任务，再定结构

> 来源：极客时间《Agent 设计模式之美》黄佳 · 组合：集成之美
> 原文链接：https://time.geekbang.org/column/article/1021399 （时长 22:56）
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

模式选型 = **因事制宜**：先弄清任务需要哪些判断、什么结果算办对、什么事情不能做，再决定把多少工作交给模型——**已有办法够用就继续使用；有做不到的地方，再比较候选方案**。学过设计模式不意味着每个 Agent 都要多加几个模式。

## 开篇：为什么还要接入 Agent

有同学问："涉及钱的操作，金额、顺序和权限都要由程序控制，直接写程序不就行了吗？"——**如果输入规范、步骤明确，程序已经能办好，就直接用程序。**

需要 Agent 的场景：客户不按表单提要求（"上周那单我想退掉"、把退货换货优惠券发票混在一起"帮忙一起处理"）——**用户意图模糊、操作流程不确定、明显存在操作风险的场景**。

## 售后服务案例（347 元退款，订单 O-9938，申请 YF-R-0311）

规则：500 元以内符合条件可自动处理；**已开过发票的订单要交财务处理**。

**第一步（先于选模式）：什么结果算办对？什么事情不能做？**
- 退款助手的任务是**按规则处理申请，不是无论如何都把钱退掉**——发票情况不明要按规定转财务核实
- **系统不应该因为没有退成钱就认为自己失败了**——这两个问题不说清，后面用再多模式也无法判断系统是否正确地完成了任务

**第二步：步骤已确定就交给程序（何时引入模型）**
- 表单入口（申请号/金额/原因编码规范）→ 完全由普通程序完成：发票未知转人工、条件满足继续办理、等待人工/保存进度/失败处理由工作流编排
- 模型派上用场的入口：聊天里"上周那单，外包装破了，东西还没用，我想退掉"——没说订单号没填字段，传统 CRM 束手无策。把订单摘要和聊天记录交给模型整理诉求、提出候选订单
- **分工**：模型帮助理解客户的话；退款金额从申请记录读取、发票从业务数据源查询、权限由程序检查（**已有明确来源的内容不需要模型猜测**）；答复先用固定模板（"申请已转人工，还需核实发票情况"）——**模板可用就没必要再调一次模型生成回复**
- 第一版设计：模型整理诉求，程序按既有流程办理，模板报告结果——**流程仍由程序控制，模型只参与其中一部分；它与"模型每轮自行选工具决定下一步"的自主 Agent 是两种设计**

**第三步：发票没查到——加评审还是转人工？**
- "发票状态未知" ≠ "财务确认未开票"（可能发票已开出只是查询数据没同步）
- **再让模型重新分析或找另一个模型评审，都不能凭空补出财务记录——缺的不是更多推理，而是一条经过核实的事实**
- 转人工 + 说明"需要核实这张订单是否开过发票"= **审批门**的工作：根据当前事实和规则决定自动办理/人工处理/不允许操作

**第四步：工具调用前后的检查（护栏三明治）**
- 创建付款指令前检查：发票状态未知只能创建人工处理单——**即使模型提出付款请求也不能跳过检查**
- 操作后再查：人工处理单有没有创建？付款指令有没有被错误创建？

**取舍**：采用审批门+执行前后检查，**不需要为"发票未知"再增加一次模型评审**——要补上的是财务确认，不是再一次分析。

## 实验证据（refund_selection_demo.py）

两份独立数据，金额都是 347 元，唯一区别是发票状态：

| | 发票状态未知 | 财务已确认未开票 |
| --- | --- | --- |
| 事实 | invoice_status=unknown | invoice_status=none |
| 起草建议 | queue_human（建议转人工，业务数据未变） | auto_approve |
| 执行后 | 退款状态=pending_human，新增人工处理单 HAP-0311，**无付款指令** | 退款状态=approved，**新增模拟付款指令 PI-0311** |

**注意建议和办理的区别**："起草"是程序按规则给出处理建议，不是让模型写答复、没创建单据、不改变业务数据；实际办理后才出现单据。**改变结果的不是模型而是财务确认。**

## 第六步：什么时候值得再调用一次模型

新问题：客户追问"照片已经传了，金额也只有 347 元，为什么还要等？"——单条模板可能够用；但若客户经常把多件商品/不同凭证/几轮沟通放一起问，客服每次重写说明很麻烦 → 再让模型起草答复（**第二次模型调用**）。

三处模型判断（提示链）：
1. **意图识别**：程序交订单摘要+聊天记录给模型，只要求整理诉求和疑问（不判断能不能退款）→ 模型给出候选订单 O-9938；**程序核对候选订单是否属于当前客户**（对象不清先请客户确认）
2. **中间：程序查清事实给建议**：保留客户原疑问+补上业务信息（金额来源/凭证检查已通过/发票状态尚未核实/规则建议转人工）。**来源要分清**：347 元来自退款申请、凭证和发票来自业务查询、建议来自规则——**客户说"照片已经传了"只说明他认为自己完成了上传；系统查到"凭证检查已通过"才说明凭证满足要求**
3. **回复问题**：模型拿材料起草解释（凭证已通过、347 元在小额范围、**目前还没核实是否开过发票**、按规则需人工确认）

> 这就是提示链：第一次调用理解问题，程序在中间核实情况，第二次调用根据情况组织答复——两次可用同一或不同模型，**重要的是后一次拿到的材料和前一次不同**。
>
> **为什么不在第一次调用时顺便写好回答？**它那时还不知道凭证有没有通过、发票有没有核实——不知道这次等待究竟是什么原因。

## 第七步：什么时候才需要模型安排步骤

组合订单场景（两件退货一件换货、用过优惠券、一件已开票）——**仍然不一定需要规划执行**：企业已有成熟组合售后流程就直接调用。

只有这类请求经常需要临时安排步骤、现有流程难覆盖时，才有理由让模型参与计划（步骤1 核实退货入库 → 步骤2 核实发票处理 → 步骤3 计算可退金额等1和2 → 步骤4 提交退款等3）。**模型提出安排后，程序要检查并保存计划、记录每步是否完成**：第一二步业务上可并行；**第三步必须等前两步结束，不能仅因模型写在计划里就提前执行**；改计划时已完成的步骤不能因重写变成"还没做"。

**三种编排方式用一个问题区分——"下一步由谁决定？"**
- 固定流程：开发时写好的程序决定
- 边查边决定（ReAct 式）：模型根据最新结果选择
- 规划执行：模型先提计划，程序保存、检查、推进

**计划做完 ≠ 满足付款条件**：假如模型漏写"核实发票"这一步，其他步骤全完成，付款程序也必须检查发票状态——**该核实的没核实就不能付款（护栏三明治的基本要求）**。

回到 347 元退款：查什么、何时转人工、何时继续办理都有明确规则——**直接让程序按规则执行就够，暂时不需要模型另拟计划**。涉及客服/财务/风控三个部门也不意味着建三个 Agent——只是从三个系统取资料的话程序调三个查询工具即可；**等确实需要不同角色分别调查、各自保存过程、结果交回共同处理时，再考虑层级委派**。

## 八、双轴矩阵怎样帮助选择

两类问题：**要补哪项职责**（能否自动处理→治理判断；多段模型工作怎么衔接→行动安排）；**怎样组织这项工作**（按条件走不同出口→路由；理解申请/查事实/起草答复有固定先后→提示链；运行时产生不同计划→规划器）。

坐标落地：审批门=治理×路由、提示链=行动×链式、规划执行=行动×编排。

**选型卡记录比只写"采用了审批门、提示链"有用**——后来接手的人能看出为什么这样设计、哪些结论还没验证；**相关设置也应随测试结果留下**（如迭代假设检验允许试几次/何时停/最多花多少钱）。

## 九、自家项目的通用顺序

> 已有办法够用，就继续使用；有做不到的地方，再比较候选方案。

1. 先说清楚**任务怎样才算完成、哪些事情不能做**
2. 让现有程序或最小方案走一遍，看**究竟哪一步还做不到**
3. 针对那个困难选少量候选，**用同一批任务比较**
4. 比较时不只看有没有办成——**还要看有没有增加原来不会犯的错、时间和费用能不能接受**
5. **记录最终决定并写明哪些部分还没验证**；每项结论都要有对应的检查

示例：差旅系统——问"住宿标准是多少"能准确找到现行制度就先给条款和出处；复杂问法需结合几处解释时再加生成；**不涉及替他办理业务就不需要照搬退款的整段审批流程**。同一员工说"帮我订好下周的行程"——任务变了（比较时间费用、可能替他作出预订承诺），才重新考虑计划和审批。**要不要审批，取决于系统能够做出什么操作。**设备故障调查：几份记录互相矛盾、需提假设再用检测排除→迭代假设检验；已有成熟诊断树→程序沿既定分支查询也能完成；需同时调查机械/电气/控制→先看能否独立展开（各有资料和明确范围）→扇出聚合。

**同一个行业不同任务可能需要不同结构；不同行业也可能遇到同一种问题。**

## 收束：回头看学过的模式

面对任务只问：**我的任务究竟卡在哪里？** 再对照 7 组模式。同样是回答错了，原因可能完全不同：资料没找到→改善查找；用了过期资料→检查更新；材料正确却推断错误→才看推理和评审。同时保证可观测性。

两条轴：一条看"要负责什么工作"，一条看"这些工作怎样组织"——步骤固定先后用链式；不同条件不同出口用路由；互不依赖用并行；根据反馈调整用循环；分层分工逐层检查用层级；统一维护计划协调依赖用编排。

> **模式的增加代表着复杂性也随之提升**：多一个循环就要处理什么时候停止；多一个角色就要处理它交回什么、谁来检查。**只有当任务确实需要这些安排，增加的工作才有必要。**

选型后应能说清四件事：**遇到了什么问题、为什么这样安排、怎样知道有效、还有什么没有验证。**

## 思考题（课程留题）

1. 如果所有客户都通过规范表单申请退款，会删掉第一版设计的哪部分、保留哪部分？
2. 发票状态未知时，补上什么信息才能继续判断？增加一次模型评审能否获得这项信息？
3. 找一项正在做的业务：什么具体变化会让你考虑从固定流程转向规划执行？引入后又多了哪项检查？
