# 40｜可观测性：看清过程，改对系统，留下可追责的运行史

> 来源：极客时间《Agent 设计模式之美》黄佳 · 治理：守正之美
> 原文链接：https://time.geekbang.org/column/article/1020682 （时长 24:14）
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

可观测性（治理×编排）在运行关键位置留下**结构化事实**，用共同标识、前后关系、版本和证据引用关联起来——日志只告诉我们某个组件做过什么；可观测性把提案、策略、批准、额度、权限和业务结果串起来，说明一项行动**为什么发生、又怎样走到最后**。三个关键词：**结构化事件、因果关系、完整性**。

## 开场案例：100 元补偿券没到账

Agent 说"100 元补偿券已发放，请到卡包查看"，用户没收到。单看最后一句话无法区分：券发给了另一个账号？请求还在等审核？根本没调发券工具？

完整记录揭示：发券工具确实返回 "200"，但返回内容还有关键字段 **pending_review**（申请已受理，等待审核）——**Agent 把"申请提交成功"说成了"券已发放"**。

**工具调用成功 ≠ 补偿券发放成功，是两项不同事实。**聚焦三个问题：① 工具返回状态传给回复生成器时有没有被保留？② 提示词有没有说清"受理"和"完成"的区别？③ 回复发出前程序有没有核对实际发放状态？——**和模型强弱无关：中间程序记了 success=True 把"待审核"丢了，后面的模型再强也缺判断依据。**传统系统也有异步受理与最终完成不一致的情况；Agent 又多了一步自然语言解释和判断，更可能把有限状态扩写成过度承诺。

血脉：Google Dapper（2010，跨服务追踪）→ Agent 时代还要保存当时拿到的上下文、选择的工具、最后的业务结果——调用链说明请求怎样流转，券有没有到账要到卡券系统确认。

## 多种可观测信号

| 信号 | 作用 |
| --- | --- |
| 日志 | 某个环节发生的事（支付适配器返回超时） |
| 追踪 | 把一次请求各步接起来（Trace/Span：发券工具调用一段、模型生成回复一段） |
| 指标 | 看一批任务趋势（最近一周 UNKNOWN 付款突然增加） |
| 评测 | Agent 在工资异常识别上是否仍达标 |
| **重放证据** | 在不重新付款的前提下还原当时判断路径——**主要是读取历史输入/版本/决定/结果重建已发生路径，不一定要再执行外部动作**（外界已变：余额变了、模型版本更新、接口不同，重新发起业务运行太难） |

## 模式定义与三个关键词

> 可观测性，就是在运行的关键位置留下结构化事实，用共同标识、前后关系、版本和证据引用把它们关联起来，帮助人查清过程、核对结果。

1. **结构化事件**：不能只说"付款成功"——结构中还要说明谁付款、付给谁、用哪张票据、消费哪个预算信封、对应哪版提案和政策
2. **因果关系**：审批发生在付款前 ≠ 审批一定导致这笔付款——要明确记录这次工具执行消费的是哪张审批票、哪笔付款属于哪个批次、哪次降权由哪项事故触发
3. **完整性**：除了检查已有日志没被篡改，还要检查**本来应该出现的审批、额度和权限控制有没有被绕开**

（双轴：专栏早期放"治理×编排"；ADPS 后续调整为 X1 横切工程面——贯穿整个生命周期，检索/记忆/规划/协作需要它，调试/评测/产品改进都依赖它。前三讲都靠它闭环：审批门证明谁批准了什么；爆炸半径证明额度怎样预留消费；渐进承诺提供升权降权所依据的真实结果。）

## 玻璃罩里的机械表

梁博比喻：在透明玻璃罩里组装修理瑞士机械表——零件很多但能看见每个零件在哪儿工作。界面把意图识别/路由判断/推理步骤按顺序展开，每步可查看当次真正使用的提示词、模型输出、调用成本。**这些记录来自真实调用位置，能指向某次检索、某个参数、某版提示词。**梁博团队跑通基本对话后就开始建这条时间线，再往上加能力——每加一层记忆/规划/工具调用都能马上看它怎样影响原有行为。

## 观测过程也要观测结果

马阳阳老师三个观察层次：**先看事情办成没有 → 再看卡在哪里 → 最后检查相关组件**——只查接口看到全部正常就结束排查，会漏掉第一层。

结果观测示例：成本 = 一段时间 Token 总消耗 ÷ 成功完成任务数（**失败尝试花的钱也算进去**，人工返工另计）；耗时把成功与失败任务分开看，少数反复重试任务单独算；产物（分析报告/失败日记）**观察后来有没有被使用**（是否据此创建任务）、采用率提供业务线索，同时抽检正确性。

## 最容易缺的记录在模型之外

SDK 给我们模型调用/Token/耗时；**业务结果有没有兑现，SDK 并不知道**。

多类标识各有用途：**trace_id**（同一次追踪）、**span_id**（其中哪一步）、父子关联/链接（哪一步接了谁的工作）、**业务申请号**（把追踪与券系统接起来、几小时后回调靠它接回原任务、长任务跨多次运行）。

**版本记录**：用户昨天得到的承诺不能拿今天改过的政策解释——保存当时实际使用的模型/提示词/检索材料/工具版本，才能判断条件在哪一处变了；当前状态可更新，关键变化要留给以后查询的人和 Agent。

**"当时有哪些选择"容易忽视**：它没用某个工具可能是判断不需要，也可能是权限过滤后根本看不到——**工具被过滤、审批被拒绝、额度不足时都应留下记录，说明原因与规则版本**。

**合规双查**：日志有发券记录但找不到对应批准记录——拿申请编号到审批系统查询：已批准则查为什么批准记录没传到日志平台；发券时还在等审批则查程序为什么提前发券。**只记"发券成功"不能说明合规，还要能查清发券前有没有得到应有批准。**

## 业界实践

- **Factory + LangSmith**：调用步骤与 AWS CloudWatch 日志关联，用户反馈附到对应调用和工作流阶段、汇入数据集——收到"这段代码建议不好"能找到当时输入/上下文/输出，改完拿原例子再测
- **Canva + Langfuse**：Help Assistant（Java + OpenTelemetry）和 Omni Agent（Python SDK）两套技术栈进同一平台。**参与分析的不只有工程师**——QA 标注、内容设计改回答与检索、日本市场业务人员建语气评测（工程师知道接口超时，未必知道哪种措辞让客户不舒服）
- 平台选择：LangSmith / Langfuse / Arize Phoenix（追踪+评测各有特色）；OpenTelemetry 是采集传递标准；已有 Grafana/Prometheus 不必全换——**先拿一条真实投诉试走一遍**：能否找到对应运行、看到模型收到什么工具返回什么、再到业务系统确认结果——走一遍才知道缺的是没记录、记录关联不上、还是业务结果缺乏清晰记录
- 重放 vs 测试：查旧记录=看已发生的经过（程序没重新作决定）；测新版本=修改后的程序重新运行但**发券工具由保存的响应代替**，不办真实业务（Canva 案例：输入与预期结果存数据集，离线实验用模拟工具响应代替真实调用）

## 查清一次也要改好下一次

同一表现（"Agent 说错了"）有两种根因、两种修改：① 转换代码只保留 success=True 丢了 pending_review → 改转换代码把业务状态传下去 + 回复规则对应上（待审核只能说申请已提交）；② 状态传到了但模型把所有成功调用解释成"办理完成" → 调整状态解释规则、提示词给清晰规则说明。

**改完怎样检验**：不必再替用户申请券——把当时保存的工具响应作为测试输入，交给修改后的转换代码和回复程序，只检查状态有没有传下去、回答有没有与状态相符。**测试未结束**：还要拿"确实已发放""申请被拒绝"的例子再测（防改完对所有情况都只会等待）——这些例子成为**回归测试集**，以后换模型/改提示词/改逻辑可复用。

**同一份失败样本贯穿调查与验证**：原因由团队检查 → 修改经测试与审核后发布。

## 三模式配合（同一任务恢复场景）

薪酬 Agent 付完部分工资、提交下一笔超时、进程退出。另一进程接手：

| 模式 | 回答 |
| --- | --- |
| 进度追踪 | 做到哪了：恢复位置——哪些已确认、哪些没处理、哪笔结果未知 |
| 交接链 | 接到了什么：任务账要求 v3 资料、收到 v2 就停在交接处 |
| 可观测性 | 先前发生了什么：找到当时请求/审批/额度/重试。**钱到底付没付要凭原请求编号向银行查询**——确认成功补结果不再付款；确认未生效才按当前有效批准和权限继续；查不清保留"结果未知"避免重复付款 |

三者可共用同一个业务任务编号。

## 记录也要管：谁能看、存多久、能不能改

1. **分清楚谁需要看什么**：客服查申请走到哪步不需要完整银行账号；开发者排查错误不需要用户密码；审计要知道谁批准了什么、执行有没有超批准范围——不同人不同内容，够用就好；本地部署也要设权限
2. **不该存的内容在记录送出去之前处理**：密码/访问令牌不写日志；账号/证件号按需脱敏；检查工具会不会自动收录；模型输出敏感信息必须有护栏拦截
3. **遮住信息后前后记录仍要对得上**：审批批准付账户 A、实际付到 B，两处都显示"账号已隐藏"就看不出区别——不展示完整账号，但要留有权限者能核对的**账户编号和版本**
4. **不同记录保存办法不同**：普通调试详情可只留一部分；付款/审批/额度/权限变更关键记录长期单独保存（用户可能几天后投诉）
5. **检查记录有没有真的存下来**："业务已经做了日志却没留下"要及时提醒——**查不到记录时不能直接认定动作没有发生，应核对业务账和外部回执**
6. **记录不应被随意修改**：发现错误追加更正（哪里错/谁改/为什么），不是删除原始记录

## 治理模块收官：三道控制一条运行史

798 张工资单 13,706,097 元，钱发出去以前：

| 控制 | 查什么 |
| --- | --- |
| 审批门 | 这份清单批过没有？谁签的字、签字时看的是不是眼前这一版、批准现在是否有效 |
| 爆炸半径控制 | 实际最多能付多少？批准总额按部门分好，每付一笔占用相应额度 |
| 渐进承诺 | 现在允许这个 Agent 做多少？接手更多部门要先有运行成绩再经升权批准 |
| **可观测性** | 把检查和执行的经过一起留下：谁按什么规则批准了哪份清单、每笔钱用了哪份额度、Agent 当时什么权限、银行给了什么结果；事故后也能查到谁在什么时候收回付款权限 |

**运行结果为审批、额度和权限调整提供依据，调整后的规则再约束下一次执行**——如果 Agent 被纠正频率越来越高，先别急让它接手更多，查清总在哪类任务出错；调整时"改了哪条规则、为什么改、谁决定、从何时生效"都要记下来。传统日志每天只记"完成了多少笔付款"，解释不了这些变化。

## 思考题（课程留题）

1. Agent 有没有"接口全成功，任务却没完成"的情况？最终结果应到哪个业务系统确认？
2. 拿一条用户投诉：能找到当时的输入/工具返回/策略版本/执行身份吗？哪一段最容易断？
3. 选一次真实失败：保留什么材料才能在不重复办理业务的前提下检验下一版是否改对？
