# 39｜渐进承诺：自治要靠证据挣出来

> 来源：极客时间《Agent 设计模式之美》黄佳 · 治理：守正之美
> 原文链接：https://time.geekbang.org/column/article/1019669 （时长 18:43）
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

渐进承诺（治理×链式★）= 把"逐步交给 Agent 的资源和行动空间"做成可检查的规则：每次扩权都要有相应运行证据和批准，证据失效或发生严重事故时权限能收回——**先让 Agent 在小事、窄范围、可撤销的动作中证明自己，再逐步把更大的工作交给它；出了严重问题，先收回相关权限，再谈恢复。**

## 开场类比：电影票 vs 国际机票

愿意先让 Agent 帮买电影票，不会第一天就把订国际机票交给它——电影票选错损失有限；国际机票牵涉姓名/证件/签证/转机/行李/退改，填错一个字母都麻烦。**Agent 成功买过几张电影票，只能说明它完成过低风险购买，不能证明它会处理一家人的跨国行程。**

企业带新人同理：新财务第一周先看流程、核对单据、整理付款清单 → 生成付款提案由主管复核 → 稳定后独立处理小额付款 → 变更供应商账户/提交整月工资/重大资金调拨仍保留更高一级确认。**先分配一小块工作看结果，结果稳定再交下一块。**

## 治理三模式闭环

| 模式 | 问什么 |
| --- | --- |
| 审批门 | 眼前这一项动作能不能开始？ |
| 爆炸半径控制 | 即使开始以后出错，最多能影响多少？ |
| **渐进承诺** | 连续完成许多次任务后，下一次能不能少问一次人、多做一点事？ |

**每一次运行的结果，都会影响以后能够获得的自治范围。**

## 信任的对象是一项具体能力

简单系统只有两档权限（能执行/不能执行），试点后一下从"不能改数据"跳到"可以发消息、提交订单、执行付款"——中间少了好几层。客服 Agent 擅长查询订单不一定适合关闭客户账户；代码 Agent 能改测试分支不应因此获得生产部署权限。

正确问法：**这个版本的 Agent，在哪项能力上已经表现稳定，可以在什么范围内独立工作？**薪酬 Agent 示例：可以独立生成上海市场部工资结算提案，但提交银行付款仍受限——**一项低风险能力积累的好成绩，不能直接借给另一项高风险能力使用。**

## 两只钟表（不能混用）

**第一只：一项任务里的钟**——先做成本低、可撤销的动作，再走向成本高、难撤销的：
- 代码 Agent：读取代码 → 生成补丁 → 运行测试 → 部署测试环境 → 小流量发布 → 扩大生产流量
- 薪酬 Agent：读取花名册 → 计算工资 → 生成结算草稿 → dry-run 检查 → 小批次真实执行 → 完整结算

**第二只：很多次任务之间的钟**——低权限反复运行、表现稳定后才申请进入下一档：只能看 → 可以建议 → 可以影子运行 → 可以小范围真实执行 → 可以在规定范围内自主处理。

**混用的两个方向都是错的**：今天一次模拟检查通过只能支持今天这份提案往下走，不会让长期权限自动升级；已能自主处理常规业务的 Agent 遇到高风险任务仍要完成该有的校验和审批。

## 五级阶梯

| 等级 | 考验什么 | 要点 |
| --- | --- | --- |
| 观察级 | 能否找到正确数据、分清版本、识别对象、信息不足时停下 | 刚接入就找错工资表，后面算得再漂亮也没用 |
| 建议级 | 把事情准备好（付给谁/付多少/依据/异常） | 人能直接判断，不必从头调查 |
| 影子级 | 在真实任务旁边跑（同批输入生成清单但不提交） | 逐项比对员工/金额/异常；**只跑很多次却不找对照结果，仍不知道做得对不对**。风险：可能读敏感数据/配置错误写入生产——只读凭证、隔离输出位置、资源限制仍要保留 |
| 受限级 | 接触真实后果 | "允许执行"写成具体范围（某部门/最多多少人和钱）；影子测试再准也可能没遇到真实写入时的超时/并发/重复请求 |
| 自主级 | 已批准日常范围内独立完成，不必每步等人点 | 绝对金额上限、租户隔离、重大例外审批仍在——**自主不是没有边界，而是边界内不再频繁打断** |

类比 Google 金丝雀发布：先让一小部分真实流量接触新版本，用结果决定是否扩大——**每一步都有对照和退路**。

## 工作台实验

- 三次晋级（观察→建议→建议→影子→影子→受限），**每次要求五条证据分别来自五个部门**（Engineering/Finance/Ops/Sales/Support）——避免只凭单一场景的重复成功获得晋级
- 四种请求检查：影子级模拟整月结算→允许；影子级实际执行整月结算→拒绝（当前只能模拟）；受限级 20 人 168,658 元→允许；受限级 798 人 13,706,097 元→拒绝（超当前权限，代码上限 50 人/100 万元）
- 三种模式各管什么：**审批门检查提案有没有获准；预算限制防止执行超额；渐进承诺检查这个 Agent 目前有没有资格承担这么大的任务**（即使审批门和预算都通过，当前等级允许范围更小就不能继续）

## 成功记录怎样变成晋级依据

追问"五次成功是谁说成功的？是不是把同一次结果复制五遍？"——RunOutcome 字段：run_id（防同一次成功重复计算）/ success / blocker / **evidence_ref**（指向业务结果或独立评测记录）/ **evaluation_slice**（证据覆盖哪类任务，防只挑简单样本）/ **occurred_at**（证据产生在当前策略和权限版本之下）/ **recorded_by**（谁记录，生产还需受信验证器核实）。

EvidenceWindow：检查运行编号和证据引用是否重复、时间是否早于当前权限签发时间、调验证器确认可信。**重复提交同一次成功不会增加晋级所需次数。**

**证据窗口在审批前后保持同一版本**：晋级时把一批证据锁成整体、审批人批准的就是这批——等待审批期间只要又出现一次失败，原来那批证据就变了，之前批准随即失效需重审。

**证据要和即将开放的权限相匹配**：给它多大权限，就先让它在相应金额/任务/租户/工具/异常场景中受检。受限级只拿 Ops 部门信封（160 人/2,748,960 元）；自主级处理整月结算但仍守各部门信封（798 人/13,706,097 元）。结果：limited 阶段 638 笔越信封被拒；**supervisor 签不了自主级票据（approval_authority_mismatch——审批权限也要匹配）**；autonomous 阶段 13,706,097 元执行。**连续处理一百笔百元以内报销，不足以证明能独立处理千万元工资结算。**

业界参照：CSA Agentic Trust Framework（2026-02）把持续表现/安全验证/治理签署列为晋级条件；微软 Agent Governance Toolkit（2026-04）把动态信任/执行权限/紧急停止放进运行时设计——**权限要跟着证据和风险变化，不能一次授予后就不再过问。**

## 升权要慢，出事先收权

升权：积累证据 + 观察期 + 审批。**严重事故：先停下来止损，不能按慢流程收权**——实验中自主级直接降回观察级（`incident INC-2026-07-08 -> level=observe`），原权限凭证立即失效；事故前成绩不能直接拿来申请恢复（`promotion_evidence_stale` + `promotion_evidence_thin`）——**必须在新版本、新策略下重新运行重新证明**。降级后旧凭证申请原本获准的 20 人小批次：拒绝；可用于重新晋级的记录：0 条。

降权也不能让任何人触发——普通调用者随手把生产 Agent 打回观察级也不合适（需权限与流程约束）。

## 生产化考量

1. **究竟准备多交给它哪一项工作**："升到自主级"不够具体——可能只想让它独立处理一类常规退款，没打算允许改客户账户。**权限按能力和业务范围分开**，出问题能针对性收回，不必停掉所有能力
2. **什么结果足以说明可以接手**：开放退款就比退款对象/金额/理由是否正确、能否识别重复申请、遇例外会不会转人工——不能只看工具返回成功，更不能只让 Agent 给自己打分。还要看放权后表现：人工纠正/回滚/事故明显增多说明测试没覆盖新风险
3. **权限必须在执行时真正生效**：付款/发信/写库/部署执行前都检查当前权限；严重事故时独立控制面可立即冻结相关能力，**不能等 Agent 自己停下来**

另一误区：做成漫长官僚流程（每级大量人工表格，Agent 永远停试点）。**成熟系统让证据尽可能自动形成**——测试结果/银行回执/工单状态/人工改判/回滚结果/异常记录自动进证据窗口；人主要处理晋级标准、边界任务、重大例外。

## 有些决定始终交给人

系统稳定后人可以少点日常确认，把精力放到放权标准/困难样本/重大例外/事故处置。但有些责任不能凭成功率自动交出：变更重要收款账户、删除不可恢复数据、有法律与人事后果的决定——**企业应提前规定哪些动作即使 Agent 处于自主级也必须人工确认**。反过来也不必每次晋级都做漫长材料审批——规则清楚、记录自动形成时，符合条件的日常检查可由系统完成，人处理需要判断和承担责任的部分。

## 思考题（课程留题）

1. 说"某个 Agent 可以自主工作"时，具体指哪项能力、哪个环境、什么范围？
2. 检查付款/发信/写库/部署的执行代码：它读取的是一张具体能力凭证，还是只根据"这个 Agent 已经可信"放行？
3. 反向测试：换掉模型版本、让权限凭证过期、人为加一条严重失败记录——旧权限是否真的失效？Agent 还能执行的话，边界漏在哪？
