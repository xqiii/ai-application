## 一句话总结

Agent 治理 = **在运行时分配行动权**：把具体提案交给策略裁决，为错误设置硬上限，让权限随可核验结果变化，并保存能够还原责任的运行记录——四个问题：能否放行（准入）、怎样追责（证据）、最多影响多少（损失范围）、权限怎样增长与收回。

## 管孩子的类比

每天两小时屏幕时间（一小时视频一小时游戏），边界内他自己安排——拆成三个二十分钟、游戏换视频、做家务换时间。规则带来了想要的东西：学会分配时间 + 拥有选择。**有规则让人轻松，还在可控范围内增加了自由**。但规则留下协商空间：多五分钟似乎没问题，一次次单独看都说得过去，连起来却可能偏离"学会管理时间"。

Agent 治理同样：人每一步都点头，Agent 只剩自动填表；只看眼前一笔调用，一串分别合规的动作合起来可能越界。**既要给它做事的空间，也要看住空间的边界。**

## 四个治理问题（发 100 元优惠券案例）

客服 Agent 给用户发 100 元优惠券，动作很小却包含三类治理问题 + 第四个时间维度：

1. **能否放行（准入）**：工单是否满足补偿条件、金额是否在权限内、需不需要人看
2. **怎样追责（证据）**：事后能找到用户请求、Agent 提案、采用的策略、审批结果、工具返回值、业务系统实际变化
3. **最多影响多少（损失范围）**：判断错也只影响这一张工单，不能顺手改全站补偿规则、不能重试连发十张
4. **权限怎样增长又怎样收回**：今天积累的成功记录是否足以换明天更大的操作空间

## 策略漂移实验：悄悄变宽的现金线

六月月末测试账本：798 PAID + 2 REVERSED，结算总额 13,706,097 元。两条规则之一是全款自动通过的金额上限：

- 上限 13,000,000 → **escalated**（转人工）——拒绝信息完整：`limit=13000000 observed=13706097.0`
- 上限放宽到 30,000,000 → **accepted**——**放行回执的 policy marks 是空的**

**拦下来的时候说得出哪条规则拦的；放过去以后，规则反而从记录里消失了。**放行记录没记采用的规则版本，事后只知道"通过了"，说不清"按什么规则通过的"、谁提出放宽、谁批准、为何调整。

（放宽限额本身可以没问题——比如公司为一次补发临时批准；问题是无据可查。）

## 三个对象分开保存：提案、策略、回执

```python
ActionProposal  # 准备做什么：绑定任务契约、结算工件、动作范围、幂等键、风险等级、可逆性
PolicyRef       # 按哪一版尺度判断：policy_id + version + content_digest
GovernanceReceipt  # 谁在什么时间作出什么裁决：control + proposal_digest + policy_digest + decided_by + decision
```

三份记录 = **申请单、规则版本、处理回执**。摘要按内容算出；执行入口付款前重新核对：眼前提案和当前生效规则是否与回执对应——金额/收款对象/策略版本变了就按新内容重新判断。这样财务问"这份清单超了 1300 万怎么还能通过"，能查到用的是限额 3000 万的第二版规则，再查这版规则的负责人和修改原因。

**四眼原则**：Agent 想把限额从 1300 万提到 3000 万，不能自己提出自己批准——提出修改的人不能同时填成批准者，程序报错（`four-eyes: policy 'cash-line' v3: proposer and approver are the same actor`）。**不仅付款需要审批，放宽付款规则也需要审批。**

**付款前重新核对回执**：提案金额或对象改变后旧回执摘要对不上，执行入口拒绝付款。

## 四个问题四种模式

| 问题 | 模式 |
| --- | --- |
| 这笔钱能不能付？ | 37 审批门 |
| 出了错会影响多大？ | 38 爆炸半径控制 |
| 什么时候可以让它自己多做一点？ | 39 渐进承诺 |
| 事后能不能查清经过？ | 40 可观测性 |

分成四种模式的原因：**这些规则经常需要分别调整**——临时提高某月结算额度，不意味着 Agent 从此可以自行批准大额付款；预算变了，审批人的责任和 Agent 的权限仍要分别确认。分开设计后能说清这次改了什么、哪些约束必须继续有效；改额度时检查额度、改权限时检查权限。

（ADPS 版本说明：ADPS 共同体后续把可观测性调整为 X1 横切工程面贯穿全部模式；专栏保留教学编排，以 ADPS 模式目录为准。）

控制面分工：**策略负责判定，执行层只消费当前有效的回执、额度和权限凭证。**

## 边界越清楚，日常打断越少

没说清哪些事可以交给 Agent，它就只能不断来问；人被问多了，容易从认真审批变成随手点"同意"。治理要先分清：哪些可以自己完成，哪些必须停下来找人确认。

业界参照：OpenAI Codex 安全设计区分**沙箱**（限制访问哪些文件、能否连网）和**审批策略**（哪些操作需要人确认）；Claude Code 提供权限设置和工具执行前检查。但具体检查什么仍由业务方决定——允许 Agent 用付款接口 ≠ 它提出的每笔付款都该执行（工资核对过吗、这笔钱付过吗、金额变了要不要重新审批）。新加坡 Agentic AI 治理框架（2026-01）：事前评估风险、明确哪些环节人负责、开发运行中持续检查、让使用者了解能力/限制/操作责任。

## 从教学 Repo 到生产系统五要点

1. **确认是谁在操作**：用户/Agent/审批人身份从可信登录与身份系统取得，不能程序随便填名字
2. **查得到规则来历**：当前限额多少、何时生效、谁提出修改谁批准——旧版本不能直接抹掉
3. **真正付款前必须检查**：最终执行付款的程序核对申请内容/审批结果/剩余额度/当前权限，不能只在前面页面检查一次
4. **分清钱付到了哪一步**：已支付/未支付/查不到结果分开记录；银行超时先查清有没有付成，不能直接再付
5. **出事后查得清也停得下**：保留脱敏操作记录，提供不依赖 Agent 自己决定的停止手段

自检方法：从"真正提交付款"的那段代码往回看——它执行之前检查了什么？"超过限额必须审批"只写在提示词里、付款程序却不检查批准记录 = 要求没真正落实。

## 思考题（课程留题）

1. 系统记录"通过"时，能查到当时采用的哪一版规则吗？
2. 提高付款限额应该由谁批准？现有记录能查到修改前后数值和原因吗？
3. 找到真正执行付款/删除数据/对外发消息的代码：它执行前检查了什么，哪些要求只写在提示词或文档里？
