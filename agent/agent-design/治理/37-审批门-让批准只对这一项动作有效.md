# 37｜审批门：让批准只对这一项动作有效

> 来源：极客时间《Agent 设计模式之美》黄佳 · 治理：守正之美
> 原文链接：https://time.geekbang.org/column/article/1017203 （时长 21:19）
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

审批门（治理×路由★）位于动作生效之前，根据主体/参数/资源/环境/影响/可逆性在自动放行、人审、拒绝之间路由；人审后，人的决定**只绑定当前提案、当前策略、当前身份和有限有效期**——一次点头只打开眼前这一扇门。

## Agent 给审批带来的新问题

传统审批无处不在（请假超三天要主管批、报销超额升级、供应商换收款账户财务复核、生产发布等放行；GitHub 要求生产部署过指定 reviewer 且禁止自我批准；AWS Step Functions 暂停等决定）。传统申请单是固定的，审批人看到已成形业务对象。

**Agent 会在运行时决定调哪个工具/什么参数/多少对象/什么次序**——用户一句"把这个月符合条件的退款处理掉"，Agent 先查订单、判资格、生成清单、调支付接口。作者亲历：Claude Code 写好给老板的邮件"还没发，你自己点"，有时补一句"你告诉我一声，我帮你直接发"——不觉得轻松而是紧张。

"让人看一眼"不够了，要回答：人看见了什么？批准的是哪一版对象？批准后 Agent 还能不能改参数？等待期间数据变了怎么办？这声"同意"能用几次、沿用到什么时候？

## 人机在门前怎样交接

粗糙的审批："这是高风险操作，是否继续？"——人不知道它查了什么、为什么、改哪些对象，只能凭感觉点批准；出问题后系统说"这一步有人确认过"。**这不叫人类监督，只是把责任推给信息不足的人。**

**三方分工**：Agent 把动作做到"可审"再来敲门（先完成工具和规则能做的，把事实整理成紧凑决策材料）；人的精力放在价值判断/业务例外/重大影响/责任归属（不是 Agent 一犹豫就送人）。

**不合格审批卡 vs 合格审批卡**（供应商换收款账户案例）："支付本月供应商货款，是否批准？"几乎没有价值——真正该注意的不是"支付货款"而是"**收款账户刚刚变了**"。合格审批卡要素：申请动作 / 金额 / **关键变化**（账户 ****2381→****9042，变更时间今天 10:42，18 个月内首次）/ 核验结果（主数据匹配、变更申请已取得、**回拨确认完成**、发票与采购订单一致）/ Agent 建议（允许付款但仅限此发票）/ 批准后影响（创建不可自动撤销的银行付款指令）/ **批准范围（仅本次、仅此账户、仅此发票、30 分钟内有效）**。

**证据不足 ≠ 需要审批**：证据不足说明 Agent 没做完，应继续查证/澄清/停止；需要审批说明事实已基本清楚，只是影响和责任超过自动权限。提案进人审前四条件：执行对象已确认 / 关键证据已取得 / 外部影响已说明且可计算的算清 / 可逆性和后续步骤已说明。

**审批范围五维度**：谁批准 / 批准哪项动作 / 作用于哪些对象 / 有效期内 / 最多用几次。聊天里一句"可以"有很多含义（这次可以/这批可以/今天内可以/以后类似都可以/允许 Agent 自己判断）——审批门要把自然语言决定**编译成有边界的许可**。参照：Codex 建议选"能完成任务的最窄授权"；Claude Code 区分临时批准/会话级授权/持久规则和 allow/ask/deny。新加坡框架称"**有意义的人类责任**"——重点不在流程里出现过一个人，而在这个人是否拥有足够信息、权限和时间作出有效判断。审批者角色要分清（NIST：审批人/系统所有者/业务操作员/最终用户各有所指）。审批者不一定永远是人：确定性规则处理硬拒绝和明确放行，边界请求可先交独立 reviewer agent（Codex auto-review）——改变谁来检查，没取消边界。

## 薪酬工作台：工件漂移实验

798 张（13,706,097 元）清单获批（**双人会签**：Alice 薪酬 + Bob 资金，一个不够）→ "补回两张工资单"（E0007、E0012 合计 38,444 元）→ 新申请 800 人 13,744,541 元 → 用旧批准付款 → **拒绝：审批回执未绑定新提案**（old_approval_authorizes=False）。

```
artifact_digest: 22d2af5795fa3f23 → 97139db8d8fc35cd
```

**工件漂移**：审批人的级别没有问题，问题出在批准对象已经换版——两位负责人没批准后来加进来的两张单据。下一步是把新增人员和差额交给他们重新确认。

## 为什么付款前还要再查一遍

**审批与执行之间有时间差——TOCTOU（Time of Check to Time of Use）**：检查时成立的条件，使用时可能已变。生产执行器付款前至少重新确认四件事（GovernanceReceipt.authorizes()）：
1. 回执决定是 ALLOWED
2. 回执绑定的提案摘要 = 当前提案摘要
3. 回执绑定的策略摘要 = 当前生效版本
4. 回执尚未过期

执行器从可信存储读回执；账户状态/结算版本/资金余额等业务条件也要提交事务前重检，用版本条件或锁防止检查后再变。

## "等待审批"是持久化运行状态

审批把 Agent 运行切成两段：前半段形成提案，后半段批准后恢复；中间可能等两分钟或两天——库存/余额/人员状态/代码版本/其他 Agent 的结果都可能变。必须持久化保存：run_id / intent_digest / policy_digest / approval_id / approval_status / required_approver / expires_at / **resume_node** / business_preconditions。

恢复时不能拿审批结果直接跳到工具调用——重新读取当前提案/策略/关键业务状态再验票据：对象变了重新生成提案；票据过期重新申请；条件仍成立才执行。（AWS Step Functions 暂停状态机等回调；LangGraph interrupt() + 检查点——注意恢复时从被中断节点开头重新运行，中断前的外部操作要防重复。框架提供暂停恢复机制，业务仍要决定保存哪些事实、回来重查哪些条件。）

**对审批规则本身的审批**：把上限从 1300 万提到 3000 万 = 更多付款可自动通过，不能由 Agent 自己决定。教学实验里普通主管无权批准，必须 CFO 点头（更严格可要治理+风险负责人共同批准）——**防止绕行：一笔付款过不了，Agent 先把规则改松，再拿新规则批准自己的付款。**

## 注意事项：审批疲劳

风险不只和工具名称相关——"读取数据库"可能是查一条订单也可能是导出全部客户资料；"运行命令"可能是 git status 也可能是删生产数据。审批门要看：调用者/动作/目标资源/环境/对象数量/金额/数据敏感度/外部可见性/可逆程度。没有放之四海的金额表，企业要建的是**委托尺度**：什么动作自动做、什么动作哪级角色批、哪些动作谁批都不能做。

两个问题：① 这项动作要不要交给人（自动放行/人审/拒绝分流）？② 交给哪个人或哪几个人（低额付款→薪酬主管；大额批次→财务控制人；收款账户变更→财务和资金分别确认）。

**审批疲劳**是头号落地问题——用 Claude Code/Codex 的人都会对一遍遍 Approve 厌烦到不知道批的是什么（后来 Claude Code 推出自动 Approve 常用命令的 Auto 模式）。**成熟审批门的目标是让人少审批，只看到值得点的那几次。**观察指标：人审比例/退回率/拒绝率/平均等待/票据过期率/对象变化失效率/高风险动作绕过审批。某条规则连续半年零拒绝 → 检查它是否还有必要进人审；确认风险和适用条件稳定后再考虑自动放行。

## 关键要点（复习用）

1. Agent 把事情做到可审（对象明确/证据齐全/差异突出/影响可见）；人判断例外/权衡后果/承担责任；系统绑定当前提案、当前策略、当前身份、限制时间和次数。
2. 审批门目标不是处处插人——日常动作安静通过，少数高风险动作带着完整材料来到人面前。

## 思考题（课程留题）

1. 你的审批单展示的是动作摘要，还是把真正变化的字段单独标出？
2. 哪些动作频繁进人审其实已稳定可自动放行？哪些金额不大但不可逆或涉及个人权益仍应人审？
3. 等待批准两小时后哪些业务事实可能已变？恢复路径会重查还是沿用旧批准？
4. Agent 缺关键证据时会继续查证、退回澄清，还是把问题包装成审批单交给人？
