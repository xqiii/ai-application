# 38｜爆炸半径控制：把最大损失写进系统

> 来源：极客时间《Agent 设计模式之美》黄佳 · 治理：守正之美
> 原文链接：https://time.geekbang.org/column/article/1020047 （时长 19:25）
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

爆炸半径控制（治理×层级★）= 在动作执行前建立**不可自行扩张**的资源与效果边界，每次外部效果发生前核减额度；边界沿任务层级逐层收窄——**任何子任务都不能通过拆分、并发、循环或重试获得父任务没有的权限**。类比：审批解决"这次能不能花"，额度解决"最多花到哪里"；一道门负责放行，一道保险丝负责短路时截住损失。

## 模式定位：批准正确，执行仍可能出错

审批人判断的是准备执行的业务提案；真正产生外部效果还要经过工作流/执行器/消息队列/网络/外部 API/回调——每层都可能出新故障。运维 Agent 扩容 2 实例可能扩出 200 个；客服 Agent 发补偿券循环终止失效连发 10 张；营销 Agent 发 500 名测试用户、下游把测试分组解释成完整名单一次覆盖十万人——**没有谁越权进入工具、动作类型都经过批准，问题出在一次合法动作产生超过预期的实际效果**。

**爆炸半径不能按工具名称粗略设置**：send_message 可以发一条回复也可以推送全会员库；update_employee 可以改办公电话也可以批量终止劳动关系；run_command 可以 git status 也可以删生产数据。要看真实资源/对象集合/数量/金额/速率/环境/传播范围/恢复条件。

## 爆炸半径不是一个数字（五个维度）

| 维度 | 限制什么 | 例子 |
| --- | --- | --- |
| 资源与数据 | 碰到哪些系统/租户/对象/字段 | 只允许上海租户、工资表、已批准员工集合 |
| 数量与速率 | 每次/每批/每窗口产生多少效果 | 每批最多 160 笔，每分钟最多 20 次 |
| 成本与时间 | 消耗多少资金/Token/算力/时间 | 本次最多 13,706,097 元，最多运行 30 分钟 |
| 并发与传播 | 启动多少 Worker、写多少下游 | 最多 3 个子 Agent，只允许一个并发付款写入 |
| 恢复与停止 | 怎样暂停/对账/补偿/终止 | 未知结果占住额度，停止开关切断后续提交 |

**最危险的往往不是单笔大动作，而是一串小动作的累计**：每次更新 100 条看起来谨慎，派生 10 个 Worker 各更新 100 条 = 写入 1000 条——每个调用没越界，组合起来越界。**限额不能只设在单次工具调用上，要选合适的聚合层级：单个动作/一次运行/一个身份/一个租户/整组 Agent。**

很多事故不首先表现为资金损失：错误邮件发 10 人和 10 万人单封成本一样、声誉后果完全不同；子 Agent 多跑 10 分钟可能只多几美元，但若不断派生 Worker 影响沿协作关系放大。

## 双信封结构

- **Hard Envelope 硬边界**：租户隔离、禁止工具、生产凭证、绝对金额上限、敏感数据类别——**只能由独立管理面或更高等级人工流程修改**。"硬"不代表永远不能改，意思是**正在运行的 Agent 和当前任务没有修改它的权力**
- **Autonomy Envelope 自主边界**：当前批量/速率/对象集合/并发数/自动化档位——硬边界内随场景和运行证据收放

有效范围 = 多层交集：effective_scope = hard_envelope ∩ principal_scope ∩ task_scope ∩ capability_scope ∩ current_context_scope ∩ evidence_based_scope。金额和数量取最小上限；对象集合取交集；**任意一层明确禁止，动作就不能继续**。

## 三层边界各管一段

1. **能力边界**：能调哪些工具、访问哪些账户租户服务、拿到什么凭证（AWS IAM permissions boundary——边界规定身份最多可能得到哪些权限，但边界本身不授予权限）
2. **执行边界**：代码运行在哪里、能写哪些目录、访问哪些网络、启动多少进程（Codex Windows 沙箱把文件写入与网络访问作为 OS 层两类约束；K8s ResourceQuota 在 namespace 层限制 CPU/内存/对象数量，超硬上限拒绝创建）
3. **业务效果边界**：最多转出多少钱、修改多少员工、发多少邮件、影响多少客户、多长时间内

前两层解决"技术上能到哪里"，第三层解决"业务上最多会发生什么"——**沙箱能阻止写出工作目录，却不知道工资单该付 8,111 还是 81,110；完全合法的邮件 API 也能在沙箱内向十万人发错误消息。三层逐层收窄，技术沙箱与业务额度不能互相替代。**

血脉：Bulkhead 船舶水密舱——一个舱进水其他舱仍工作；软件里连接池/服务实例/资源池分开。Agent 场景还要隔离租户、资金、客户、数据。

## 拆任务不能复制权限

根任务 100 万采购预算拆给 5 个采购 Agent，每个都配"最多 100 万" = 系统实际创造 500 万行动空间。**任务拆分可以复制工作，不能复制权力**：根任务持有总信封，子任务从父信封**预留**更小份额，父级剩余额度随预留减少，子信封总和永不超过父信封。

未使用子额度可以返还但有条件：子任务已结束、没有仍在跑的调用、没有结果未知的外部效果——否则 Worker 把额度返还后旧请求晚到、下一个 Worker 重新消费同一份额额 = 双重支出。

## 薪酬工作台：重试风暴实验

798 张 13,706,097 元已获 CFO 批准（票据正确绑定结算集），按五部门分批付款（Engineering/Finance/Ops/Sales/Support 各 160 或 158 张）。固定故障：Ops 批次（160 人）正常执行后再多跑四遍。

**无额度**：money out = **24,701,937 元**，多付 10,995,840 元。审批门为什么没拦住？——**审批检查的是准备执行的结算提案，提案没变；错误出现在执行阶段，同一项已获准动作实际发生五次。审批批准的是计划，爆炸半径控制约束的是实际效果。**

**有信封**：根信封 = CFO 批准的整月总额；五部门各预留子信封（同时限制金额/付款次数/员工集合三维度）。执行器每发一笔钱先从对应信封提款（BudgetEnvelope: max_amount/max_payments/allowed_refs，draw() 检查通过才更新）。重跑结果：money out = **13,706,097 元**，**refused draws = 640**（首条拒绝：envelope_amount_exceeded :: draw=8,111 remaining=0）——**程序 bug 还在，业务损失已被限制在批准范围内**。额外付款为零不代表无代价：无效工作、告警、人工处置仍有成本——爆炸半径控制把损失从不可追回的钱换成可处理的拒绝记录。

越界尝试也会被拦：给已满的根额度再建 500 万补发信封 → `reservation_over_parent :: child=5,000,000 parent_remaining=0`；子信封处理父名单之外的员工 → `reservation_out_of_scope`。

## 幂等键穿过系统边界

外部调用结果不确定：向银行发付款请求后连接中断，本地不知道成没成功——立刻退额度，重试可能形成第二笔付款；永不退，卡住真实失败的请求。

解法：付款准备阶段生成稳定 idempotency_key；超时重试沿用同一键；下游看到相同键返回第一次结果（Stripe 官方做法：相同键重试返回同一结果并检查参数一致）。

**EffectPermit**（一次性效果许可）四状态：IN_FLIGHT → COMMITTED / RELEASED / **UNKNOWN → 对账后再进 COMMITTED 或 RELEASED**。UNKNOWN 期间额度继续占用；独立对账任务读银行流水决定额度已消费还是可释放——**Agent 自己说"刚才应该没成功"不能成为释放依据**。

> 预算信封限制累计效果，幂等键负责识别"这是不是同一次请求"。

## 先小后大也是缩小半径

不只"达到上限后拒绝"，还可以分阶段落地先观察再扩大：发布先一个实例/少量流量（健康指标+业务验收通过再扩）；群发先内部种子名单（退信率投诉率正常再扩）；改数据 dry-run 后先改 100 条（对账抽样通过再扩）；扩容先加 2 个实例设自动回收；付款先按部门或受控批次（每批回执完整账实一致）。新加坡+Google Sandbox 把受控测试、渐进式真实部署、风险分级监督、"有边界的灵活性"列为落地要点。

（这里缩小的是已获批准动作在本次运行中的即时半径；39 讲渐进承诺处理的是长期自治等级能否提高。）

## 边界必须放在 Agent 之外

**写在提示词里的"本次最多支付一千万元"不是爆炸半径控制**——模型可能忽略提示词，提示词也无法阻止另一条路径/回调处理器/补偿任务直接调银行接口。真正的控制必须位于**统一的外部系统**：付款/重试/恢复/回调/人工补单都经过同一个账本和同一组限额。

Agent 若拿着能直连银行的凭证或能改写预算账本，程序里有检查也未必拦得住——**执行 Worker 只拿受限凭证，由统一入口核对额度后提交付款；硬上限交给独立管理流程**。K8s 资源配额文档指出：管理员不仅要创建 ResourceQuota，还要限制其他主体删除或修改配额，否则边界本身会被执行者拆掉。**一个能自行提高额度、关闭计量或修改停止开关的 Agent，是危险的、没有边界的。**

## 从 Lab 到生产三问

1. **一次错误企业最不能接受什么损失？**薪酬怕多付也怕付错人（同时圈金额和名单）；营销在意打扰多少客户；云资源先看实例数和小时费用——先找业务后果再决定限什么限多少
2. **哪些执行者实际在花同一份额度？**生产里 10 个 Worker 同时付款，账上剩 10 万、两个 Worker 同时申请 8 万——不能各自查完余额都通过。**检查和占用额度要在同一笔事务里**；金额统一用"分"或十进制定点数
3. **出了问题谁能确认结果、谁能停下后续动作？**银行已付款回执没回来时，查本地日志不够，要有人或独立程序去银行对账；额度继续占用，重试沿用原幂等键；止损时值班人员能从独立入口停止新付款

测试方向：沿同一笔付款试并发领取、重复提交、丢失回执。

## 思考题（课程留题）

1. 系统真正需要限制的是单次大动作还是大量小动作的累计？限额设在工具调用、一次运行还是整个租户上？
2. 请求超时后记成失败、成功还是 UNKNOWN？获得证据以前额度是否仍被占用？
3. 三个子 Agent 分别拿到合法额度，谁负责保证总和不超过根任务上限？
