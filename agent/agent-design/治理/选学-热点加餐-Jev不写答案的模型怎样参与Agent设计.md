# 选学｜热点加餐：Jev——不写答案的模型，怎样参与 Agent 设计？

> 来源：极客时间《Agent 设计模式之美》黄佳 · 治理：守正之美（加餐，时长 16:51）
> 原文链接：https://time.geekbang.org/column/article/1019029
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

Jev（TypeSafe AI 2026-09-15 发布，称 System One）把"需要理解语义但结果不是一段话"的小判断从生成模型里拆出来：**复杂分析和代码生成交给生成模型、需要理解语义的小判断交给 Jev、能准确计算检查的交给程序**——朴素三分工；核心提醒：**模型给出的判断和程序随后允许发生的动作要分别设计**。

## 为什么需要 Jev

排障流程里事情难度差别很大："这段日志和当前故障有没有关系？"（看懂做判断就够）/"下一步先查配置还是调用方？"（几个方向选一个）/"修改重试逻辑同时避免重复扣款"（才真正需要复杂推理）——前两类也必须动用负责复杂分析和写代码的模型吗？

Jev 三接口（都需先把问题问清楚）：
| 接口 | 怎么问 | 返回 |
| --- | --- | --- |
| Choice | 下一步先查配置、依赖服务还是业务代码？ | 一个选项 + 各选项概率 |
| Score | 这份文件对当前排障有多大帮助？ | 按预先定义等级的加权分数 |
| Noul | 这段记录描述的是一次连接超时吗？ | 命题成立的概率值 |

使用要点：Choice 候选项由开发者提供——只给"配置/代码"两选项模型就无法回答"信息不够"，**通常还要留一个"暂时无法判断"出口**；Score 要先说明评分依据（分等级再评分，不是只问"你觉得多相关"）；Noul 适合边界明确的是非问题（"这段日志是否描述连接超时"比"这个系统有没有问题"清楚得多）。

**边界**：分类和排序早就是机器学习任务——不生成文字不代表没有理解和判断能力；但官方列出短板：复杂间接推断、计数和日期比较。"共有多少条超时记录""两个日期相差几天""金额有没有超上限"——**程序本来就能准确计算，没必要绕一圈问模型**。

## 排障接入示例

测试环境订单接口超时（三条材料：连接超时/未收到响应/最近调整过 HTTP 代理配置）→ 先让 Jev 在"查配置/查依赖/查代码/材料不足"中做选择 → 业务代码把 config 对应到**已登记的只读函数** → 拿到材料再交生成模型深入分析。

**Jev 没有自己翻整个仓库、没有修改配置权限——它只建议排查方向；能读什么、用哪个工具读仍由程序控制。**

两个硬提醒：
1. **把"只允许只读"写进问题里只是在告诉模型任务范围——真正的只读限制要由工具权限和运行环境落实**
2. 问题先后顺序："先读哪份配置"可现在问，"这份配置哪里有问题"要等配置读回来才能问——同一份材料上的独立判断可批量提交，有前后依赖的必须一步步来；但**拆得越细未必越好**（每增加一个判断环节都要准备输入处理返回，前面选错方向后面还可能漏关键证据）

## 接在不同位置，做的事也不同

沿排障过程放回 ADPS 模式可找到接入点：挑材料=上下文分诊、挑模型=复杂度路由、检查结果=生成评审。**但接入时更重要的是把每一步写清楚**：
- Jev 判断某份文件"很相关"，程序是否一定加载？未必——可能超数据权限、可能已有足够重复材料
- Jev 建议重启服务，程序是否可执行？不能——可能当前任务只允许查看、生产环境可能禁止变更时段

> **"做这件事可能有帮助"和"现在允许做这件事"是两个问题。**

检查生成结果同理：Jev 判断"修复说明是否解释了超时原因"，但**接口究竟修好没有要看实际测试**——说明写得再完整，测试没通过仍不能发布。

## 大海捞针案例：从 182 个 Skills 中选出适合技能

Hermes 182 个技能，问题不只是"有没有"还有"会不会选错"（想修改已有 PPT，目录里同时有制作新 PPT、编辑 PPT 等相近能力）。两轮处理：
1. 先判断这次请求是否需要技能；需要就从简短目录选出排名前三候选
2. 再读候选的完整描述和部分指令，检查是否真的适合——**细看后都不合适可以一个都不推荐**

关键：**第二轮不能只是给第一轮盖章——必须有机会发现"刚才看简介觉得适合，读完指令才发现不是我要的"**。

官方数据：488 条请求中 315 条有合适技能，错误加载率从 16.8% 降到 7.3%（jev-1.12 + 固定版本 Claude Haiku；换到自己的目录需重新验证）。细节：推荐结果交给后续 Agent，Agent 仍保留自己的技能目录并决定加载什么——**评测要分开看：推荐有没有选对、后面 Agent 有没有真的加载对**；技能涉及生产数据库还要查版本/访问权限/执行范围。

**最喜欢的设计是保留"一个都不选"**——三个不合适的候选也能排出第一名，第一名只表示"相比另外两个更好"，不表示能完成任务。**实际系统里允许拒选，常常比继续调整排名更重要。**

## 支持 Jev ≠ 所有判断都能交给它

Vercel AI Gateway（2026-09-16）、LangChain 接入示例（09-17，模型路由 + 工具调用前审查中间件）。但"支持"不代表所有用法都包含：
- LangChain ModelRouterMiddleware 是**根据最新用户消息为整次 Agent 运行选模型**，还不是"每走一步根据最新情况重新换模型"的调度器
- 工具调用前审查：判断"这份文件是否值得读"选错通常只是多读材料；**判断"一次写操作能不能放行"选错影响大得多——必须和身份、权限、沙箱及审批机制一起考虑**

LangChain 评测实验（09-20）：五条天气查询运行记录，不同评审模型各重复评判一百次——Jev 五百次通过与否判断都与人工标注一致、连续评分波动低。**像拿五份试卷反复批改：结果一致说明评分稳定，但不能据此判断换一批题型也都对**（且文章没记录 Jev 具体服务版本，复现需补齐）。

**评审器得看到实际证据**（工具究竟返回什么、测试究竟通过没有）——只把 Agent 自己写的"任务已完成"交给评审器，它每次都稳定打高分也不能证明事情真做成了。

## 试用方法

从"下一步优先查哪里"这种只读选择开始（判断经常发生、历史材料可回放、选错通常有机会补读——第一步不必拿生产付款/删除数据做试验）。

**三版本对照**：现有规则、要求简短结构化输出的生成模型、Jev——三者拿同样材料面对同样候选；**原来的生成模型如果只需返回一个标签，就让它直接返回标签，不要要求它写一大篇解释再用这个结果证明 Jev 更省**。厂商数据可帮选试验方向，但任务组织方式/输出要求/部分由其他模型提供的参考判断都会影响比较结果。

**先看它选错以后发生了什么**：配置问题却先查代码——可能只是多读两个文件随后找到问题；也可能一直没读到关键配置最后生成错误补丁。**两种情况都叫"选错方向"，后果差很远**——不能只看局部准确率，还要看有多少次选了"信息不足"、这些任务后来交给谁，连同补读/升级模型/重试费用一起算。

**两步测试**：① 回放历史记录（易定位问题、不影响真实操作）② 让完整任务继续执行（检查最后有没有解决故障、通过测试）——**局部选择更准不一定抵消新增一次网络调用的成本；局部选择与原来不同也不一定影响最后修复**。

**记录过程不需要保存模型隐藏思考**：当时给了什么材料/哪一版问题和候选项/调用了哪个模型/返回了什么/程序采用了哪个结果/执行了哪个工具/最后测试有没有通过——足以区分是模型选错、程序处理错、还是下游工具失败。发送外部服务前按数据要求裁剪脱敏。

**别只盯模型版本**：给 Choice 增加一个选项、改写一句候选说明、调整"什么情况下可以直接采用"的条件，都可能改变系统行为——这些改动也要测试，不能当作无关紧要的文字修改。

## 关键要点（复习用）

1. 接入便宜的判断模型，**不是把原有检查撤掉的理由**——把 Jev 当值得试验也随时可替换的组件：成功就保留，不如规则或生成模型就换回去。
2. 好副产品：更清晰地审视整个开发流程——**这一步到底在判断什么，谁来做比较合适：Coding Agent？Jev？还是固定程序代码？**

## 思考题（文中问题）

试用 Jev 的切入点、三版本对照法、选错后果分析——以及：你的流程里哪些调用真的需要复杂分析、哪些只是做一次分类选一个方向、哪些原本就应该交给程序？
