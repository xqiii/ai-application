# 12｜分层保留：给 Agent 的记忆建一套货架

> 来源：极客时间《Agent 设计模式之美》黄佳 · 记忆：沉淀之美
> 原文链接：https://time.geekbang.org/column/article/988057 （时长 21:17）
> 课程主页：https://time.geekbang.org/column/intro/101162601?tab=catalog

## 一句话总结

分层保留（记忆×层级★）= 把记忆按**作用域、生命周期、可信度**切成多层，每层有独立的加载策略、写入规则、淘汰规则和 token 预算——本质是 LLM 时代的**工作集（working set）管理器**，决定什么常驻、什么按需换入、什么换出。

## 模式定位

最常见的错：把所有东西都叫"记忆"——安全政策、用户偏好、项目规则、任务进度、工具返回 JSON 全堆进同一个 prompt。后果：临时判断被当长期事实复用、长期规则被工具结果覆盖、用户偏好串到别的用户、项目调试配置被当团队规范。

双轴坐标：**记忆 × 层级**。关键不是"多层"，而是"**各有命运**"——不同类型的记忆有不同存储位置、读取时机、覆盖规则和失效方式。

**先问五个坐标，不要一上来问分几层**：
1. 作用域：组织/项目/用户/任务/会话/当前一轮？
2. 活多久：几分钟/一个 session/一个项目周期/长期？
3. 权威来源：人写的/工具返回的/框架生成的/模型推断的？
4. 有没有证据：测试结果/代码路径/用户确认/只是模型猜测？
5. 占多少预算：常驻 context 还是按需工具取回？

> 冷热分层只回答访问频率，回答不了"合规规则能不能被覆盖、用户偏好能不能串租户"。长程 Agent 出问题常因不同可信度的信息被放在同一层。

## 五层货架

| 层 | 放什么 | 类比定性 |
| --- | --- | --- |
| 策略/管理层 Policy | 组织规则、合规红线、安全边界（生产库不能直写、权限变更必须人审） | **边界**——不能被用户一句话覆盖 |
| 项目/领域层 Project | CLAUDE.md、AGENTS.md、架构约定、测试命令、课程大纲 | **项目资产**——要能进仓库、review、diff、回滚 |
| 用户/租户层 User | 用户偏好、租户配置、长期画像、mastery score | **数据库资产**，不是聊天日记——最怕自由文本堆积 |
| 任务/会话层 Task/Session | 当前目标、里程碑、checkpoint、进度、已排除方案 | **状态**——可恢复；短期状态不污染长期画像 |
| 草稿纸/轮次层 Scratchpad/Turn | 当前轮工具结果、中间判断、候选方案、临时变量 | **工作台**，不是档案馆——用完即走或升层 |

层数与产品作用域一致即可：个人助手 3 层、开发者 Agent 至少 4 层、企业系统更细边界。

## 覆盖关系比层数更重要

- 策略层不能被覆盖，只能被执行
- 项目层可覆盖通用默认值，不能覆盖策略层
- 用户层影响表达和偏好，不能覆盖项目硬规则
- 任务层决定当前优先级，不能改写长期事实
- 草稿纸只能提出候选判断，不能直接污染长期记忆

反例：销售 Agent 把用户一次"想看便宜的"写成长期偏好，三个月只推低价版；代码 Agent 把临时 mock server 地址写进项目规则，生产发布还在读 mock；客服 Agent 把某租户折扣记成全局价格规则。

**升层机制**：内层可临时影响外层的使用，但不能自动改写外层的事实。用户说"我会装饰器了"→ 可以临时调高讲解难度；但把 mastery score 从 0.3 改 0.6 需要更多证据（完成练习、连续答对、通过测试）。candidate_update 带 layer_from/layer_to/evidence/confidence/requires_review。

## 写入路由：先放工作台，再决定升层

scratchpad → Memory Router 决定升层：工具结果通过验证 → 任务层；被排除方案有测试证据 → 进度追踪/失败日志；用户偏好多次确认 → 用户层；项目约定有人类 review → 项目层；风险教训完成复盘 → 失败日志。

避开两个极端：**全都不记**（每轮从头来）和**全都记**（草稿纸的猜测全进长期记忆，仓库没清理）。中间路线 = 先用好工作台，再用框架约束什么能沉淀、到哪层、带什么证据、何时过期。

## 最小代码骨架要点

```python
MemoryLayer: POLICY / PROJECT / USER / TASK / SCRATCHPAD
MemorySource: HUMAN / TOOL / AGENT_INFERENCE / VERIFIED_TRACE / FAILURE_REVIEW

LayerPolicy: token_budget + ttl + allow_agent_write + require_evidence + backend
# POLICY: budget 1200, 禁止 Agent 写, backend=managed_file
# PROJECT: budget 3000, 禁止 Agent 写, backend=git_file
# USER: budget 1500, 可写但需证据, backend=postgres
# TASK: budget 5000, ttl 7 天, backend=checkpointer
# SCRATCHPAD: budget 2500, ttl 2 小时, 不需证据, backend=runtime_state
```

四个设计点：① SCRATCHPAD 是正式层（有 TTL、预算、升层规则，不是随便写几句）；② POLICY/PROJECT 默认禁止 Agent 直接写（要人类 review 或仓库证据）；③ require_evidence 把"能不能长期保留"跟证据绑定；④ assemble_context() 按层组装而非按时间排序——各层不互相挤。

## 用户场景：编程教练 Agent 的四层落地

三个版本演进：无状态（第三次来还问"学过 list 吗"）→ 全量历史塞 prompt（围着 list/dict/loop 打转，忘了学生已学到装饰器——不是没记住，是记得太多分不清轻重）→ 分层。

- **用户层**：student_profile（经验/目标/偏好）+ mastery（topic_id/score/last_practiced/common_mistakes）
- **项目层**：课程结构（第 7 章/共 12 章）、course_policy（先给最小例子再讲术语）——由人维护，Agent 不能因一次对话改写
- **会话层**：本节目标、已讲主题、当前卡点、**emotion_state**、next_step
- **草稿纸层**：本轮代码片段、工具结果、临时假设、讲解计划

关键细节：今天卡住 → 先放会话层（≠长期学得慢）；连续三次同错 → 带证据升用户层 common_mistake；本轮代码片段只放草稿纸；课程大纲放项目层。

## 工程落地三件事

| 事 | 做法 |
| --- | --- |
| **存哪里** | 策略层→配置中心/只读文件；项目层→文件系统+Git（要 review/diff/blame）；用户层→profile store/关系库（要 schema/版本/迁移）；任务层→checkpoint store；草稿纸→runtime state |
| **何时读** | 策略层启动加载但要短；项目层加载核心约定、长文档挂 handle；用户层加载摘要按字段查详情；任务层恢复最近状态；草稿纸只在当前调用前拼、用完丢——**分层存储如果最后全量读取，只是把仓库分了区，出门还是背着整个仓库** |
| **何时写** | 普通：定时写回 + session 结束兜底；高风险（金融/医疗/权限）：关键状态实时写回 + 一般批量——长程 Agent 跑半小时崩一次丢一段状态，很快失去信任 |

**长期层 schema 纪律**：不写 `{"learning_pace": "slow"}`，要写完整 metadata（value/source/confidence/evidence/set_at/scope/schema_version）——写时麻烦一点，debug 时救命。

## 工作集（working set）类比

不完全是数据库 schema 设计——LLM Agent 独有问题：**每次推理需要哪些记忆是不确定的**（这轮要用户偏好、下轮要测试命令、再下轮要上周失败经验）。

OS 工作集：进程活跃页留 RAM，不活跃换出，估不准就频繁 swap 性能崩掉。Agent 版本：上下文窗口=RAM，文件/DB/向量库=磁盘，本次推理需要的记忆集合=working set。策略层常驻（定义边界）、项目层半常驻、用户层摘要常驻、任务层动态进入、草稿纸只在当前轮进入、大体量语义记忆交给 RAG 按需取回。**好的分层不看存了多少，看该进的进了、该挡的挡了。**

## 四个常见故障

1. **所有历史对话塞 prompt**：后半段迷失不是没上下文，是旧信息太多、权重没分层。
2. **自由文本长期记忆**：偏好写成散文，半年后同一件事十种说法，检索不稳定更新不可靠——长期层至少高频字段 schema 化。
3. **scratchpad 直通长期记忆**：草稿纸是半成品（猜测/临时解释/未验证观察），要验证、蒸馏、加证据后再升层。
4. **没有降权机制**：记忆永远有效最危险——用户偏好会变、业务规则会变，没有版本/来源/证据/失效条件，旧记忆就是新判断的毒药。

## 关键要点（复习用）

1. 第一原则：按作用域、生命周期、可信度分层。
2. 第二原则：每层有独立的工程命运（backend/TTL/预算/schema/加载/写入/覆盖/淘汰）。
3. 第三原则：长期层要结构化（像资产），临时层要可丢弃（像状态/草稿）。
4. 分层的目标不是把记忆放整齐，而是让 Agent 分得清**什么该信、什么该用、什么该忘**。

## 思考题（课程留题）

1. 分析你熟悉的 Harness 如何做分层保留。
2. 画出当前 Agent 的记忆货架：各层在哪？有没有几类信息被塞在同一个 history 字段里？
3. 找一条最近写入的长期记忆：有来源、证据、版本、失效条件吗？下次被错误召回时怎么判断它不该用了？
4. 检查草稿纸：是工作台还是长期记忆的垃圾入口？设计一条最小升层规则。
