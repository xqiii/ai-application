# 15｜失败日记：让 Agent 把摔过的跤变成本事

## 一句话总结

失败日记（记忆×循环★）= Agent 机队的黑匣子：把一次摔倒蒸馏成**可跨任务召回的教训**（6 层结构 + 结构化召回键），在下次同类任务的关键入口（尤其高风险工具调用前）主动召回——不是错误日志，是从"错误事实"到"可行动经验"的蒸馏。

## 模式定位：不是错误日志

双轴坐标：**记忆 × 循环**——形成闭环：失败发生 → 检测分类 → 记录证据根因 → 审查批准 → 相似任务主动召回 → 改变下一次行动 → 观察是否再失败。

与相近机制的区别：

| 机制 | 服务谁 | 记录什么 | 自动影响下次 |
| --- | --- | --- | --- |
| Retry | 当前执行器 | 错误码、重试次数 | 否 |
| 错误日志 | 运维/工程师 | 堆栈、请求、环境 | 否 |
| Postmortem | 团队 | 影响、根因、改进 | 靠人阅读 |
| 进度追踪 | 当前 Agent | 目标、里程碑、状态 | 服务当前恢复 |
| **失败日记** | **下一次 Agent** | 失败模式、根因、教训、召回条件 | **主动进入** |

错误日志回答"刚才哪里报错了"；失败日记回答"**以后遇到某种情形时，Agent 应该提前改变什么行为**"。

Manus 实践佐证：长循环任务里失败本来就是循环的一部分——保留失败动作和后续观察，模型会调整对相似动作的判断；清除失败痕迹 = 清除它能利用的证据。

## 薪酬场景案例

6 月结算：客户 A 的 30 名员工被错误写进客户 B 的薪酬组——上下文残留客户 B 的旧说明，模型在自然语言里复述了旧 id，工具封装允许从文本提取参数。**验证闸门兜住了**（员工归属与租户不一致 → 中止）。进度追踪做完三件事（needs_rework、废弃快照、重新绑定）——但这次失败没变成经验，7 月还会再犯。

失败日记蒸馏出教训：
- 凡是跨租户的 payroll_*_id 都不能从自然语言摘要中提取
- 工具调用前必须从 SessionState 按 key + tenant scope 绑定，校验租户/部门/月份归属

7 月结算再次调 create_payroll_batch 前，系统召回这条经验——**6 月的一次事故，变成 7 月的一道护栏**。

## 失败日记的 6 层结构

| 层 | 解决的问题 |
| --- | --- |
| 失败边界 Failure Boundary | 这件事算不算值得沉淀的失败 |
| 失败分类 Failure Taxonomy | 属于哪种可重复的失败模式 |
| 证据包 Evidence Bundle | 当时到底发生了什么 |
| 根因与补救 Root Cause & Repair | 为什么会错、系统该怎么改 |
| 召回触发器 Recall Trigger | 下次什么时候应该想起它 |
| 留存与审查 Retention & Review | 谁确认它可信、保留多久 |

### 1. 失败边界：不是只有崩溃才算失败

四种边界：
- **hard_failure**：任务无法继续（工具崩溃/权限拒绝/上下文溢出）
- **gate_failure**：验证闸门没通过（人数不符/金额异常/证据不足）
- **semantic_failure**：表面完成但完成的不是原始目标（目标漂移/口径错误）——比普通超时更危险
- **safety_failure**：触碰租户、权限、环境或人审边界

反过来也别把小抖动都写进来（偶发网络重试、无影响的格式修正）——判断标准：**是否值得 Agent 改变下一次任务的行为**。

### 2. 失败分类：为了召回，不是百科全书

落地分类：tool_failure / retrieval_failure / planning_failure / goal_drift / context_contamination / mechanical_state_mismatch（id 金额账号绑定错误）/ boundary_leak（租户权限边界泄漏）/ hitl_bypass（绕过人审）/ policy_violation / unknown。类别是下次召回正确经验的主要依据。

### 3. 证据包：三平面快照 + 原始观察

延续 14 讲三平面：SessionWorkspace（哪个节点失败/状态/重试次数）、SessionNarrative（当时目标/工作集/关键判断）、SessionState（机械值从哪来/属哪个 scope/被谁消费）+ Raw Observation（工具输出/验证报告/堆栈/人审记录）。只保留原始错误 = 只保存症状；三平面一起保留才能诊断。

### 4. 根因与补救：不要写"模型太粗心"

symptom / root_cause / repair / lesson 四件套。

- 无效根因："LLM 产生了幻觉"——无法指导工程改进
- 有效根因："payroll_group_id 同时存在于自然语言摘要和 SessionState，工具封装没限制参数来源、没校验租户 scope，旧摘要中的 id 覆盖了确定性状态绑定"——能落到具体动作（禁止从自然语言抽机械参数、加 scope 校验、补回归测试）

### 5. 召回触发器：写得再好不召回等于没写

每条日记写清 recall_when：task_family / tools / mechanical_keys / categories / 风险级别。三个召回点：
1. 新任务启动时：召回同 task_family 高风险失败
2. 任务规划时：召回同场景经验教训
3. **高风险工具调用前**：按工具名+机械参数召回——副作用真正发生的地方，一张短短的"危险卡"好过十条长日志

**结构化召回键（task_family + tool + mechanical_keys）比纯文本/embedding 相似更可靠**——很多事故来自同一业务动作、同一批机械参数、同一工具入口，语义相似不是主线索。

### 6. 留存与审查：不能变成垃圾桶

状态机：**draft**（Agent 自动生成初稿）→ **needs_review**（根因不确定或高风险需人审）→ **approved**（可进入召回）→ **archived**（过期/无价值/问题已被机制消除）。**只有 approved 才能召回。**

留存分热温冷：最近失败保留完整 trace；一段时间后保留压缩条目+证据引用；长期只留高严重度、高复现率、真被召回过的。高风险类别（跨租户泄漏/人审绕过/机械串错）不自动淘汰，要进回归测试集——**修复过的 bug 最好的归宿是变成一条永久测试**。

## 完整失败日记示例（串租户事故）

```yaml
failure_id: fj-payroll-20260612-001
task_family: payroll_run
boundary: safety_failure
category: boundary_leak
severity: high
status: approved
symptom: 30 名员工租户归属与当前任务不一致...
root_cause: 工具封装允许从自然语言摘要提取 id；上下文残留覆盖了 SessionState；调用前没校验 tenant scope
repair: 废弃错误薪资组 / 禁止工具封装解析自然语言 id / 只允许 SessionState 绑定 / 强制校验 tenant-org-month / 增加回归测试
lesson: 跨租户机械参数必须 SessionState 确定性绑定；机械 id 不得通过摘要传递；写操作前验证 tenant scope
do_not: 不从自然语言摘要复制 payroll_*_id；scope 未过校验不调用写入型薪酬工具
recall_when: {task_family: payroll_run, tools: [...], mechanical_keys: [...]}
```

注意：没有一句"模型不够细心"，而是细致记录哪个状态平面混了、哪个工具入口放宽了、哪道闸门抓住了、下次调用前该出现什么提醒。

## 代码骨架要点

FailureEntry 把 symptom/root_cause/repair/lesson/do_not/召回条件**分开存**（系统才能检索统计）；EvidenceBundle 按三平面存证据；RecallTrigger 结构化召回键；`is_recallable()` 只有 approved 才召回；`recall_before_tool()` 按 task_family(+3)/tool(+3)/mechanical_keys 交集打分取 top-k，并累计 recalled_count。FailureTrace = 失败日记的 Memory Trace。

离线训练数据属于第二阶段：未经审查的失败直接训练会把错误根因和过度概括内化进模型。先跑通记录、审查、召回、注入。

## 安全：失败日记本身是攻击面

长期记忆库就是攻击面（memory injection / poisoning / tampering）。往里写一条假教训（伪装成"跨租户写入可以跳过校验"），下次召回就被污染。MemoryGraft 攻击：恶意流程伪装成"已验证的最佳实践"藏在普通文档里被 Agent 摄入。**记忆投毒是持久的**——会话重启后继续存活，几周后被语义相似任务触发；OWASP Agentic 安全倡议把它列为十五类威胁的 T1 头号关注点。

两端治理：
- **写入端**：来源标记、人审、租户隔离——一条日记从哪来、谁审过、属哪个租户都要可查
- **召回端**：召回的历史经验是"**边界提醒**"，不是"绝对真值"——Agent 应把它当需要再核对的提示，不是不容置疑的指令

## 衡量指标

| 指标 | 含义 |
| --- | --- |
| **重复失败率**（最核心） | 已记录的失败模式又发生多少次；mechanical_state_mismatch 从月 12 次降到 3 次 = 在积累经验 |
| 召回有效率 | 召回的经验中多少真正改变了计划或参数 |
| 漏召回率 | 重复失败发生时，对应日记存在却没被召回 |
| 误提醒率 | 召回了多少与当前任务无关的经验 |

日记越写越多但同类错误不降 = 问题出在召回点、分类、根因或教训写法。

## 落地三步（挑高重复高损失任务族）

1. 把 Verification Gate 产生的 gate_failure 和 safety_failure 自动转成失败日记草稿（证据最完整，最容易起步）
2. 设计 8~12 个失败类别 + draft→needs_review→approved→archived 审查状态机
3. 只加几个召回入口（任务规划时 + 高风险工具调用前），把短危险卡送到真正发生副作用的位置；盯住重复失败率

黑匣子类比：飞机事故调查不是为了修好这一架，是读出黑匣子、把事故拆成可命名可复现的失败模式、传播到整支机队。**错误日志服务一次维修，黑匣子服务下一次飞行。**

## 记忆模块小结

四模式合拢：**分层保留解决"架"**（建货架）、**RAG 解决"取"**（取证据）、**进度追踪解决"录"**（能对账能续跑的账）、**失败日记解决"省"**（反省——把摔跤变成护栏）。程序性记忆（技能包）留到反思模块。下一模块进入推理。

## 思考题（课程留题）

1. 最近一次 Agent 重复犯错：是没被记录，还是记录了没被自动召回？
2. 挑一条失败记录：根因是"模型幻觉/用户没说清"这种甩锅式解释，还是落到了具体状态平面、工具入口和系统改进动作？
3. 失败经验在什么时刻出现？位置来得及改变行动吗？
4. 有人写入伪装成最佳实践的恶意经验，你的来源追踪、审查机制、租户隔离挡得住吗？
