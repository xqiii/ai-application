# 25｜护栏三明治：高风险行动的前中后防线

> 来源：极客时间《Agent 设计模式之美》黄佳 · 行动：合一之美
> 原文链接：https://time.geekbang.org/column/article/1002659 （时长 23:05）
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

护栏三明治（Action×Hierarchy★）= 把高风险工具调用实现为 **PRE → TOOL → POST** 三阶段协议：前置守卫在副作用发生前拦截输入并规范化参数，受控执行记录原始输出，后置守卫决定哪些内容可发布——**前置拒绝阻止工具运行，后置拒绝阻止结果发布，已发生的影响进入补偿管理**。

## V5 实验：危险发生在两个时刻

两个切片：① 输入检查——`transfer_funds(emp="E0007", amount=999999)` 工具名合法、类型可接受，金额超自动执行上限 200000——要在工具运行前发现，钱转出去就晚了；② 输出检查——`{"msg": "已为 E0007 处理，账户 6222-0007-0049"}` 工具返回后才能看到完整回复——检查结果能否发布。

对照：直接执行（异常转账 1 次、可发布输出含账号）vs 护栏三明治（**异常转账 0 次** / PRE=blocked_pre / POST=blocked_post / **可发布输出不含账号**）。

- blocked_pre = 工具根本没运行（动作账转账次数 0）
- blocked_post = 工具已返回、原始结果存在，只是没获准进入下游发布通道

同一项规则放在副作用前还是后，作用完全不同。

## PRE：还有机会让副作用不发生

常见前置检查：输入结构字段类型 / 身份租户对象权限 / 金额频率风险预算 / 黑名单账户状态地区限制 / 业务对象版本新鲜度 / 幂等键存在 / **审批票据与当前参数一致**。

**请求参数 vs 有效参数分开保存**：前置钩子可做规范化（字符串金额转整数、手机号统一格式），但调用者传入的参数可能已不是工具收到的参数——SandwichTrace 同时存 args（最初请求）和 effective_args（真正送入工具的参数），且要**深拷贝**（浅拷贝时钩子改 payment.currency 内层字段会连原始请求一起改掉）。否则事故后轨迹展示一份参数、工具执行的是另一份，证据链不清晰。

## TOOL：异常不等于没有发生

调用报错 ≠ 外部操作失败：银行已入账但返回超时；邮件服务器已接收但确认前连接断——重试就发两封。生产至少五个状态：**NOT_STARTED / STARTED / SUCCEEDED（外部确认成功）/ FAILED（外部确认失败）/ UNKNOWN（结果不确定）**。

UNKNOWN 最麻烦：不能马上重试，拿同一幂等键去外部系统查询——确认成功补记成功，确认失败才考虑重执行，查不清转人工。**异常只说明"我没收到明确结果"，不说明"这件事没发生"**——付款/下单/发邮件/发券都必须处理。

## POST：管住发布，不假装撤销

后置检查输出结构/敏感信息/业务后置条件/外部回执。开始检查时工具已执行完——后置守卫只能阻止结果继续使用或发布，不能让已发生的事自动消失。

状态必须分清：**blocked_pre**（工具没运行）/ **blocked_post**（原始结果不发布，外部影响可能已发生）/ **compensated**（外部确认补偿成功）。`rollback_marked=True` 只表示发现问题需要补偿，**不代表补偿已完成**——钱不会因布尔值退回来，还要真正调用补偿工具并等外部确认。

## 钩子顺序与失败语义

钩子顺序本身是策略：**成本低、结果确定、最容易提前发现问题的先执行**——输入结构 → 本地权限 → 参数阈值 → 对象版本 → 外部名单 → 人工审批 → 工具函数。参数格式已经错了就立刻拒绝，没必要调外部合规服务、更没必要让人审批。

审批通过 ≠ 现在仍可执行：等待审批的半小时里余额可能变化、对象可能被改——**审批结束后要重新检查依赖实时状态的前置守卫**。

**fail closed（失败即拒绝）**：正式启用的钩子自己崩溃 → 默认 BLOCK——守卫无法完成判断时，系统不能擅自当成"检查通过"。高风险操作宁可暂时拦住，不能安全状态不明时继续运行。

**影子模式（blocks=False）**：新策略上线先不拦截真实业务——完整运行但只记录"如果生效会拦住哪些请求"，BLOCK 降级为带标记 WARN；影子钩子崩溃也只记 `[shadow] hook crashed` 不阻断。影子期间统计命中率/误杀率/钩子耗时/业务分布，明确 owner 与 policy version，达标后逐步切强制模式。

## 整体结构（八个角色）

风险分级器（按工具/对象/参数定防护等级）、策略注册表（钩子/版本/负责人/适用范围）、PRE Chain、**受控执行器（原始工具的唯一调用入口）**、POST Chain、守卫轨迹（请求参数+有效参数+策略判定+原始结果引用）、效果账本（外部回执+真实提交状态）、补偿管理器（冲正/重试/人工接管）。

**引用监视器（Reference Monitor）三条件**：每次敏感访问都经过检查；调用者不能篡改或绕开检查点；检查机制足够小可分析验证。教学代码公开了工具注册表（可绕过守卫直接调用）——生产要**隐藏原始 Handler 只暴露受控代理**，数据库/网络/云服务权限只给代理身份不给 Agent 进程。

> **真正能形成安全边界的不是提示词，而是运行时控制**——受控代理、沙箱、网络策略、服务端授权。提示词写"请勿绕过"只能提醒模型，不能阻止模型越界。MCP Tool Annotations（readOnlyHint/destructiveHint/idempotentHint）只是 Server 自我说明，客户端不能当授权依据。

**OpenAI Agents SDK 工具守卫**：输入守卫（执行前，可拒绝调用）、输出守卫（执行后，可拦截/替换/抛异常）；人工审批通过后默认**重新执行一次输入守卫**（审批期间状态可能变了）。但框架有守卫 ≠ 所有路径受保护——托管工具/内置执行工具/handoff/agent.as_tool() 不天然走同一套守卫。**生产不能只问"有没有加守卫"，要问"Agent 一共有多少条路径能影响外部系统、是否全部经过等价检查"。**

## 组合绕行与契约漂移

**组合绕行**：read_profile → compose_email → send_email 三步各自合法，组合起来把员工资料发给外部邮箱——每步通过检查，组合产生不允许的结果。不能只看单次调用是否合规，要看**信息在整条行动链中怎样流动**（source→sink）：通过行动轨迹和工件来源证据连接传播路径，最终发送前阻止/冻结/升级审批。

**契约漂移**：守卫按 v1 检查 amount/recipient，工具升级到 v2 新增 transfer_type——守卫要么漏检新字段放过高风险，要么把合法新请求全拦住。解法：工具/SDK/文档/守卫从**同一份版本化契约生成**，策略声明 compatible_schema；未知版本不猜字段含义，拒绝或转人工。

**补偿幻觉**：rollback_marked ≠ rollback_started ≠ rollback_succeeded ≠ external_recovery_confirmed。即使退款接口返回成功，最好仍查银行/支付平台最终状态。最危险：补偿失败后删除补偿记录——业务 PAID、系统忘了欠用户一次退款。补偿持久状态机 + 重试预算 + 死信队列 + 人工核实，直到外部确认恢复才结清。

## 防护税与行动模块收束

守卫不是越多越好：每道检查都带来延迟、费用、误杀 = **防护税**。正确做法是检查强度与风险匹配，持续观察钩子耗时/费用/误杀率。

**全模块矩阵（五类故障 × 六配置）**：

| 配置 | 新增控制 | 仍然暴露 |
| --- | --- | --- |
| L0 裸循环 | 无 | 全部五类 |
| L1 最简工具集 | 缩小能力面 | V2~V5 |
| L2 工具调度 | 执行准入 | V3~V5 |
| L3 规划执行 | 冻结完成事实、限制局部重排 | V4~V5 |
| L4 提示链 | 段间事实闸门 | V5 |
| L5 护栏三明治 | 前置后置守卫 | 无 |

**五讲 = 五道控制边界，彼此不能替代**：最简工具集（Agent 可以接触什么）/ 工具调度（这一次允许调用什么）/ 规划执行（整张计划怎样推进恢复）/ 提示链（中间工件怎样交接）/ 护栏三明治（高风险动作执行前后怎样守住）。状态账 + 动作账 + 工件证据 + 外部回执合在一起，系统才有资格说明自己究竟做了什么。

## 思考题（课程留题）

1. 选一个真正不可逆的工具：哪些规则必须前置守卫、哪些结果只有后置守卫能查、最终提交放哪？
2. 前置守卫会不会修改参数？请求值和实际执行值是否分别留在审计记录？
3. POST 命中后原始输出存哪、谁还能读？已发生的外部影响怎样进入补偿状态机？
4. 设计一条三个单点合法动作组成的越界序列：现有系统能否从行动事件识别 source-to-sink 路径？

## 下一模块预告

反思：Agent 完成行动后怎样根据真实轨迹复盘失败、把教训整理成可回放/评测/审批的改进、改进怎样经验证后安全回流运行时。
