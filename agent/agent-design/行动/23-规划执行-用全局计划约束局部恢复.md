# 23｜规划执行：用全局计划约束局部恢复

## 一句话总结

规划执行（Action×Orchestration★）= 把目标契约编译成**可校验的计划图（DAG）**：每个 PlanStep 有稳定身份、依赖、状态；局部失败时规划器只能提交**作用域明确的计划补丁**（不得改写已产生外部效果的 DONE 步骤），解决长程 Agent 两大问题——目标被局部说明接管、恢复范围不断扩大重放已完成副作用。

## V3 实验：第一笔成功，第二笔超时

三步计划 s7（E0007 发薪）→ s12（E0012 发薪，固定网关超时）→ s300（E0300，依赖 s12）。第一次运行：s7 DONE / s12 FAILED / s300 SKIPPED。

外部恢复手册说"网关超时后把所有转账步骤重置为待执行从头开始"——Agent 照做就会重复付款 E0007。

对照结果：未装规划执行 → 暴露（E0007=2、E0012=1、E0300=1）；装上 → 守住（各 1 次）。未装侧把三步全部改回 TODO，执行器重跑 s7。**必须核对动作账**：只看数据库终态，两次写 PAID 都显示 PAID，重复动作被最终态掩盖。

与工具调度的分工：工具调度管住单次调用；本讲问题在更上层——恢复逻辑没有从失败位置继续，而是整批重跑。实验暂时关掉工具调度保护，单独观察规划边界。

## 模式定义与 PlanStep

> 规划执行把目标契约编译成一张可校验的计划图。每个计划步骤具有稳定身份、依赖、状态和输入输出引用；执行器只运行依赖已满足的就绪步骤；局部失败时，规划器只能提交作用域明确的计划补丁，补丁不得改写已经完成且产生外部效果的步骤。交付可检查、可暂停、可恢复的执行状态。

```python
@dataclass
class PlanStep:
    step_id: str          # 稳定身份：恢复时靠它认出"还是原来那一步"
    description: str
    handler: str          # 指向允许执行的处理函数
    deps: list[str]       # 前置依赖：依赖没完成本步不能运行
    status: StepStatus    # 执行事实：TODO/DOING/DONE/FAILED/BLOCKED/SKIPPED
    ...
```

步骤为节点、依赖为箭头 = **有向无环图（DAG）**。执行器每次只回答一个具体问题：哪些 TODO 步骤的所有依赖都已 DONE（**就绪步骤 ready steps**）。

三步清单为什么不够——"1. 给 E0007 发薪…"是给人看的清单，恢复程序缺关键信息：第二步依赖谁、第一步是否真完成、失败后第三步等还是跳、重启从哪续接。规划执行 = 把自然语言提纲变成执行器能计算的工件。

**DONE 是最值得认真对待的状态**：只要一步已产生外部副作用（工资已打、邮件已发、配置已发布），DONE 就对应一项业务事实。

状态机：TODO→DOING→DONE/FAILED；TODO→BLOCKED→人工放行→TODO；依赖失败的后继→SKIPPED。判断依据留在计划里，下一轮不靠对话上下文猜。

## 局部重排：局部在哪里

装上规划执行后，恢复不接受 restart_all，规划器只为失败位置提交**计划补丁（PlanPatch）**：只补 s12（保留 deps=["s7"]——重试 s12 时承认 s7 已完成并沿用该前置事实）。

只靠规划器"自觉"不够——**replan_local 先从失败步骤找受影响范围（{s12, s300}），验证器检查四条边界**：
1. 补丁只能替换受影响范围内的已有步骤（提交 s7 → 拒绝）
2. DONE 步骤不得被覆盖
3. 范围外节点的依赖不得被删除（新 s12 悄悄删掉对 s7 的依赖 → 发现它切断了与既有事实的联系）
4. 新增步骤必须接回失败子图（可从失败子图到达），数量不超 cap

**规划器负责提出新办法，执行边界掌握在确定性代码手里——模型可以建议，运行时负责证明建议没有越界。**

框架不缺灵活性：验证器不写死业务顺序，只检查通用不变量（完成步骤不能改写/补丁不越出受影响子图/外部依赖不丢失/新增范围不超预算）。换成采购审批/数据迁移/代码发布，替换 PlanStep 和 handler 即可复用。

## 一张计划背后的五个角色（+审批闸门）

| 角色 | 职责 |
| --- | --- |
| 目标契约 Goal Contract | 批次目标、范围、预算、业务不变量（每员工最多成功付款一次）、完成证据、恢复原则（冻结已确认副作用） |
| 规划器 Planner | 首次生成计划；失败时生成局部补丁 |
| 计划校验器 Plan Validator | 检查依赖、循环、补丁范围、权限、业务约束 |
| 执行器 Executor | 算就绪步骤、调 handler、推进状态 |
| 检查点存储 Checkpoint Store | 持久化计划版本、步骤状态、输出、外部回执 |

高风险任务加**审批闸门**：人的批准绑定到确定的计划版本——计划 v17 获批、重排成 v18，旧批准应失效或重新确认，不能悄悄沿用。（Anthropic 2026-04 Claude Code Plan Mode：执行前用户审阅修改批准整份计划——计划正在成为用户能拥有和批准的控制工件。）

## 计划时决定对象，执行时读取真值

计划可能比数据更早生成：规划器昨天把账号金额抄进步骤参数，今天工资单可能已修订、审批已撤回——**计划越完整，错误反而越稳定**。

稳妥做法：PlanStep 保存业务对象**引用**（args={"payroll_ref": "payroll:E0012:2026-06"}），执行时才读取当前金额/版本/审批状态。**计划时冻结"给哪张工资单发薪"，执行时重新核验"这张工资单现在能不能发"。**

分工：规划执行决定接下来做哪一步（全局次序），工具调度检查这一步现在能不能做（当前准入）——**计划排到了，不代表可以执行**。

## 检查点和幂等账要一起设计

最棘手窗口：银行已入账、本地没写 DONE、进程崩溃、重启只见 DOING。**不能简单标 FAILED 重付**——先进 UNKNOWN/VERIFYING，用稳定业务幂等键（`payroll:2026-06:E0012:salary`）查询银行结果：成功→补记 DONE；明确失败→才允许重试；给不出确定结果→等待或转人工。

幂等账实现：idempotency_ledger 表（idempotency_key PRIMARY KEY / request_digest / status / provider_ref / result_digest）。执行前写键（唯一约束保证一次）；SUCCEEDED 直接返回上次结果；IN_PROGRESS 等待或退出；调银行带同一键；超时先记 UNKNOWN 查流水确认。**同键不同请求摘要（金额/账号变了）必须拒绝**。

> 检查点记录"流程确认到哪里"（帮任务续跑）；幂等账记录"外部动作发生过几次"（约束副作用）。少任何一本账都谈不上可靠恢复。本地数据库单独无法凭空保证外部付款只发生一次。

## 软件工程血脉与工业实践

WBS（工作分解）→ PERT/DAG 调度（依赖与关键路径）→ 工作流引擎（节点状态+重试）→ WAL（先落恢复事实再推可见状态）→ Saga（跨服务补偿）。Agent 的新变化：规划器可按语义动态生成计划、运行中提出补丁——但依赖闭合、已完成冻结、恢复持久化仍交给确定性工程机制。

工业汇合：Anthropic 长程 Agent Harness（进度文件/功能清单/Git 历史跨会话留工作）；LangGraph 检查点（从最近成功边界恢复，同轮其他成功节点保留不重跑）；Temporal durable execution（进程崩溃/网络故障后按事件历史恢复）。**这些系统都没创造"绝对只执行一次"的魔法——外部副作用仍需稳定幂等键和可查询回执。**

## 何时值得用 + 参考指标

值得用：步骤多有依赖/并行分支/审批节点；跨长时间需暂停恢复人工接管；副作用不能随意重放（支付/Offer/运维变更/数据迁移）；业务要执行前审阅计划。不必用：单次查询、只读调用、短问答——规划本身有成本，环境变化太快时过早冻结细节会让计划迅速过期。

| 指标 | 回答什么 |
| --- | --- |
| 计划校验失败 | 规划器最常违反哪些约束 |
| 就绪队列等待时长 | 哪些步骤长期等不到依赖 |
| 重排范围 | 每次失败改了多大范围 |
| 已完成动作重放率 | DONE 是否再次进入执行队列 |
| 结果未知积压时长 | UNKNOWN 状态积压多久 |
| 检查点恢复成功率 | 重启后能否续接 |
| 审批失效率 | 计划变化后旧审批是否正确失效 |

## 关键要点（复习用）

1. Agent 负责提议怎样恢复（局部计划补丁）；确定性执行器负责裁决（DONE 不能重开，只许改失败步骤及下游）。
2. 目标契约让原始目标离开第一轮 Prompt，成为可持续比较的基线。
3. 仅仅是更长的提示词撑不起长程任务——能持续保存目标、进度和业务事实的执行结构才可以。
4. Agent 可以临场想办法，但不能临场改写已经发生的业务事实。

## 思考题（课程留题）

1. 计划步骤保存的是业务对象引用，还是规划时读到的金额/账号/审批状态？
2. 银行已入账、本地没写 DONE：靠什么幂等键和外部回执决定补记/等待/重试？
3. 计划局部修改后原来的人工审批还有效吗？审批绑定版本号、内容哈希还是两者？
