# 22｜工具调度：从候选选择到执行准入

> 来源：极客时间《Agent 设计模式之美》黄佳 · 行动：合一之美
> 原文链接：https://time.geekbang.org/column/article/999645 （时长 30:49）

## 一句话总结

两个模式两层防线：**最简工具集**（Action×Route）让越界工具在当前任务不可达（工具前沿），**工具调度**（Action×Route★）让合法工具满足状态和次数约束才能执行（执行准入）——精华：先缩小能做什么，再判断这次能不能做，做完还要能证明发生了什么。

## 三个基本原则（三个"不等于"）

1. 企业工具库 ≠ 当前任务应当看见的工具集（工具前沿）
2. 语义上选对了工具 ≠ 这次调用已获得执行准入
3. 一次坏调用被拒绝 ≠ 原始业务目标已完成

分别区分：整体能力库 vs 当前能力面；选择 vs 授权；局部拒绝 vs 全局任务恢复。

L0→L2 消融结果：L0 裸循环（状态差 3 行/出账 2 笔/受损）→ L1 最简工具集（状态差 1 行/出账仍 2 笔）→ L2 工具调度（状态差 1 行/**出账 1 笔/守住**）。**只看数据库终态 L1 和 L2 都是一张 PAID，动作账才揭示前者写了两遍。**

## 第一层：最简工具集——让越界工具不可达

L0 暴露五项能力（query_payroll/transfer_salary/normalize_bank_account/clear_payroll_note/reverse_transfer），发薪目标真正需要的只有前两个。

**工具前沿（Tool Frontier）** = 当前任务、当前身份、当前阶段真正可见的那组工具——本轮工具调用能打开的那扇窗。防线不"劝"模型改变主意，只让越界能力**没有执行入口**。

生成顺序（**先硬权限过滤，再语义召回**——无权使用的工具不应先被向量检索推到模型眼前；语义召回可误差，硬过滤管资格必须准确）：

```
企业工具总目录 → 来源/租户/身份硬过滤 → 阶段与副作用等级过滤
→ 语义召回与重排 → 常驻核心工具 + 少量相关扩展 → 当前工具前沿
```

要点：最简工具集 ≠ 删工具——银行账号维护能力仍在企业库，只是不出现在发薪步骤；低频工具可 Tool Search 按需发现或交子 Agent 持有。"最简"移走无关能力，"完备"保证原目标能完成；具体数量看业务目标/身份/阶段/数据范围/副作用风险。

## 第二层：工具调度——合法工具也要准入

ToolMetadata 执行契约：`requires_fresh_state=True`（写前重读最新状态=fresh read）、`quota_per_session=1`（会话/工具/对象最多一次）、`rollback_action="reverse_transfer"`（补偿走冲正，不能假设原动作没发生）、`risk_level=CRITICAL`。

**行动意图（Action Intent）** = "工具名+参数"的结构化候选——表达想做什么，不等于已授权的命令。调度流程：行动意图 → 工具前沿 → 选择候选 → 检查准入 → Handler → 动作证据。

**dispatch() 四关**：
1. **注册表**：工具不存在/未注册 → rejected("tool_hallucination")——注册表既是目录也是可执行白名单
2. **调用配额**：used >= quota → rejected("quota_exceeded")
3. **状态新鲜度**：超过 freshness 窗口 → rejected("stale_state_must_refresh")
4. **审批要求**：awaiting_approval

**rejected 和 failed 必须分开**：rejected = 没获得准入，副作用尚未开始；failed = Handler 已运行出现异常——网络超时时远端可能已成功，异常不代表没执行。

## 被拒之后：Harness 负责把任务拉回正轨

工具调用分上下半场：**上半场拒绝偏航提案（工具调度管），下半场完成原始目标（Harness 管）**。L2 中两条 transfer_salary 都因 stale_state 被拒，E0007 仍是 DRAFT——北极星目标未完成。

Harness 持有三类信息：北极星目标、当前任务状态、每次尝试的 DispatchTrace（含拒绝原因）。恢复策略写成确定性控制代码：先 query_payroll（写 fresh-state 时间戳）→ 再 transfer_salary（配额 0、状态新鲜 → 放行 → 一笔 30000 元 disciplined=1 的付款）。生产还要：查询失败就停止付款（read_trace 检查）；**被拒绝的调用不消耗配额**（否则攻击者制造失败调用就能占掉合法名额）。

职责边界：**工具调度判断一次调用能否进 Handler；Harness 依据原目标决定重读、等待、改计划或停止**。调度器不应偷偷承担整项任务的目标恢复。

## "选工具"其实是四个动作

| 动作 | 回答 | 诊断 |
| --- | --- | --- |
| 发现 Discovery | 系统里有没有 | 正确工具没搜到 → 改工具目录/Tool Search |
| 建立前沿 Frontier Building | 当前该看见哪些 | 正确工具被误移出 → 改前沿生成 |
| 选择 Selection | 语义上用哪个 | 候选都有但选错 → 改排序 |
| 准入 Admission | 此刻能不能执行 | 选对但不满足条件 → 查状态证据和策略 |

（工具放行后业务结果错误 → Handler 或副作用控制问题。）分阶段指标才能让日志指向真正的修复位置——只看"工具成功率"，四层混成一个数字。

## 判断点与执行点必须分开

- **PDP（Policy Decision Point）**：做 allow/deny/await 判断（生产可放独立策略服务）
- **PEP（Policy Enforcement Point）**：挡在 Handler 门口，保证拒绝不可绕过（必须跟着 Handler）——业务代码不能绕过 Dispatcher 直接拿付款函数

血脉：最简工具集←最小权限；工具调度←完全仲裁 + Command/Strategy。老原则解决新问题；AI 时代的新变量是行动意图由自然语言动态生成。

**ToolMetadata 字段要有人真正消费**：description/when_to_use/when_not_to_use 帮助发现选择；exclusive_with 声明互斥；is_read_only/is_destructive/is_concurrency_safe 描述执行特征；requires_fresh_state/requires_approval/quota 参与准入；rollback_action 描述补偿。**字段写了不等于运行时已执行**——当前参考实现没消费 risk_level/is_mcp/exclusive_with/is_concurrency_safe，看到 CRITICAL 不能推断系统已兑现保证。

**注册时先拒绝自相矛盾的契约**：破坏性工具必须声明 rollback_action；不能既只读又破坏性。但检查只证明字段填了值——生产还要校验补偿入口可解析、参数兼容、语义真能恢复；**随手填一个假的补偿入口比坦白没有补偿更危险**。MCP Tool Annotations（readOnlyHint 等 2026-03）只是风险词汇供参考——第三方 Server 可以自称只读，客户端不能据此自动授权。

## 四种生产压力（S1-S4）

**S1 并发配额竞态**：两个 worker 同时 fresh read、同时通过配额检查（quota=0）、都付款、计数写 1——真实付款 2 次账面 1 次。会话配额只解决"别调太频繁"；支付要**业务幂等**：`goal_id + employee_id + payroll_month` 组成稳定幂等键，共享数据库唯一约束**原子占位**；第二个请求发现已存在 → 查询原动作结果，不再付款。

**S2 TOCTOU（检查时与使用时不一致）**：10:00 读 9600 元，10:01 别人改成 99600，60 秒窗口内照常付款。时间不能证明数据没变——**StateEvidence 绑定对象和版本**（resource_ref/version/observed_at/content_hash），写入时比较版本：版本一致才更新（**Compare-and-Swap**），版本变了重新读取并使旧版本绑定的审批失效。

**S3 进程重启失忆**：quota/freshness/saga_log 存内存字典，重启后新进程不知道付没付款 → 重复支付。生产要**行动账本（Action Ledger）**持久化：幂等键/准入决定/数据版本/执行结果/外部回执/补偿状态。重启第一件事查账。外部结果 UNKNOWN（timeout 但银行可能已收到）→ 按幂等键查询结果确定性，**不能直接重试**。

**S4 补偿债务丢失**：付款成功 → 记录补偿 → 冲正失败 → 删除记录——工资 PAID、系统忘了还欠一笔债。生产补偿状态机：PENDING_COMPENSATION → COMPENSATING → COMPENSATED / **COMPENSATION_FAILED → MANUAL_REVIEW/REDO**；失败记录保留重试次数、最后错误、下次重试时间、负责人，直到补偿完成或人工结案。

**DurableToolDispatcher**：dispatch(intent, contract, state_evidence, approval) → selector.select → policy.decide → ledger.append → 幂等层 acquire lease（执行租约，只有占位成功的一方调真实工具）→ executor.run → commit_result。逐级加厚原则：两三个只读工具时注册表+参数校验就够；支付/删除/发消息/运维变更进入后控制才加厚——**风险越高、副作用越难恢复，越值得把决策点、执行点和证据账分开**。

## 监控指标表

| 指标 | 定位什么 |
| --- | --- |
| 工具发现召回率 | 正确工具有没有被搜到 |
| 工具前沿召回率与大小 | 必要工具被误删？候选过多？ |
| 候选选择准确率 | 正确工具排第几 |
| 准入拒绝原因 | 因状态/次数/审批/权限被拒 |
| 重复副作用数 | 同一幂等键实际提交几次 |
| 状态版本冲突 | fresh read 后对象又变了几次 |
| 补偿债务年龄 | 未完成补偿积压多久 |

行业动态：Anthropic Tool Search Tool（2025-11，defer_loading 延迟加载——"系统拥有多少"和"本轮看见多少"拆开，对应最简工具集的渐进发现）；OpenAI Agents SDK Tool Guardrails（执行前后检查阻断，但托管工具/内置执行/handoff 不自动走同一管线——用框架要逐类核对哪些入口真的受控）。**工具调用正走向三层配合：按需发现、风险描述、运行时执行边界——任何一层都不能单独承担全部安全保证。**

## 思考题（课程留题）

1. 找一条真实工具误调用记录：属于发现/前沿/选择/准入/Handler 哪层问题？当前日志能区分吗？
2. 给有副作用的工具写三项准入条件：哪些只靠时间戳不够，必须绑定对象版本或审批票据？
3. 给薪酬付款设计业务幂等键：远端付款成功、本地回执未写时崩溃，新进程该查什么、绝不能直接做什么？
4. 让补偿连续失败三次：补偿债务存哪里、何时重试、何时转人工、谁负责？
