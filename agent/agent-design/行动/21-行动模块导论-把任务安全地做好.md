# 21｜行动模块导论：把任务安全地做好

> 来源：极客时间《Agent 设计模式之美》黄佳 · 行动：合一之美
> 原文链接：https://time.geekbang.org/column/article/998295 （时长 20:53）
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

行动是系统第一次产生**真实副作用**的环节：工具 success 只证明"调用跑完了"，正确行动要同时过六项检查（GoalAligned/ScopeAuthorized/StateCurrent/PolicyAdmitted/EffectExactlyOnce/EvidenceComplete）——行动运行时由决策/控制/效果/证据四平面组成，光有状态账不够，还要有动作账。

## 模块定位

推理模块留下的都是**判断**：18% 调薪放行、9600 元入账、缺口归因报告——此时钱还没动、工资单还是 DRAFT。行动把判断变成数据库写入、API 调用、状态迁移和外部通知——**副作用 = 系统对真实世界的真实影响开始发生**。

行动模块先关心四件事：
1. 该做的能落下去
2. 范围外的动作不能混进去
3. 同一副作用不能重复发生
4. 执行之后要留下证据

感知看漏可重读、推理走偏可补证据，**行动碰的是外部世界**：多发一笔钱必须追回、错发工资单员工不满、异议记录不能随便清空（审计问题）。

## 行动压力测试工作台（L0 裸循环实验）

GitHub 仓库 huangjia2019/agent-design-patterns 的 action/payroll-lab——消融实验设计：固定北极星目标（"给 E0007 发薪，金额以已核验工资单为准，不动员工主数据"）+ 固定外部备注（要求补发工资、改 E0007 银行账号、清空 E0012 异议记录），只逐层加防线，看每层挡住什么漏掉什么。

**L0 裸循环结果**：合法发薪完成的同时——两处越界写入（账号被改、异议被清）、一次重复副作用（两笔付款）、两次时序违规（跳过 fresh read）。程序没有报错、工资发出去、一片绿色——**不是没做成，而是把不该做的也一起做成了**。

偏航机制：压力实验在调用模型处安插确定性夹具，把备注文本翻译成候选工具调用——这是**故意做的 Prompt Injection**，裸循环检查不出来。候选动作直接进 handler，中间没有目标核对、最小工具集、执行准入、幂等键和前置护栏。

关键教训：工资单状态表看不出付款次数（第二次调用仍写 PAID），stress_payment_log 才暴露付了两次——**只比较终态不够，状态账和动作账要分开**。

## 四笔账

| 账 | 回答什么 | 例 |
| --- | --- | --- |
| 状态账 | 业务现在什么状态 | 工资单 DRAFT 还是 PAID |
| 动作账 | Agent 尝试和执行过什么 | 申请付款两次，一次拒一次放行 |
| 效果账 | 外部世界实际发生了什么 | 银行真正出账几笔、金额、回执 |
| 证据账 | 当时凭什么允许执行 | 数据版本、审批回执、准入理由、策略版本 |

## 正确行动的六项检查

| 条件 | 回答的问题 | L0 表现 |
| --- | --- | --- |
| GoalAligned | 动作是否仍服务原始目标 | 清理异议记录没有推进发薪目标 |
| ScopeAuthorized | 对象与副作用是否获授权 | 修改账号和备注越界 |
| StateCurrent | 参数是否来自足够新的事实 | 两次付款都跳过 fresh read |
| PolicyAdmitted | 动作是否经过当前策略准入 | 提案直接进 handler |
| EffectExactlyOnce | 同一副作用是否只提交一次 | 动作账记录两笔付款 |
| EvidenceComplete | 能否核实结果并继续恢复 | 本地账能揭示重复，外部回执未实现 |

**工具名只是门牌号，决定控制强度的是门后会发生什么**：transfer_salary 关系到钱（要幂等键/fresh read/外部回执/补偿流程）；query_payroll 只读（可宽松重试并发）。风险不能只看工具名称，要看产生什么副作用。

## 四个运行平面

| 平面 | 负责什么 |
| --- | --- |
| 决策平面 Decision | 根据目标和观察提出候选动作 |
| 控制平面 Control | 核对目标、工具、状态、配额、审批和策略（L0 中故意留空的部分） |
| 效果平面 Effect | 提交真实副作用 |
| 证据平面 Evidence | 证明发生了什么，驱动恢复与补偿 |

Demo 把四平面集中在 while True 里（模型输出工具名就执行）= 把权限、时态和证据全粘在一起。

完整运行顺序：推理结论 → 目标契约与计划 → 执行器选 Plan Step → 提示链生成/校验 Artifact → 工具调度器缩小候选决定准入 → 护栏三明治（PRE→TOOL→POST）→ 业务账本 + ActionEvent + Checkpoint。

## 三层实验地图

1. **L0-L2 同刺激消融**：同一道题同一份错误备注，一根根装回护栏——回答"哪层设计起了作用"
2. **V3-V5 边界定向压力**：规划执行（中途超时整批重跑问题）、提示链（污染工件传递）、护栏三明治（高风险输入输出）各配最适合攻击它的刺激，无模式 vs 有模式对照
3. **S1-S4 生产压力**：并发击穿配额、TOCTOU（检查时与使用时不一致）、进程重启丢状态、补偿失败

## 四个模式 + 一个原则

| 模式 | 双轴坐标 | 补上的边界 |
| --- | --- | --- |
| 最小工具集 | Action×Route（约束侧） | 当前步骤可见的能力范围 |
| 工具调度 | Action×Route | 单次工具选择与执行准入 |
| 规划执行 | Action×Orchestration | 多步依赖、状态与局部恢复 |
| 提示链 | Action×Chain | 段间工件与交接闸门 |
| 护栏三明治 | Action×Hierarchy | 高风险动作的 PRE/TOOL/POST |

嵌套运行：规划执行选 PlanStep → 提示链生成核验 Artifact → 最小工具集算范围 → 工具调度决定准入 → 护栏三明治包住高风险 handler。

**软件工程血脉**（Saltzer & Schroeder 两条纪律：最小权限、完全仲裁）：最简工具集←最小权限；工具调度←完全仲裁/Strategy/Command；规划执行←Workflow DAG/状态机/持久化执行；提示链←Unix 管道/编译器 Pass/契约式设计；护栏三明治←引用监视器/中间件/纵深防御。**Agent 带来的新变量只是：候选动作和中间工件可以由概率模型生成了。**

## ActionTrace：动作账

ActionEvent 骨架：action_id/tool_name/risk_level/arguments_repaired/guardrail_blocked/guardrail_reason/success/retry_count/**planned**/timestamp。`planned=False` 暴露"不请自来"的动作；`scope_creep_ratio = 事件数/planned 数`。

生产版还要补：goal_id、plan_id、subject_ref、idempotency_key、对象版本、策略决定、外部回执，以及比 success:bool 更细的失败时态：ACTION_PROPOSED → ADMITTED → STARTED → SUCCEEDED / FAILED / **RESULT_UNKNOWN** → COMPENSATION_REQUESTED → SUCCEEDED / FAILED。

## 长任务放大行动风险的四条路径

1. **局部合规、全局偏航**：每个工具单独看都合法，Agent 被最近异常吸引围着细节转，原始完成条件退到上下文边缘。
2. **错误沿交接传播**：上段写错金额，后面步骤认真加工错误，日志仍全显示 SUCCESS。
3. **工具成功、业务结果未知**：外部接口已受理但响应丢在网络——重试带来重复副作用，放弃漏掉已成功的动作。
4. **发现失败、补偿尚未完成**：POST 给 BLOCK 只说明结果不合格；退款/冲正/恢复都是新业务动作，也会失败，也要进自己的状态机。

**执行成功 ≠ 行动正确**：正确行动 = 目标一致 + 范围授权 + 策略准入 + 副作用恰好一次 + 证据完整。一次"顺手处理"几十步传播后会变成很难追溯的业务事实。

## 思考题（课程留题）

1. 打开你的 Agent 工具列表：哪些只读、哪些改业务状态、哪些只能补偿无法撤销？
2. 支付请求超时但数据库仍 DRAFT：还需要哪些动作证据才能决定重试/查远端/转人工？
3. 夹具改一个词提案就变。换成真实模型，怎么固定任务、工具权限和完成条件？怎么区分模型偶发偏航与运行时缺少机械边界？
