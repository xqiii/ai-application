# 24｜提示链：用段间契约阻断错误传播

> 来源：极客时间《Agent 设计模式之美》黄佳 · 行动：合一之美
> 原文链接：https://time.geekbang.org/column/article/1000895 （时长 15:52）
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

提示链（Action×Chain）= 把复杂行动拆成职责清楚的链段，中间结果升级为带**结构、版本、来源**的工件（Artifact），段间闸门（Gate）执行交接契约——**多个提示词按顺序调用只是线性串接；提示链真正的工程接口是工件 + 闸门**。

## V4 实验：一个错误总额的链路

两段流程：① 核对薪酬总额 → ② 根据对账结果生成付款申请。SQLite 可信台账总额 3100000；第一段收到外部对账附件后生成：

```json
{"status": "RECONCILED", "delta": 0, "total": 9999999}
```

格式合格、字段齐全、状态写"已对账"——但总额被换成 9999999。第二段没算错，它忠实地使用了上游数据，生成 `PAYMENT_REQUEST total=9999999`。**问题出在交接处：格式合法、事实错误的中间结果，未经独立核验就进入下游。**

对照：线性串接（只检查输出非空）→ 生成错误付款；提示链（加链外事实闸门）→ 污染工件被拒，付款申请没有生成。两种方式执行步骤没变，区别只在：**第一段的结果交给第二段前，有没有经过真正的验收**。

## 模式定义

> 提示链把复杂任务拆成固定顺序的小步骤。每一步只承担一项清晰职责，产出一份中间工件。工件通过段间闸门以后，才能进入下一步。

三个核心概念：**链段 Step**（完成一项明确任务，可调模型/规则/工具）、**工件 Artifact**（链段正式交付下游的中间结果）、**闸门 Gate**（决定下游能否签收）。

血脉：Unix 管道（小程序各做一件事+标准 IO）→ 编译器 Pass（消费结构化中间表示）→ ETL/CI（数据质量门+阶段验收）→ 契约式设计（前置/后置条件+不变量）。Agent 的新变量：**中间工件由概率模型生成——可能语言流畅格式漂亮，却在关键字段偏离事实，所以要像外部系统交付物一样接受验收**。

Anthropic 建筑实践：提示链 = 顺序模型调用 + 中间程序化闸门；OpenAI 注入防御的 source-to-sink 视角：工件与闸门为传播路径增加可核验、可阻断的接缝。闸门无法保证上游永远不犯错，但**能缩短错误传播的距离——发现越早，恢复范围越小，代价越低**。

双轴：**行动 × 链式**。与规划执行的分工：规划执行管整张任务图（哪个 PlanStep 能运行、失败改哪片子图）；提示链管相邻步骤交接（一个步骤内部有哪些链段、工件能否进下一段）。一个计划步骤完全可以包含一条提示链。

## 工件不是一段临时对话

生产对账工件示例：artifact_type / **schema_version**（上下游兼容性）/ batch_id + **ledger_version**（绑定具体业务快照）/ total_fen / delta_fen / **source_refs**（关键数字能回到可信来源复核）。

工件 vs 草稿纸：草稿纸是暂存区，随上下文结束消失；工件要**跨步骤流动、可能被保存/重放/审计**，必须接受正式契约检查。

链段设计六问：角色 Role / 任务 Task（只做哪一件事）/ 输入 Inputs / 输出契约 Output Contract / 约束 Constraints / 证据 Evidence。说不清交付什么、说不清下一段怎么验收 = 形式上把大提示词拆成三次调用，只增加延迟。**提示词变多只是实现代价，链的价值来自那些能截住错误的接缝。**

## 代码实现要点

ChainStep（step_id/system_prompt/prompt_template/**gate**/gate_description/**max_retries**/retry_prompt_suffix）。默认闸门只检查非空。

执行器 `PromptChain.run()` 的关键一行：`prior[step.step_id] = run.output`——**只有闸门判定成功，工件才获得自己的名字**，进入后续链段可读的上下文；没通过就不悄悄流向下一段。重试预算耗尽 → 记录失败原因结束整条链，第二段不会收到"可能有问题"的半成品。

## 段间闸门四层检查

| 层级 | 问什么 | 机制 |
| --- | --- | --- |
| 语法 | 能不能解析 | JSON/XML parser |
| 结构 | 字段/类型/枚举对不对 | JSON Schema、Pydantic |
| 语义 | 业务不变量成立吗 | 金额非负、借贷平衡、状态迁移 |
| 事实与来源 | 与可信世界一致吗 | 数据库版本、签名、来源链 |

前两层解决"能不能读"，后两层回答"能不能信"。

**污染工件实验**：`{"status": "RECONCILED", "delta": 0, "total": 9999999}` 能通过非空检查和字段检查——要拦住必须查语义和事实。事实闸门三件事：① 输出可解析 JSON；② status/delta 符合业务含义；③ **从 SQLite 可信台账重新读取真实总额核对**。最重要的设计：trusted_total 来自链外——**工件可以自己声称 delta=0，但不能拿自己的说法证明自己正确，事实检查必须找独立可信源**。

另一种攻击：不改总额，只把 E0007 和 E0012 个人金额对调——总额仍对、当前闸门放行、钱发错人。真实薪酬工件要守住一组不变量：batch_id 与当前批次一致 / ledger_version 未过期 / total_fen 与台账一致 / employee_id 批次内唯一 / 逐行金额与工资单一致 / 收款账号属于对应员工 / source_refs 可访问版本匹配。**每条不变量要回答：从哪个可信源核验、失败交给谁。**

**结构化闸门判定 GateDecision**（不只返回 bool）：accepted / rule_id / reason_code（LEDGER_VERSION_STALE→重读数据；EMPLOYEE_ACCOUNT_MISMATCH→人工复核；JSON_PARSE_ERROR→才适合让模型修格式）/ observed / expected / evidence_refs / retryable——**不同失败原因需要不同应对**。

## 重试必须带来新的信息

相同输入、相同模型、相同提示词原样再跑 = 只是重新抽样。有效恢复至少改变一项信息条件：带上闸门的结构化失败原因 / 重新读取可信源 / 缩小本段任务范围 / 切换模型或确定性算法 / 回退到能重建事实的上游步骤 / 转人工或失败队列。

**LLM_ERROR 和 GATE_FAILED 分开记录**：服务商故障 = 调用没正常完成；工件不合格 = 模型已交付但没通过验收——避免用业务重试掩盖基础设施故障。

## 整链成本与两个相反问题

整链一次通过率 P(chain) = p1×p2×…×pn——七步链每步 95%，整链只剩约 70%。**不要为了"看起来工程化"把每句话拆成一次模型调用**。规则计算/字段转换/事实查询优先确定性代码，需要语言理解/归纳/生成的阶段才调模型。

一对相反问题：
- **信息饥饿**：第三段只看到第二段摘要、没拿到第一段关键证据——允许后续模板按 step_id 引用所有已成功工件
- **上下文污染/成本膨胀**：所有历史原文反复塞进每个链段——完整工件存 **Artifact Store**，链路只传引用 + 当前步骤真正需要的字段（artifact_ref/schema_version/source_refs/selected fields）

> 提示链每一步需要的是完成本职工作的**最小证据集**，不是越多上下文越好。

## 何时用 + 指标

适合：任务有清晰阶段且每段可定义可检查输出；核算/生成/校对/合规需要不同模型规则工具；中间结果需留档复核或被其他系统消费；错误越过交接点代价明显放大。不适合：任务很短、输出只供人读、各步骤高度耦合无法定义中间契约——没有验收条件的拆分只增加费用延迟和状态管理。

| 指标 | 回答什么 |
| --- | --- |
| 链段通过率 | 哪个链段最不稳定 |
| 闸门拒绝率与误杀率 | 闸门过松还是误杀太多 |
| 重试放大率 | 一次任务放大成多少次调用 |
| 工件结构漂移 | 上下游版本还兼容吗 |
| 来源链完整度 | 关键字段能追到独立来源吗 |
| 整链一次通过率 | 整条链一次通过率多少 |
| 错误逃逸率 | 哪类坏工件越过了闸门 |

闸门拒绝率高不一定是好消息——可能守得准，也可能上游模型长期失控；要和失败原因、人工复核结果一起看。

## 思考题（课程留题）

1. 系统里选一份关键中间工件：下一段接收前最该检查哪三个字段？
2. 为其中一个关键字段找链外证据：为什么不能让工件自己证明自己正确？
3. 闸门拒绝后，下一次尝试要增加什么新信息，才不只是原样重试？
