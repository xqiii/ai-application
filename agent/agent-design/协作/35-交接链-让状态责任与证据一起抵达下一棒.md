# 35｜交接链：让状态、责任与证据一起抵达下一棒

> 来源：极客时间《Agent 设计模式之美》黄佳 · 协作：合鸣之美
> 原文链接：https://time.geekbang.org/column/article/1015307 （时长 15:35）
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

交接链（协作×链式）= 按业务顺序连接多个责任主体，每次换手提交一份**结构化、带版本的交接包**，接收方**验收成功后才获得下一步控制权**——维护一条版本链，任何一棒用了旧状态，接缝就拒绝本次交付，版本停在最后一个已验收位置。

## 开场案例：旧结论在下一棒复活

事实核查员把研究员的"dsh 子 Agent 默认完全隔离"改成"进程内 spawn Worker 使用独立会话，文件系统隔离取决于运行策略"。修订正确。但编辑环节系统里同时放着原始主张和核查结论——编辑顺手参考旧句子生成标题，发布者看见 source_checked=true、正文非空，就把旧结论发了出去。**上游已经纠错，下游又把错误捡回来**——每位 Agent 单独看都完成了工作，问题出在工作交接的缝隙。

## Demo：text relay vs contract handoff

- **text relay**：source_checked=true published=true，但发布的 draft 仍是核查前的旧句子（problem=stale_claim_survived）
- **contract handoff**：
```
research   v0→v1 accepted=true
fact_check v1→v2 accepted=true
edit       v2→v2 accepted=false reason=stale_claim_binding   # 接缝拒绝，状态不前进
edit       v2→v3 accepted=true                                # 重新读取 v2 用已验证结论写稿
publish    v3→v4 accepted=true
```

编辑第一次用旧主张，接缝检查发现编辑稿摘要与 v2 核查结论摘要对不上 → 拒绝交接，错误稿没混进接力棒。**v2→v2 表示"Agent 尝试过"但"系统没有接收"**。四棒程序实际增加三件事：每棒声明接什么交什么、交接内容带版本、接缝检查前后版本关系。

## 模式定位与血脉

> 交接链按业务顺序连接多个责任主体，每次换手都提交一份结构化、带版本的交接包，接收方验收成功以后才获得下一步控制权。

**发送成功 ≠ 接收成功**：接收成功还要确认对象正确、版本正确、内容满足这一棒前置条件。审批系统发来通过票，付款 Agent 还要等接缝检查完成，责任才从上一棒转到下一棒。

血脉：Unix 管道（稳定边界让实现自由替换——但管道不理解业务语义，交接链要加版本/所有权/验收）→ 契约式设计（提供者保证后置条件、调用者满足前置条件，不靠"大家应该知道"——requires 与 provides 是这条思想在 Agent 上的表达）→ Saga 1987（长事务拆子事务+失败补偿——交接链不等同 Saga 却遇到相同现实：前几棒可能已产生外部影响，后面失败无法把世界回滚到原点，补偿/升级/人工责任必须提前设计）。

**与提示链（24 讲）的区别在控制权**：提示链发生在同一 Agent 或同一条工作流内部（步骤二消费步骤一工件，运行责任同一个 Harness 持有）；交接链把责任交给另一位专业 Agent/另一个会话/另一个系统——下一棒可能有不同工具/权限/服务级别，交接时要写明谁接手、接了哪版、验收依据、失败后谁继续。可组合：一棒内部用提示链（核查 Agent 检索→抽证据→形成结论），把正式结果交给编辑 Agent 时用交接链。

## 实现四件套

1. **StageSpec**（这一棒接收什么交出什么）：编辑棒声明 consumes (verified_claim, verified_claim_digest)、produces (draft, draft_claim_digest)、绑定规则（draft_claim_digest == verified_claim_digest，违反即 stale_claim_binding）。运行时按声明验收——少字段/多字段/改写别人拥有的字段都拒绝。角色提示词告诉模型"你是编辑"，StageSpec 告诉程序编辑这次消费哪几项事实、交付哪几项工件。
2. **FactRecord**（这个值是谁根据什么产生的）：key/value + **producer_stage**（责任人）+ **evidence_ref**（来源）。下游有疑问可把问题送回对应阶段。薪酬场景：员工身份来自 HR 主档、审批状态来自审批系统、到账状态来自银行回执——三个值都能写成自然语言的"已确认"，生产者和证明方式完全不同。
3. **BindingRule**（新工件必须使用已验收事实）：核心检查一行 `draft_claim_digest == verified_claim_digest`——不把结论写死在框架里，换业务只换绑定两端：付款文件摘要 = 审批回执中的工资单摘要；部署制品摘要 = 安全扫描通过的构建摘要；合同签署页属于法务评审过的正文版本。**交接链检查"下一棒消费了哪一版上游事实"，具体事实由业务契约定义。**
4. **Baton 与 StageReceipt**（成功才前进）：Baton 是不可变版本化接力棒，阶段不能直接改它只能提交增量；接缝通过后编排器才创建下一版。StageReceipt 记录阶段/输入版本/输出版本/是否接收/原因——区分"Agent 尝试过"和"系统已经接收"。**共享可变字典做不到**：一个 Agent 写进两个字段后异常退出，下一棒可能把半成品当正式状态继续用；不可变版本为每次换手留下清楚的提交边界。

交接包 = 一张值班交接单（生产还补任务 ID/工件引用/有效期/权限/截止时间/人工接手人）。原始轨迹留在子会话或审计存储，接力棒只带当前状态和可展开的引用——减少上下文负担，保住追溯路径。

## 失败后从原地继续

交接失败至少返回三项：失败阶段、最后已接收版本、机器可读原因（edit v2→v2 stale_claim_binding 齐备）。编排器重新调度编辑棒、再提供同一个 v2——**研究和核查没必要重跑**。

接入外部副作用多做两件事：① 同一阶段生成**稳定幂等键**（网络超时重试时接收方识别同一次交接；A2A 允许用 messageId 去重但规范不保证天然幂等——业务系统仍要持久化自己的执行键和结果）；② 区分"**没有收到回执**"和"**对方没有执行**"——银行可能已打款只是本地没收到响应，不能简单重试，先查询外部真实状态再决定补发/补记回执/转人工。

## 2026 年的交接接口

- **OpenAI Agents SDK**：handoff 是模型可调用的工具——input_type 约束交接原因/语言/优先级，input_filter 筛选下一位看到的历史，is_enabled 动态关闭交接路径。提醒：input_type 适合交接元数据，已有应用状态放运行上下文；涉及参数授权要在 on_handoff 开始处重新检查
- **DeepSeek Harness**：ctx.subagents 挂多 provider——spawn 新上下文、fork 继承父会话已完成历史；provider 决定任务怎样运输，Baton 决定业务状态怎样交付
- **A2A v1.0**：Message/Task/Artifact 分开——Message 交流、Artifact 正式产出；关键内容不能只依赖临时消息，客户端要用任务和工件恢复状态
- **Anthropic 长程实践**：claude-progress.txt + Git 历史——进度文件快速接手，Git 提供可验证版本历史。共同说明：**上下文会结束，工件和版本要留下**

框架解决会话/路由/生命周期/协议互通；**业务系统仍要定义工资单/合同/简报/部署包的验收条件——模型知道"该转给谁"，不等于接手者已经拿到可放行的业务状态。**

## 适用边界

适合：顺序和责任都有业务意义的流程——研究/核查/编辑/发布；客服分诊/专业处理/升级/回访；合同起草/法务审核/签署/归档；薪酬核算/资金检查/付款/银行回执；长程 Agent 跨会话跨天继续同一工作。

不必用：一个 Agent 一个上下文几步完成；多项工作无先后依赖（扇出聚合更省时）；团队说不清每棒交付什么只能转发聊天记录；多 Agent 同改一份状态无所有权和合并规则。**每增加一棒增加一次序列化/验收/等待/失败恢复——新角色应有独立的专业责任、权限边界或验收价值；只为角色扮演拉长链条，系统更慢更难追责。**

## 协作模块收官：四模式打配合

四种模式共享一套边界语言：**任务有身份、事实有来源、工件有版本、改变有责任、接收有回执**。外部框架（dsh、OpenAI Agents SDK、DeepAgents）可替换 Agent 的运输方式，业务契约决定协作是否成立。

## 思考题（课程留题）

1. 交接包能否区分原始主张、已确认事实和最终工件？
2. 下一位 Agent 怎样证明自己消费的是上一棒刚验收的版本？
3. 某一棒失败后，系统能否指出最后检查点、拒绝原因和接手人？
