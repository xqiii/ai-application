# 33｜扇出聚合：让多路证据保留差异再汇成结论

> 来源：极客时间《Agent 设计模式之美》黄佳 · 协作：合鸣之美
> 原文链接：https://time.geekbang.org/column/article/1012847 （时长 23:05）
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

扇出聚合（协作×并行）= 把有真实并行面的任务分发给多个独立执行者，聚合器依据**覆盖、口径、冲突、来源**规则把局部工件收成"可以继续裁决"的结果——**收回来不等于拼起来；好的聚合器不是尽快消灭差异，而是先判断哪些差异可合并、哪些必须保留。**

## 开场实验：扁平化投票的错误

三位研究员分别回答 dsh 子 Agent 隔离问题的三个维度：Atlas 说会话上下文隔离（session）、Birch 说进程内 Worker 可能看同一工作区（workspace）、Comet 说工具列表可受限（tools）。

- **flatten and vote**（没写 shared 就算支持隔离）：verdict=isolated support=2/3, lost=workspace:shared——三张卡没围绕同一字段投票，折叠成布尔值后多数票失去统计意义
- **evidence-aware gather**（按维度收回）：verdict=**qualified**（有条件成立）——session=isolated / workspace=shared / tools=restricted 各有来源，risk=workspace_shared 交下游

准确表述：进程内 spawn Worker 拥有独立会话，工具面可受限；文件系统是否隔离取决于 provider、沙箱和运行策略。**session=isolated 与 workspace=shared 并不冲突——它们描述两种不同边界；扁平化的错误在于删掉了证据所属的维度。**

## 模式定位与三个收益

血脉：MapReduce（2004，Map 处理分片 / Reduce 按键合并 / 运行时管调度故障恢复）——最重要的启发是**执行函数与收口函数分开设计**。Agent 比数值计算多一层语义问题：两个整数可直接求和，两份调查结果可能讨论不同对象/时间/单位/来源。Bagging 的前提也是基学习器存在差异——**同一模型/提示/资料/搜索顺序的多个 Worker 共享同一盲区：输出数量增加，独立证据没有增加。三份同源判断不会因为来自三个会话就自动成为三份独立证据。**

双轴坐标：**协作 × 并行**。三段运行：扇出可独立推进的工作 → 各 Worker 在隔离上下文形成小工件 → 聚合器按明确规则对齐/去重/保留冲突收成总结果。

三个收益：
1. **缩短墙钟时间**：三方向 12+8+10 分钟串行 30 分钟，并行接近最慢一路+调度聚合开销——适合检索/扫描/初筛/核验等等待长、分片依赖少的任务
2. **扩大证据面**：不同来源/工具/专业角度（安全查漏洞库、代码读调用路径、运维查配置）——但证据面扩大 ≠ 增加票数，要保留结论和来源血缘
3. **局部失败显式化**：8 个 Worker 处理 800 份合同只回来 7 份——聚合器应报告缺哪一批，而不是把 7 份高质量报告拼成看起来完整的总结。类型化聚合把缺席/超时/坏格式/冲突保留在报告中，系统才有机会选择等待/重派/降级/交人

**与相近模式的区分**：层级委派强调责任划分（三块责任是否全完成）；扇出聚合强调多路结果收回（保持维度不被压成一张选票）；并行探索强调候选解法（三条补丁路径竞争，不是证据分片收回）。真实系统常组合：Lead 按地区层级委派 → 每地区对资料源扇出聚合 → 未决问题启动并行探索。

## 聚合前的可比性五要素

EvidenceCard 最容易忽略的是 **dimension**——没有它，"会话隔离"与"文件共享"像两个打架的答案；有了它，系统才知道两张卡谈不同边界。

生产可比性还要：
1. **对象一致性**：所有 Worker 在讨论同一对象吗？"Claude Managed Agents""Claude Code subagent"和自建 wrapper 名称接近、运行边界完全不同——对象绑定产品/provider/部署方式/实体 ID，不只靠自然语言名称匹配
2. **时间一致性**：一个用 2026-08 文档一个引 2025 旧实现，结论不同可能只是版本变化——保留 observed_at/版本号/commit
3. **单位口径一致**：38444 与 384.44 可能只差分元换算；10% failure rate 按调用算还是按任务算——归一化前不能加总比较
4. **来源可追溯**："根据官方资料"不是稳定引用——保留来源 ID/版本/访问时间/内容摘要
5. **置信语义一致**：不同 Worker 的 0.8 是模型主观把握、分类器概率、规则命中率还是校准统计概率——字段名相同不代表语义相同

## 聚合器五步

1. **盘点缺席**：要求的工件是否全部出现——缺一个维度报告就进 insufficient，不让主 Agent 凭常识补写。分片 ID 识别（expected {A,B,C,D} / received {A,B,D} / missing {C}），缺失分片进结果状态/监控/重派——**成功结果的数量不能掩盖未处理输入**
2. **归一口径**：workspace/working directory/repo root 可能指同一对象也可能分别指容器目录/进程工作目录/仓库根——归一化靠术语表/实体映射/业务主数据，不靠字符串相似度。E0007 和 0007 是否同一员工要查主数据；USD 100 和 SGD 100 不能相加；按月统计与按结算周期统计不能混
3. **去重**：区分"独立来源支持同一结论"与"同一来源被多个 Worker 重复引用"——三张卡引同一篇官方文档说明独立找到同一资料，不是三份独立证据。去重看结论重复+来源重复+来源间上游依赖（两篇文章来自不同网站也可能都在转述同一份公告——文本不同不代表证据独立）
4. **处理冲突**：发现不同值不立刻投票，先判断冲突类型——本讲两张卡是"不同维度限定"，不是需要消灭的冲突。**投票策略只在以下同时成立时用**：回答同一命题、同一对象和版本、同一取值语义、各路判断足够独立、投票规则与业务风险匹配
5. **检查接缝**：单项全过后检查合起来是否产生新问题——每部门付款没超预算，加起来可能越公司资金线；每微服务满足局部延迟，整链可能超端到端 SLA；每份合同无高风险条款，组合后可能有集中度风险。**接缝问题不属于任何一个 Worker，只能在聚合层被发现**

## GatherReport：报告要把分歧留下来

```python
@dataclass(frozen=True)
class GatherReport:
    verdict: Literal["isolated", "qualified", "insufficient"]
    accepted: bool                          # 结构准入
    missing_dimensions: tuple[...]          # 哪些要求的证据未返回
    conflicting_dimensions: tuple[...]      # 哪些维度内部有未解决冲突
    cards: tuple[EvidenceCard, ...]         # 原始证据卡和来源，可回溯
```

**accepted（材料齐全、结构完整、内部无未处理冲突）≠ 结论为真**——两种判断放同一个 success 字段，上层就分不清到底通过了什么。**状态与结论分开。**

## Harness 现状

现代 Harness 解决运行问题，不解决证据语义：
- **Anthropic 多 Agent 研究系统**：Lead 创建 Subagent 并行探索，压缩结果送回主上下文——适合 breadth-first 查询；Lead 仍要分配范围/判断重叠/识别缺口/形成答案。**Subagent 数量扩大搜索容量，不能替代聚合规则**
- **OpenAI Agents SDK**：asyncio.gather 并行 + output_type 结构化——不会自动知道哪些分片该到齐、哪些来源同血缘、两个结论是真冲突还是维度不同
- **DeepSeek Harness**：ctx.subagents 统一接缝（spawn/fork/ACP/Codex/Claude Code）——provider 决定怎样执行、EvidenceCard 规定局部结果表达、GatherReport 规定多路收回；**Harness 管并发会话生命周期，业务代码负责覆盖口径冲突溯源接缝**

## 指标与适用边界

四指标：分片覆盖率（缺失分片是否都被披露）/ **独立证据率**（最易被高估——三张卡不代表三份证据，要记录去掉同源转述后的来源数）/ 冲突保留率（多少冲突被保留送裁决 vs 被错误扁平化）/ 增量收益（新增 Worker 的新覆盖是否抵得上调用聚合成本）。聚合器本身也要版本和回归测试——词表变化、身份映射错误、冲突规则更新都会改变结论。

适合：输入天然分片（合同/客户/地区/目录/时间窗）；多源核验调查；业务窗口短等待成本高于调用成本（事故排查/风险扫描）。不适合：后项必须读前项完整中间过程；多 Worker 同改一份状态无隔离合并机制；各路结果无共同对象单位时间口径；最终只能把长文本交给大模型"凭感觉总结"；单 Agent 基线已够快。

**Worker 不是越多越好**：分片过细，调度/超时/重试/去重/聚合固定成本迅速增加；聚合器消费所有局部工件，可能成为新的上下文瓶颈。规模大用**分层聚合**：局部 Worker → 分组聚合器 → 区域主题报告 → 上层综合——每层保留覆盖/冲突/来源，不在中间层过早抹平。

## 关键要点（复习用）

1. 扇出解决多路工作怎样同时推进；聚合解决结果怎样收成一份**不掩盖证据状态**的报告。
2. 五步：盘点缺席 → 归一口径 → 去重 → 处理冲突 → 检查接缝。
3. 能够并行返回的结果不一定能够直接比较。

## 思考题（课程留题）

1. 多路结果真的在回答同一字段，还是只因都用了"风险/通过/隔离"这些相似词就被放进同一轮投票？
2. 聚合报告能否列出预期分片/已返回/缺席/未决冲突/每条结论的来源？
3. 三位 Worker 引用同一篇资料：系统记录的是三票支持，还是一份证据被三次发现？
4. accepted=true 表示材料齐全、结论正确，还是业务获准执行？这几种状态被压成同一个成功字段了吗？
5. 增加一位 Worker 带来的新覆盖或独立证据，抵得上额外调用/去重/聚合成本吗？
