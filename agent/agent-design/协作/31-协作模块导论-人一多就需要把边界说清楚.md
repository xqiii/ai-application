# 31｜协作模块导论：人一多，就需要把边界说清楚

> 来源：极客时间《Agent 设计模式之美》黄佳 · 协作：合鸣之美
> 原文链接：https://time.geekbang.org/column/article/1010532 （时长 15:07）
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

Agent 协作 = 把共同目标分配给多个相对独立的执行上下文，再通过明确的边界协议把局部结果组成可验收的整体——三个动作：**分出去、做回来、验整体**；四句话边界契约：**意图随消息、真值随引用、结果随工件、责任随验收**。

## 开场案例：三个研究员交回同一份材料

任务"研究 2026 年多 Agent 框架"同时给三位研究员，结果拿到同一块内容的三个版本（都比较 CrewAI 和 LangGraph）。根因：系统只复制了目标，没有说明——你负责哪块、哪些不在范围内、依据哪版资料、最后交回什么、谁检查完整性。三位都选了最容易进入的方向，各自合理，叠在一起留下两块无人负责的空白。

**两种"完成"**：
- 局部完成：某位研究员返回了一份材料
- 整体完成：必需内容覆盖、重复冲突处理、通过总目标验收

很多多 Agent 系统只记录第一种——所有子 Agent 返回父任务就 completed，做重/漏项/能不能拼起来留给最后的大模型"总结一下"。**这更像同时发起几次调用，谈不上协作。**

**什么才算协作**：一个 Agent 连续调工具仍是一位执行者；加载三份 Skill 也没有变成团队。协作讨论的是多个**相对独立**的执行上下文（上下文/工具/状态/责任至少一项被明确分开）围绕同一目标工作——可以用同一种模型，也可来自不同模型/不同 Harness/不同公司系统。

## 协作契约：意图、真值、结果和责任

工作在单个 Agent 内部时很多信息藏在上下文（为什么排除某方案/用哪版资料/还欠哪步）；跨过边界这些隐含信息就靠不住——接收者只拿到"继续完成简报"，关键数字经几轮自然语言转述混入旧值，上游认为已交付下游认为只是帮忙，出问题无法追责。

**四句话契约**：
1. **意图随消息**：任务消息说明这一棒做什么、做到哪、哪些明确不做——"研究多 Agent 框架"太宽，应该是 Atlas 管拓扑 / Birch 管状态 / Comet 管交接
2. **真值随引用**：关键事实指向原始记录/官方文档/代码版本/数据库快照/commit——不反复口头转述
3. **结果随工件**：Worker 不只返回自由文本——研究交资料卡、代码交补丁和测试结果、审批交版本化决策记录（最小研究卡：责任面/结论/适用范围/来源/版本/未决问题）
4. **责任随验收**：接收者依据明确标准签收后责任才真正交付（谁接收/哪一版/哪套标准/通过退回还是等待/下一步谁负责）

落到三类核心对象：**任务卡 TaskCard**（task_id/goal_ref/owner/scope/input_refs/deliverable/acceptance_ref）、**结果工件 ResultArtifact**（producer/artifact_ref/evidence_refs/version/content_digest）、**验收回执 AcceptanceReceipt**（artifact_version/reviewer/accepted/reason）。

## 什么时候才值得协作

多 Agent 不是更高级的默认架构——它是支付通信、调度、等待和聚合成本后换取**并行、隔离、专业分工、独立视角**。

四类值得考虑的情况：
1. 存在真正互不依赖的工作面（不同资料源/地区/合同/目录/测试分片可并行缩短墙钟）
2. 过程信息超一个上下文的承载范围（子 Agent 留大量搜索阅读，只交压缩工件）
3. 权限或专业责任需要分开（研究员可读资料、发布者才有写权限；对账看工资事实、付款才能调银行接口）
4. 独立视角本身有价值（第二证据源/专职评审/竞争假设——价值不是速度而是不同观察条件）

**三个门槛**：任务可拆（责任清楚可单独验收）/ 状态可管（上下文工具工作区可隔离或写入串行收口）/ 结果可验（局部工件能对齐组合并整体验收）。

**Anthropic 16 Agent 写 C 编译器案例**（产出约 10 万行 Rust、能编译 Linux 6.9）：跑得起来不是因为 Agent 多，而是任务可拆 + 各自有测试 + Docker/Git/CI 防踩脚。**16 个 Agent 卡在同一个 Linux 内核错误上时并行反而失效**——反复排查同一问题、覆盖彼此修改；用 GCC 作正确参照、把问题重切成可单独验证的小块后并行才重新发挥作用。

**多 Agent 写代码不是不行**：每人独立 worktree/容器/沙箱 + 任务锁/合并规则/自动测试/发布门槛——一个都不能少，否则只是把一个人的写权限复制成十份，冲突跟着放大。

**判断是否划算**：先跑单 Agent 基线，再比结果质量/总 token/实际耗时/重复工作/交接问题/真正通过验收的比例——多花成本就要拿出收益。**并行也有天花板**：十个人同时查资料，最后总要有人合材料、统一口径、处理冲突做决定——收口环节慢整体就快不了。

**场景判断表**：

| 现场 | 怎样拆 | 判断 |
| --- | --- | --- |
| 开放式行业研究 | 按地区/公司/资料源分头检索，主编统一成稿 | 适合（工作面独立、读多、可交叉核对） |
| 八百份合同初筛 | 每 Worker 只读一份交风险卡，聚合器查漏评重复冲突 | 适合（输入天然分片） |
| 修一个文件里的状态机 Bug | — | 先克制（单 Agent + 测试循环更连贯） |
| 月末付款 | 对账与异常核查并行，付款只留一个入口 | 混合（判断并行、写入集中） |
| 跨团队内容风控 | 多检测 Agent 按事件独立运行 | 规模够大再考虑编舞，先补事件追踪和治理门 |

## 协作四模式（协作链不同位置）

| 模式 | 边界 | 作用 |
| --- | --- | --- |
| 层级委派 | 谁负责哪块、主管怎样保留总目标 | 拆成拓扑/状态/交接三张互补任务卡；**子代理隔离是伴随机制**（回答"这位 Worker 在什么边界里工作"：看哪些上下文/用哪些工具/多少预算/失败影响多大） |
| 扇出聚合 | 多路结果怎样带口径来源冲突返回 | 统一对象口径、识别同源重复、保留未决冲突、检查全局约束——**不要急着把差异抹平** |
| 对抗评审 | 谁有权提异议、异议怎样影响放行 | 防止主编把有限结论改成无证据的绝对标题（资料只证明进程内隔离，标题却写"所有子 Agent 默认完全隔离"）——提案权/举证权/裁决权由不同责任主体承担 |
| 交接链 | 状态证据责任怎样交给下一棒 | 版本化交接包（当前目标/已确认事实/工件引用/被排除项/下一步责任），接收方签收后责任才转移 |

## 业界 Harness 对照

| Harness/协议 | 边界和接口 |
| --- | --- |
| CrewAI | Crew 角色协作、Flow 状态流程；层级流程 manager 承担委派与验证 |
| OpenAI Agents SDK | 区分 agents-as-tools 与 handoff——**工作委派和控制权转移不是一回事** |
| Claude Managed Agents | 每 Agent 独立 session thread；共享基础设施 ≠ 共享上下文/工具/历史 |
| DeepSeek Harness | ctx.subagents 统一多 provider，提供 persona/工具过滤/委派深度边界 |
| A2A v1.0 | Message 交流、Artifact 正式交付；协议负责互通，业务负责验收 |

名字各异（manager/worker、coordinator/specialist、agent/subagent），要回答的问题没变。

## 关键要点（复习用）

1. 只会分出去 = 一群各自宣布完成的 Agent；没有隔离 = 看似分工实则共享嘈杂上下文；只验局部不验整体 = 开场案例。
2. 三类对象：任务卡固定意图范围、结果工件携带结论来源版本、验收回执说明签收与父目标能否继续。
3. 多 Agent 真正要设计的是 **Agent 之间的边界**——让工作分得出去、收得回来、争得明白、接得安全。
4. 管理启示：设计好"意图随消息、真值随引用、结果随工件、责任随验收"后，团队管理是否也该有清晰的目标设定、沟通机制、明确的责任和交付物形状？

## 思考题（课程留题）

1. 当前设计里的多个 Agent 各自承担哪块不可替代的责任？
2. 删掉其中一个 Agent，交付会明确少掉什么？答案是"好像也不会少" = 一次昂贵的重复调用。
3. 多位 Agent 结论不同时：谁有权修改最终工件、谁有权宣布通过、谁负责保留被否决版本的证据？
