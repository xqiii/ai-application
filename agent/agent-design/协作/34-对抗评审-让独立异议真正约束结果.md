# 34｜对抗评审：让独立异议真正约束结果

> 来源：极客时间《Agent 设计模式之美》黄佳 · 协作：合鸣之美
> 原文链接：https://time.geekbang.org/column/article/1013893 （时长 13:26）
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

对抗评审（协作×循环）= 把提案、举证与放行分配给相对独立的责任主体，评审者对候选工件提出**带规则和证据的结构化异议**，由确定性闸门决定退回/修订/放行/升级——**评审不是"有人看过"，而是"有人能够挡住"；评审结果必须进入状态转移条件。**

## 开场案例：标题说得过满

聚合报告的结论是带条件的（"进程内 spawn Worker 使用独立会话，工具面可收窄；文件系统是否隔离取决于 provider、沙箱与运行策略"），主 Agent 觉得不够利落，把主题定为"DeepSeek Harness 的子 Agent **默认完全隔离**"。

两位评审员检查适用边界：一位指出会话隔离不能推出文件系统隔离；另一位补充不同 provider 在上下文/工作区/工具范围上语义不同。根据异议，重新拟定更准确的主题："dsh 的子 Agent 在会话、工作区与工具三个层面上分别怎样隔离"。

启发：评审者提出反对意见的同时，要让意见**进入合并与发布的状态转移条件**——存在未关闭 blocker 时，候选稿不能从"评审中"进入"已批准/已发布"；修订后的新版本要重新接受评审。

## "有评审"和"评审生效"的差别

Demo 两轮对照：
- **review as comments**：两位评审员提出 2 个 blocker，意见被完整记录，但发布函数没把意见纳入准入条件 → v1 照样发布（problem=objections_recorded_but_not_enforced）
- **review as gate**：存在未关闭 blocker 就不能发布 → v1 拒绝 → 修订为带边界表述的 v2 → 重新评审无阻断项 → 发布闸生成**绑定当前版本的回执**

同样的病灶遍布工程现场：PR 有要求修改的评论但仓库允许强制合并；安全扫描产生高危报告但流水线只查构建成功；合规 Agent 给出风险标记但付款函数只看审批字段是否存在——**系统具备评审功能，评审没有获得控制效果**。

## 工程定义与四个不可缺少的对象

> 对抗评审，是把提案、举证与放行分配给相对独立的责任主体，由评审者针对某一版候选工件提出带规则和证据的结构化异议，再由确定性闸门或授权裁决者决定退回、修订、放行或升级人工。

"对抗"指**目标函数和责任位置不同**：提案者负责证明"可以做"，评审者负责检查"凭什么可以做"（主动寻找足以阻止当前版本进入下一阶段的失败条件）。

四个不可缺少的对象：
1. **候选工件**——没有它，评审对象会在过程中漂移
2. **结构化异议**——没有它，评论无法稳定进入机器规则
3. **裁决策略**——没有它，blocker 只能停留在界面上
4. **版本回执**——没有它，旧评审可能被借给一份已经改过的新工件

位于协作维度：提案/质疑/放行由不同责任主体承担——即使底层同一模型，角色也要在身份/上下文/数据访问/权限中形成明确边界。位于循环拓扑：评审拒绝后走完整路径 提案→评审→退回→修订→重新评审，**新版本不能继承旧版本结论——循环不是让多个 Agent 无休止互相评论，而是让每个新版本都重新获得属于自己的裁决。**

四角色（三权分立，maker-checker 原则）：提案者（提方案）、评审者（指出哪条失败条件被触发）、裁决者/放行闸门（决定能否进入下一阶段）。

## 与生成评审的区别

| | 生成评审（27 讲） | 对抗评审（本讲） |
| --- | --- | --- |
| 服务目标 | 当前产出的质量改进（"还能不能写得更好"） | 状态能否达到转移标准（"是否满足放行条件、是否存在不能被优点抵消的硬伤"） |
| 评审者位置 | 可以是同一运行时中的另一个角色 | **协作边界上的独立责任主体**，异议影响工件能否放行 |
| 升级理由 | — | 错误代价、审计要求、职责分离 |

可以组合：外层对抗评审发现 blocker → 修订过程内部用生成-批评提高修复质量 → 修订完成外层仍要重新评审。**内层负责把东西改好，外层负责决定改好的东西能否发表。**

## 评审独立性的结构化

**"用了多个 Agent"不能证明评审独立**——多个 Agent 可能同一模型、继承同一段上下文、读同一份错误摘要，最后在同一个盲区互相确认。

跨模型增加认知差异，不能代替事实独立：两个不同模型都只读一份错误月报，仍可能一起批准错误数字；反过来，同一模型提案阶段只读月报、评审阶段读独立数据库查询，也可能形成有价值的事实对抗。

**独立性是一组可审计的结构证据**：谁在评 / 它看到了什么 / 它没有继承什么 / 它从哪里取得事实 / 它能不能给自己放行。任务风险越高，要求越严格。

**风险覆盖表**：三位评审者可能都在检查文风，没人核对事实和权限。回答"删除其中一位以后，哪类风险会失去观察者？"——答得出来就不能被取代；答不出来它可能只是"再看一眼"的重复角色。

## 状态机与回执绑定

```
DRAFT → IN_REVIEW ─┬─ CHANGES_REQUESTED → REVISED → IN_REVIEW
                   ├─ ESCALATED
                   └─ APPROVED → RELEASED
APPROVED + mutation → STALE → IN_REVIEW
```

评审发生在上午十点、发布在十一点——中间候选内容/依赖数据/规则版本都可能变化。**发布入口必须重新核对"现在拿到的工件就是刚才评审的那一版"**：回执绑定提案身份版本 + 正文与来源引用的联合摘要——正文改一个字或来源引用被换掉，摘要都变，旧回执不能传给新工件。

> **审批状态不是工件的永久属性，而是"某个版本在某套规则和证据下曾经通过"的历史事实——它不一定持续稳定。**

## 何时适合对抗评审

适合：错误真的会进入下一步业务、单靠程序规则难以完全判断的场景——付款 maker-checker；公开报告重要结论独立核查；安全方案有人专门从攻击面挑问题；法律/医疗/合规职责分离；代码测试通过仍可能有权限扩大或架构副作用。

尤其适合**程序难以直接判断的内容风险**：一句话有没有说过头、结论是否超出证据支持范围、几个分别正确的局部事实拼起来有没有被概括成错误结论——字段齐全格式正确，Schema/类型/规则校验都发现不了。

分工配合：**能明确写成规则的检查（格式/类型/余额/身份/版本绑定）交给确定性程序更稳；需要理解"意思"的问题交给对抗评审**——比把所有检查都交给 Critic 可靠。

风险分层：普通内容一个 Critic 足够；重要工件加独立证据和确定性闸门；真正高风险动作保留人工授权。**关键不是多一个评审者，而是这位评审者到底增加了什么：新的风险覆盖、新的证据来源，还是新的控制权。**

## 思考题（课程留题）

1. Critic 提出 blocker 后，真的能阻止发布/付款/部署吗？
2. 修订产生新版本后，会重新评审还是继续沿用旧回执？
3. Critic 相比提案者，到底多看到了什么新的证据或风险？
