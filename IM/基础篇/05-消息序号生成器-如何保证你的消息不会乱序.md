# 05｜消息序号生成器：如何保证你的消息不会乱序？

> 来源：极客时间《即时消息技术剖析与实战》袁武林 · 基础篇
> 课程主页：https://time.geekbang.org/column/intro/225
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

消息时序一致性的关键是为每条消息找到一个可比较的"时序基准"（全局序号生成器）；由于服务端集群性能差异与多线程处理，即使有了序号也不保证推送有序，还需要服务端包内整流和接收端本地整流兜底。

## 时序一致性为什么重要、为什么难

- **重要性**：消息时序代表发送方的意见表述和接收方的语义逻辑理解，乱序会造成聊天语义不连贯、曲解误会。点对点场景要求接收顺序与发出顺序一致；群聊场景要求群里所有接收人看到的消息展现顺序都一样。
- **理论容易**：单发送方 + 单接收方 + 双端单线程 + 唯一 TCP 连接 + 服务端单线程处理，时序自然有序。
- **实际困难**：单点模型吞吐太低，现实中是多发送方、多接收方、服务端多线程并发处理。时序一致性要求消息具备"时序可比较性"——核心问题是找到一个共同"时序基准"，工程上分三步：找到时序基准 → 解决基准的可用性 → 减少基准之外的误差。

## 如何找到时序基准：三种候选逐一排除

| 候选 | 结论 | 原因 |
| --- | --- | --- |
| 发送方本地时钟/本地序号 | 不可靠 | 用户可随时调整时钟导致序号回退；重装应用本地序号清零；群聊、多点登录等多发送方场景时钟不同步——A 先发言但手机时钟比 B 慢半分钟，按时间排序反而认为 A 晚于 B |
| IM 服务器本地时钟 | 一般不可用 | 服务集群化部署，NTP 同步只能把机器间差异降到毫秒级仍有误差；服务器规模大，时钟统一性维护有挑战 |
| 服务端全局序号生成器 | 可行 | 全局递增序号避免多服务器时钟不同步，常见实现：Redis 原子自增 incr、DB 自增 id、Twitter snowflake 类"时间相关"分布式序号生成服务 |

## "时序基准"的可用性问题

- **Redis incr / DB 自增 id**：取号必须在主库执行，主库单点部署可用性保障较差，且高并发取号容易出现单点性能瓶颈。
- **snowflake 类时间相关生成器**：发号性能一般没问题，但携带的时间精度有限（一般秒级或毫秒级，微博 ID 生成器精确到秒级）；集群化部署携带的服务器时间同样存在时钟不一致问题（只是比控制大量 IM 服务器相对容易）。
- **业务层面的放宽**（结论：并非不可行）：
  - 群聊和多点登录没必要保证跨群的绝对时序，只需保证单个群内有序——可给每个群独立"ID 生成器"，通过哈希规则把压力分散到多个主库实例。
  - 大部分业务可接受同一秒内多条消息的细微排序误差，用户基本无感知，秒级/毫秒级时间精度够用。
  - **微信**：聊天和朋友圈时序用一个"递增"版本号服务实现，版本号是每个用户独立空间，保证递增、不保证连续。
  - **微博**：消息箱依赖"分布式的时间相关的 ID 生成器"对私信、群聊排序，目前精度能保证秒间有序。

## "时序基准"之外的其他误差与两级整流

有了序号也不保证按既定顺序到达，原因有二：集群机器性能有差异（有的机器慢或恰逢 GC，更早收到的消息反而更晚推送）；服务端"取序号、暂存消息、查询接收方连接信息"等多线程处理，先取号的消息不一定先到达。此外某些场景要求绝对有序（如"发分手消息 + 勾选取关"同时触发两条消息，"取关"信令先处理会导致发消息失败），需要两级整流：

- **服务端包内整流**：发送方业务层合并多条消息，或经单发送线程 + 单 TCP 连接保证到达有序；服务端整流流程——生产者为每个消息包生成 packageID、包内每条消息带有序自增 seqId，消费者按 packageID + seqId 整流，最终执行模块只有在一定超时时间内完整有序收到所有消息才执行最终操作，否则按业务触发重试或放弃。背景案例：离线推送中网关机订阅本 IP 的 Topic，Redis 队列组件 Sharding 和网关机多线程消费会导致乱序，"删除所有会话"之类信令乱序推送会造成端上逻辑错误。
- **接收端本地整流**：消息连同序号一起下推；接收方收到后若当前序号大于前一条则追加在会话末尾；否则向前查找倒数第二、第三条，直到找到恰好小于当前消息的那条，插入其后展示。

## 关键要点（复习用）

1. 时序一致性的核心：为消息找到共同的"时序基准"，使其具备"时序可比较性"。
2. 发送方本地时钟/序号（可回退清零）、IM 服务器本地时钟（集群 NTP 仍有毫秒级误差）都不可作基准；应使用全局序号生成器。
3. 全局序号生成器两条路线：单调自增（Redis incr、DB 自增 id，主库单点有可用性和性能瓶颈）与时间相关分布式 ID（snowflake 类，精度秒/毫秒级且集群时钟仍不一致）。
4. 按业务放宽要求：只保证单群有序（每群独立 ID 生成器哈希分压）、接受秒内细微乱序；微信用每用户独立递增版本号，微博保证秒间有序。
5. 有序号 ≠ 推送有序：机器性能差异（GC）和多线程处理仍会导致乱序。
6. 绝对有序场景用"服务端包内整流"：packageID + 包内 seqId + 超时内完整有序才执行。
7. 接收端本地整流：按序号向后追加、乱序时向前查找插入，保证多接收方最终一致。
