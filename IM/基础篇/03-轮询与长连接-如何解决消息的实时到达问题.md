# 03｜轮询与长连接：如何解决消息的实时到达问题？

> 来源：极客时间《即时消息技术剖析与实战》袁武林 · 基础篇
> 课程主页：https://time.geekbang.org/column/intro/225
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

消息实时性的关键是"最快触达，且耗费资源少"；IM 架构经历短轮询 → 长轮询 → 服务端推送（WebSocket / TCP 长连接衍生协议）的演进，分水岭在于能否摆脱 HTTP 无状态的限制、做到基于事件的"边缘触发"。

## 短轮询

PC Web 早期，大部分数据获取采用一问一答的"请求响应"模式（如今浏览门户新闻、刷微博仍是），依赖"手动"触发，新消息产生时不能很好地感知并获取，不适用于实时性要求高的场景。这一时期的 IM 软件多采用**短轮询**：定期、高频地轮询服务端新消息——服务器接到请求后，有新消息就返回，没有就返回空列表并关闭连接。

- 优点：从"请求响应"模式孵化而来，迁移升级成本较低，比较容易落地。
- 缺点：①为提升实时性轮询频率一般较高，但大部分请求是无用的，客户端既费电也费流量；②高频请求对服务端压力大——大量服务器用于抗高频轮询的 QPS，对后端存储资源压力也大。
- 适用：用户规模比较小、不愿花费太多服务改造成本的小型应用。

## 长轮询

与短轮询的最大改进：短轮询不管本轮有没有新消息都马上响应返回；长轮询在本次请求没获取到新消息时**不马上结束返回**，而是在服务端"悬挂（hang）"等待一段时间，等待期内有新消息就能马上响应返回。大幅降低客户端高频无用轮询的网络/功耗开销，也降低服务端处理请求的 QPS，比短轮询更先进。

但长轮询没有完全解决服务端资源高负载的问题，仍然存在：

1. 服务端悬挂请求只是降低了入口请求的 QPS，**并没有减少对后端资源轮询的压力**——假如有 1000 个请求在等待消息，可能意味着有 1000 个线程在不断轮询消息存储资源。
2. 超时时间内没获取到消息就会结束返回，客户端"无效"请求的问题没有完全解决。

适用：对实时性要求比较高、但整体用户量不太大的场景；在不支持 WebSocket 的浏览器端仍有较多使用。

## 服务端推送：真正的边缘触发

短轮询和长轮询没法做到基于事件的完全的"边缘触发（当状态变化时，发生一个 IO 事件）"，根本原因：它们基于 HTTP 协议实现，而 HTTP 是无状态协议——同一客户端的多次请求对服务端来说没有关系，服务端不记录客户端连接信息，所有请求只能由客户端发起；服务端收到新消息时，没法找到对应的客户端来推送。

### WebSocket

随 HTML5 出现，基于**单个 TCP 连接的全双工通信**的 WebSocket 在 2011 年成为 RFC 标准协议，逐渐代替短轮询和长轮询；因获得 Web 原生支持被广泛应用于 IM 服务，Web 端基本属于 IM 的标配通信协议。客户端和服务端只需完成**一次握手**即可创建持久的长连接并随时双向数据传输；服务端收到新消息时可通过建立的连接直接推送，真正做到"边缘触发"，保证消息到达的实时性。

优点：

- 支持服务端推送的双向通信，大幅降低服务端轮询压力；
- 数据交互的控制开销低，降低双方通信的网络开销；
- Web 原生支持，实现相对简单。

### TCP 长连接衍生的 IM 协议

除 WebSocket 外，还有 XMPP、MQTT 及各种私有协议：用户上线连接时，在服务端维护"用户设备 ↔ 具体 TCP 连接"的映射关系；长连接一旦建立就一直存在（除非网络被中断），有消息需要实时推送时就能通过这个长连接实现服务端实时推送。

- **XMPP**：比较成熟、扩展性不错；但基于 XML 格式的协议传输冗余比较多、流量不友好，整体实现复杂，如今移动网络场景用得并不多。
- **MQTT**：轻量级、基于代理的"发布/订阅"模式，省流量和扩展性突出，在很多消息推送场景广泛使用；但它不是 IM 专有协议，对群组功能、离线消息等 IM 个性化业务场景仍需大量复杂的扩展开发。
- **私有协议**：开发人力相对充足的大厂多基于 TCP（或 UDP）自研——一方面贴合业务需要、做到真正的高效和省流；另一方面安全性更高、被破解的可能性小。目前主流大厂多以私有协议为主实现。

## 关键要点（复习用）

1. 实时性 = 最快触达 + 耗费资源少；现在聊天/直播 App 消息收发延迟基本控制在毫秒级（移动网络进步 + 实时技术不断迭代）。
2. 短轮询：定期高频请求，无消息返回空列表；迁移成本低，但客户端费电费流量、服务端 QPS 与存储压力大。
3. 长轮询：无消息时服务端悬挂等待，有消息立即返回；降低无效请求与 QPS，但后端轮询压力不减、超时空返回仍在。
4. 轮询类方案做不到边缘触发的根因：HTTP 无状态，服务端无法主动找到客户端。
5. WebSocket：2011 年成 RFC 标准，单 TCP 全双工，一次握手建立持久长连接，服务端可直接推送，Web 端 IM 标配。
6. XMPP（成熟但 XML 冗余、实现复杂）、MQTT（轻量省流、发布/订阅，但不支持群组和离线消息）、私有协议（高效省流 + 更安全，大厂主流）。
7. TCP 长连接类协议的核心：服务端维护用户设备与 TCP 连接的映射关系，连接常驻（除非网络中断）。
