# 07｜分布式锁和原子性：你看到的未读消息提醒是真的吗？

> 来源：极客时间《即时消息技术剖析与实战》袁武林 · 基础篇
> 课程主页：https://time.geekbang.org/column/intro/225
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

"总未读"和"会话未读"因性能原因需单独维护，但两者变更不原子（部分失败或并发覆盖）会导致"有提醒点进去没有消息""有新消息却没提醒"；解法按性能与复杂度递进：分布式锁 → 支持事务的资源（WATCH 乐观锁）→ 原子化嵌入脚本（Redis + Lua）。

## 未读数为什么重要、怎么维护

"未读数"是强提醒方式：通过 App 角标或内部 Tab 数字标签告知用户新消息。重度用户靠它在多个社交 App 间判断去留；两类错误都不可接受——有提醒点进去却没有事件（强迫症不可接受）、有新消息未读数错误没提醒（错过重要消息）。

两个概念：

- **会话未读**：当前用户和某一个聊天方的未读消息数（群聊/直播间的对端是群或房间）。
- **总未读**：所有会话未读的和。

**为什么要单独维护（而不是实时聚合）**：总未读被高频使用——每次消息推送要带上总未读用于角标展示；有些 App 通过定时轮询同步客户端与服务端的总未读（如微博的消息栏总未读还包括其他业务通知的未读数，靠推送累加计算并不准确）。高频访问下每次聚合所有会话未读，会话数多时需多次从存储获取，容易出现个别会话超时没取到导致总数算少，多次获取累加也容易出现性能瓶颈。所以总未读和会话未读一般**单独维护**。

## 两个不一致案例

单独维护带来一致性问题：总未读数必须等于会话未读数总和，否则出现"收到新消息但角标和消息栏没提醒"或"有提醒、点进去找不到是哪个会话有新消息"。

- **案例一（部分失败）**：B 初始会话未读 0、总未读 0。A 给 B 发消息，加未读第一步"会话未读 +1"成功，第二步"总未读 +1"失败，消息照常推送。结果：B 不知道收到新消息，可能漏看。
- **案例二（并发覆盖）**：加未读第一步"会话未读 +1"后，执行未读的服务器变慢；此时 B 恰好点开与 A 的会话触发清未读——会话未读清 0、总未读清 0 都执行完；变慢的服务器恢复后才继续执行加未读第二步"总未读 +1"。结果：退出会话后角标有 1 条未读，点进去却找不到是哪个会话。

根因：**两个未读的变更不是原子性的**——会出现一个成功另一个失败，也会出现并发更新互相覆盖。

## 三种原子性方案对比

### 方案一：分布式锁

每次修改前先加锁，都变更完后再解开。实现方式：依赖 DB 的唯一性约束（固定记录插入成功与否判断锁获取）、分布式缓存如 MC 的 add、Redis 的 setNX 等。优点是普适性较好；问题：引入一套新的资源访问逻辑会降低吞吐；锁的管理和异常处理容易出 Bug——锁资源的单点问题、宕机情况下如何保证锁最终能释放。适用于较小规模的即时消息场景。

### 方案二：支持事务功能的资源

事务"将多个命令打包，一次性按顺序执行"，执行期间不会主动中断，服务器执行完事务中所有命令才处理其他客户端命令。Redis 通过 **MULTI、DISCARD、EXEC、WATCH** 四个命令支持事务：变更未读前先 WATCH 要修改的 key，事务内执行"变更会话未读 + 变更总未读"，若最终执行时被 WATCH 的 key 已被修改，事务失败，业务层重试直至成功。优点：不需要额外维护锁的资源，实现较简单；缺点：WATCH 是乐观锁策略，未读变更频繁的场景（如很火的群）需要多次重试才能成功，执行效率低、性能容易出现瓶颈。

### 方案三：原子化嵌入脚本（推荐）

Redis 支持嵌入 **Lua 脚本**原子化执行多条语句，可在脚本中实现总未读与会话未读的原子变更，还能实现较复杂的业务逻辑——例如"未读数 7 天未被查看清除就过期失效"这种"读时判断过期并清除"的逻辑。优点：无需额外维护锁资源、高并发下性能好、能承载复杂变更逻辑；代价是嵌入脚本开发有额外学习成本。注意事项：Redis 是服务端单线程模型，Lua 脚本中尽量不要有远程访问和其他耗时操作，以免长时间 Hang 住导致整个资源不可用。

## 从未读数到通用分布式并发更新

本讲表面是消息未读数不一致问题，站在宏观视角是**分布式场景下的并发更新问题**：分布式锁、事务资源、原子化嵌入脚本三种方案，对任何需要保证多个操作的原子性或事务性的分布式场景都是可选方案。

## 关键要点（复习用）

1. 未读数是强提醒，"假提醒"与"漏提醒"都严重伤害体验；总未读 = 所有会话未读之和，但两者单独维护。
2. 单独维护的原因：总未读被高频使用（推送角标、轮询同步），实时聚合多次取数易算少且有性能瓶颈（微博总未读还含其他业务通知，靠轮询同步）。
3. 不一致的两种根因：两步变更部分失败（漏提醒）、并发更新互相覆盖（假提醒）。
4. 分布式锁普适但吞吐低、锁管理复杂（单点、宕机释放），适合小规模场景。
5. Redis 事务（MULTI/DISCARD/EXEC/WATCH）实现简单免管锁，但 WATCH 乐观锁在高频变更下重试多、性能差。
6. Redis + Lua 原子化嵌入脚本：高并发性能好、可实现复杂逻辑（如读时判断 7 天过期清除），仅多学习成本。
7. Lua 脚本内禁止远程访问和耗时操作，防止 Hang 住单线程的 Redis。
8. 三种方案是通用的分布式原子性/事务性方案，不只服务于未读数。
