# 04｜ACK 机制：如何保证消息的可靠投递？

> 来源：极客时间《即时消息技术剖析与实战》袁武林 · 基础篇
> 课程主页：https://time.geekbang.org/column/intro/225
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

可靠投递 = 不丢消息 + 消息不重复。用"业务层 ACK + 超时重传 + Sequence ID 去重"的组合解决在线推送的丢失与重复，再以"消息完整性检查（时间戳比对 / 全局自增序列）"兜底服务器宕机等重传失效场景。

## 消息丢失有哪几种情况

以最常见的"服务端路由中转"型 IM 系统为例（非 P2P：消息从用户 A 发出先经 IM 服务器中转，再由服务器推给用户 B；少数 P2P 类型由 A 的网络直达 B 的网络、不经服务端路由）。发消息整体分两部分：

- 第一部分（步骤 1、2、3）：用户 A 发消息到 IM 服务器，服务器将消息暂存，然后返回成功结果给 A。
- 第二部分（步骤 4）：IM 服务器把暂存的消息推送给接收方 B 的在线设备。

丢失场景：

1. 第一部分步骤 1/2/3 都可能失败——发送过程中网络不通、服务器存储失败、A 等待超时但服务器一直没返回结果，这些情况 A 都会被提示发送失败；之后可通过**重试**弥补，但注意：客户端超时重试时，请求可能已在服务端成功处理、只是响应慢了，因此会导致发送重复消息——**发送端要针对同一条重试消息带一个唯一 ID，供服务端去重使用**。
2. 第二部分：推送的准备阶段或消息写入内核缓冲区后，服务端出现**掉电**，消息无法成功推给 B；此时连接的 IM 服务器已无法正常运转，需要后期的补救措施解决。
3. 即使消息成功通过 TCP 连接到达 B 的设备，B 设备接收后的处理出问题也会丢——如把消息写入本地 DB 时异常没能成功入库：网络层已投递成功但 B 看不到消息，比较难处理。

对策：第一部分靠客户端 A 的超时重发 + IM 服务器的去重机制；第二部分参考 TCP 协议的 ACK 机制实现一套**业务层 ACK 协议**。

## 业务层 ACK 机制

ACK（Acknowledge）即确认。TCP 协议默认自带 ACK 机制，通过标准 ACK 数据包告知发送方已成功接收数据。业务层 ACK 类似，解决的是：**IM 服务推送后如何确认消息是否成功送达接收方**。

流程：IM 服务器推送消息时携带一个标识 **SID**（安全标识符，类似 TCP 的 sequenceId）；推送出消息后将该消息添加到"**待 ACK 消息列表**"；客户端 B 成功接收完后，回一个业务层 ACK 包（携带本条接收消息的 SID）；服务器收到后从"待 ACK 消息列表"删除此条记录，本次推送才算真正结束。

### ACK 机制中的消息重传

推送途中消息可能丢失：B 网络实际已不可达但 IM 服务器还没感知；B 的设备还没从内核缓冲区取完数据就崩溃了；消息在中间网络途中被某些中间设备丢掉、TCP 层一直重传不成功——都会导致 B 收不到消息。

对策（参考 TCP 的重传机制）：IM 服务器的"等待 ACK 队列"维护一个**超时计时器**，一定时间内没收到 B 回的 ACK 包，就从"等待 ACK 队列"中重新取出那条消息进行重推。

### 消息重复推送的问题

收不到 ACK 有两种情况：推送的消息真正丢失导致 B 不回 ACK；或者 **B 回的 ACK 包本身丢了**。第二种情况触发的服务端重传，会让接收方收到重复推送的消息。

对策：服务端推送消息时携带一个 **Sequence ID**，在本次连接会话中唯一；针对同一条重推的消息 Sequence ID 不变；接收方根据这个唯一 ID 做业务层去重——去重后用户 B 看到的仍是一条消息，不影响使用体验。

## 兜底：消息完整性检查

"ACK + 超时重传 + 去重"能解决大部分用户在线时推送丢失的问题，但不能覆盖所有场景：若 IM 服务器在推送出消息后因硬件原因**宕机**，重传这条路走不通了，而 B 重连上线后可能并不知道之前有消息丢失。

思路：在 B 重新上线时，让服务端有能力进行完整性检查，发现 B"有消息丢失"的情况，就重新同步或修复丢失的数据。比较常见的实现是**时间戳比对**：

1. IM 服务器给 B 推送 msg1，顺便带上最新时间戳 timestamp1；B 收到后更新本地最新消息时间戳为 timestamp1。
2. 服务器推送第二条 msg2，带上当前最新时间戳 timestamp2；msg2 推送过程中因某种原因 B 与服务器连接断开，没成功送达。
3. B 重新连上线，携带本地最新时间戳 timestamp1；服务器把暂存消息中**时间戳大于 timestamp1** 的所有消息返回给 B，其中包括之前没送到的 msg2。
4. B 收到 msg2 后，更新本地最新消息时间戳为 timestamp2。

注意：时间戳可能存在多机器时钟不同步的问题，会有偏差、导致数据获取不够精确；实际实现上也可以使用**全局的自增序列作为版本号**来代替。

## 关键要点（复习用）

1. 可靠投递的两个标准：不丢消息、消息不重复，都直接影响用户体验（打赏、送礼消息丢了/重复后果严重）。
2. 发送段（A→服务器）的丢失：客户端超时重发弥补失败，服务端按唯一消息 ID 去重防重试造成的重复。
3. 推送段（服务器→B）的丢失：业务层 ACK 机制——SID + "待 ACK 消息列表" + 客户端回带 SID 的 ACK 包后删除记录。
4. 重传：等待 ACK 队列配超时计时器，超时未收 ACK 就重推（参考 TCP 重传机制）。
5. ACK 包丢失也会触发重传 → 接收方按连接会话内唯一、重推不变的 Sequence ID 做业务层去重。
6. 服务器宕机导致重传失效：用户重连上线时做消息完整性检查，发现丢失即补推修复。
7. 完整性检查常用时间戳比对；多机时钟不同步有偏差时，改用全局自增序列作版本号。
