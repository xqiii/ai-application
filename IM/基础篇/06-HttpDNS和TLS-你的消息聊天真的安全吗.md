# 06｜HttpDNS 和 TLS：你的消息聊天真的安全吗？

> 来源：极客时间《即时消息技术剖析与实战》袁武林 · 基础篇
> 课程主页：https://time.geekbang.org/column/intro/225
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

安全性是 IM 能否存在的底线：从传输（HttpDNS 保入口 + TLS 保链路）、存储（单向散列加盐 + 端到端加密）、内容（敏感词/图片识别 + 联动处置）三个维度防范 DNS 劫持、截获、篡改、伪造与隐私泄露。

## 消息安全性的三个维度

"实时性、投递可靠性、时序一致性"是评价 IM 服务可用性和先进性的指标，安全性则是底线和立命之本。私密聊天 App、轨迹位置服务（位置暴露可能带来人身风险）、远程工控系统（操作被截获篡改可能导致严重工程事故）对安全要求远高于一般业务。从消息的产生和流转细分，安全性分三个维度：**消息传输安全性、消息存储安全性、消息内容安全性**。

## 传输安全一：访问入口安全（HttpDNS）

IM 一般提供公网"接入服务"作为消息收发出入口，通过域名提供给客户端。常见问题是 DNS 劫持，分两类：

- **路由器 DNS 设置被篡改**：常见于安全设置不够（如默认密码）的家用宽带路由器，被黑客或木马改为恶意 DNS，返回仿冒内容或植入弹窗广告。解法：重置路由器配置并修改默认管理密码。
- **运营商 LocalDNS 劫持**，三种典型情况：
  1. 运营商为降低跨网流量、缓存部分域名指向内容，把域名强行指向自己的内容缓存服务器 IP；
  2. 运营商修改 DNS 的 TTL（缓存时间）导致 DNS 变更生效延迟（作者此前一个线上业务域名的 TTL 在某些省市能达到 24 小时）；
  3. 小运营商把 DNS 请求转发给其他运营商解析，分配的 IP 可能跨运营商访问，请求变慢甚至不可用。

**HttpDNS 方案**：绕开运营商 LocalDNS，通过 HTTP 协议（而非基于 UDP 的 DNS 标准协议）直接与 DNS 服务端交互（HTTP 接口后端再向权威 DNS 请求并做数据同步），有效防止域名被劫持。附加优势：HttpDNS 服务器能获取真实用户出口 IP，可选择离用户更近的节点接入，或一次返回多个接入 IP 让客户端测速择优，接入调度更精准（前提是 HttpDNS 服务自身有较全的 IP 库）。目前大厂基本采用 HttpDNS 为主、运营商 LocalDNS 为辅的模式，第三方云厂商也提供 HttpDNS 解析服务。

## 传输安全二：传输链路安全（多通道 + 私有协议 + TLS）

链路安全隐患四类：**中断**（破坏网络、破坏可用性）、**截获**（被动窃取内容）、**篡改**（破坏完整性和真实语义）、**伪造**（模拟正常用户或 IM 服务端）。

- **防中断——多通道 failover**：主链路不通或不稳定时自动切换。两个方向：从 HttpDNS 返回的多个接入 IP 中切换，防某一 IP 中间链路被破坏；切换传输协议，如从基于 UDP 的 QUIC 切到基于 TCP 的私有协议，或给 TCP 私有协议加 HTTP Tunnel 二次封装（微博目前支持此方式），防针对特定协议的中断攻击。
- **防截获/篡改——私有协议**：二进制私有协议因编码问题天然具备一定防窃取防篡改能力，相对 JSON/XML/HTML 等明文传输，被截获后破解成本更高。
- **防截获/篡改/伪造——TLS**：单纯加密的难点在密钥协商——固定密钥会因客户端被反编译泄露；连接时协商的临时密钥在传输中可能被截获；第三方伪装服务端交换密钥则加密也防不住泄露。TLS 把"对称加密算法、非对称加密算法、密钥交换算法、消息认证码算法、数字签名证书、CA 认证"结合：非对称加密 + 密钥交换保证加密密钥不被破解泄露；对称加密保证数据截获后无法破解、无法篡改；数字签名和 CA 认证验证证书持有者公钥有效性、防服务端身份伪造。
- **性能代价与 TLS 1.3**：TLS 相比 TCP 三次握手多出算法确认、密钥协商交换、证书验证，握手多 1-2 个 RTT，有连接效率和传输性能的额外开销。TLS 1.3 支持 1-RTT 甚至 0-RTT 握手，大幅降低额外消耗；2018 年 8 月定稿（RFC 8446）后大规模铺开仍需时间，微信早在草案阶段就自行实现了"基于 TLS 1.3 的 MMTLS 协议"。

## 存储安全：单向散列加盐 + 端到端加密

消息漫游和离线消息需要把消息暂存在服务端数据库并保留一定时间，内部人员非法查询或"拖库"都会泄露隐私。

- **账号密码**：采用"高强度单向散列算法"（SHA、MD5 等）+ 每个账号独享的"盐"（很长的随机字符串）加密存储。非暴力破解下很难由密文反推明文，加盐进一步提高逆向难度；但密文和盐都被获取也只是提升破解成本，还需网络隔离、DB 访问权限、存储分离等多方位综合防治。
- **消息内容**：存在服务端无论明文密文都有泄露风险，最好方式是内容采用**端到端加密（E2EE）**——通信双方各自生成密钥对并交换公钥，私钥保存在本地不给 IM 服务端，消息用接收方公钥加密，服务端无私钥无法解密，中间任何环节都不解密；同时消息内容**不在服务端存储**。除收发双方外任何中间环节（包括研发者）都无法获取原文，顶多停止这种加密方式。WhatsApp、Telegram 采用 E2EE；国内 QQ、微信等由于网络安全要求暂未采用。

## 内容安全：识别 + 联动惩罚处置

针对恶意链接（引诱到钓鱼网站）和反政、淫秽图片视频等风险的识别与传播控制，一般依托第三方内容识别服务：

- 敏感词库识别文字内容；图片识别技术处置色情/广告/涉政图片视频；
- "语音转文字"和 OCR（图片文本识别）辅助挖掘图片和语音；
- 爬虫技术分析链接内容，识别"风险外链"。

服务端更多要做与识别配套的**惩罚处置机制**：个别人发色情视频图片可联动"禁言"；群里多人发违规视频可"禁止发多媒体消息"或"解散群"，按业务灵活处理。

## 关键要点（复习用）

1. 安全性是 IM 的底线和立命之本，分三个维度：传输安全、存储安全、内容安全。
2. 入口安全的最大威胁是 DNS 劫持：路由器 DNS 被篡改 + 运营商 LocalDNS（指向缓存服务器、改 TTL 致变更延迟、转发解析致跨网变慢）。
3. HttpDNS 用 HTTP 协议绕开 LocalDNS 直接向 DNS 服务器解析，还能基于真实出口 IP 精准调度、返回多 IP 供客户端测速择优。
4. 链路四类隐患：中断、截获、篡改、伪造；防中断靠多通道 failover（多接入 IP、QUIC→TCP 私有协议、HTTP Tunnel 二次封装）。
5. TLS 组合对称加密、非对称加密、密钥交换、消息认证码、数字签名证书、CA 认证，分别解决密钥泄露、内容截获篡改、服务端伪造；代价是握手多 1-2 个 RTT，TLS 1.3 优化到 1-RTT/0-RTT（微信 MMTLS）。
6. 密码存储用高强度单向散列 + 每账号独享长随机盐，并辅以网络隔离、DB 权限、存储分离。
7. 消息存储的极致安全 = 端到端加密（私钥不出本地、服务端无私钥解不了）+ 服务端不存消息；WhatsApp/Telegram 采用，QQ/微信因国内网络安全要求暂未采用。
8. 内容安全 = 敏感词库、图片识别、语音转文字/OCR、外链爬虫分析 + 禁言、禁发多媒体、解散群等联动处置闭环。
