# 02｜消息收发架构：为你的 App，加上实时通信功能

> 来源：极客时间《即时消息技术剖析与实战》袁武林 · 基础篇
> 课程主页：https://time.geekbang.org/column/intro/225
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

IM 可看作融入各业务系统、提供"实时交互"能力的技术模块；给已有系统增加 IM 功能（不重建账号体系）的核心三块工作：消息存储（内容表 + 收发双索引 + 最近联系人表）、高效实时的消息收发通道（含第三方辅助通道）、两级消息未读数。

## 消息存储：三个关键表

### 消息内容表 + 消息索引表

点对点消息收发双方的历史消息相互独立——发送方删除某条消息，接收方仍能获取到。因此：

- **索引表**：收发双方各有一条自己的索引——发送方的发件箱索引（0）、接收方的收件箱索引（1）。
- **内容表**：收发双方看到的消息内容一致，独立存一份消息维度信息（消息 ID、消息内容、消息类型、消息产生时间）；两个索引表通过同一个消息 ID 与内容表关联。

例：张三给李四发"你好"→ 内容表插 1 条（ID=1001，内容"你好"，文本消息，创建时间）；索引表插 2 条——张三的索引（对方 UID=李四、发件箱 0、消息 ID=1001）、李四的索引（对方 UID=张三、收件箱 1、消息 ID=1001）。

### 最近联系人列表

让互动双方快速查找聊天对象，一般携带两人最近一条聊天消息用于展示。与消息索引表的两个区别：

- 只更新存储收发双方的**最新一条**消息，不存所有历史消息。
- 使用场景不同：索引表用于查收发双方的历史聊天记录，是**会话维度**；联系人表用于查某一个人最近的所有联系人，是**用户全局维度**。

写路径差异：索引表收到消息时大部分是**插入**操作；联系人表很多时候是**更新**操作（首次聊天新插记录，之后再聊天只更新最新一条消息 ID）。张三发完消息会分别更新张三和李四的最近联系人表。

## 消息收发通道

发送方通过发送通道把消息从本地发到 IM 服务端；IM 服务端通过接收通道把消息投递给接收方。两条通道可以各自独立存在，也可以合并为一条。

### 发送通道（实现相对简单）

- 方式一：IM 服务端提供 HTTP 协议的 API 接口，客户端调用接口把消息发给服务端。
- 方式二：客户端与 IM 服务端维护 TCP 长连接，消息以私有协议封装后经长连接发送。

重点是服务端提供消息发送 API，发送方能以任意方式调用发出即可。

### 接收通道（重点：可靠的长连接）

非 P2P 模式下，"有一条消息要投递给接收方"这件事接收方无法实时感知，只有 IM 服务端收到消息时能实时感知，因此投递由服务端触发（不讨论接收方轮询模式）：

- 网关服务与接收方设备之间维护 TCP（或 WebSocket）长连接，借助 TCP **全双工**能力（同时收发数据），有消息时从服务端实时推送给接收方。
- 接收方不在线（网络不通、App 没打开）时，通过第三方手机操作系统级**辅助通道**（苹果 APNs、安卓 GCM、小米/华为等厂商通道）经手机通知栏投递；这类通道由手机厂商维护，只要手机网络可通，App 未打开也能推送——但自身存在问题，多数情况下只作为提升实时触达的辅助手段。

"可靠长连接"的两层含义：

1. 双方能较精确感知长连接可用性，网络原因断连时快速感知并重连等恢复性操作。
2. 经长连接投递的消息不能丢失（解决方式在第 3 篇展开）。

## 消息未读数

对双方互动积极性和频率影响很大的功能：通知栏权限被限制或被忽略时，App 角标的总未读数、联系人后面的会话未读数是"有人给我发了新消息"的重要补救提醒。两个计数维度与变更场景：

- **用户维度总未读** + **会话维度会话未读**。
- 张三给李四发消息 → 李四总未读 +1、李四-张三会话未读 +1；李四打开与张三的聊天页 → 会话未读 -1、总未读 -1。

存储位置：IM 服务端（如 QQ、微博）或接收方本地端（如微信）——需要支持"消息多终端漫游"的应用必须在服务端存储未读数，不需要的可选本地存储。服务端存储下如何保证两个未读数的一致性（分布式场景）留到第 6 篇讨论。

## 关键要点（复习用）

1. 一条消息的生命周期：发送通道提交 → 服务端存储 → 未读数变更 → 接收通道推送（长连接为主、辅助通道兜底）。
2. 点对点消息三表：内容表 1 条 + 索引表 2 条（发件箱/收件箱），靠同一消息 ID 关联；收发双方历史相互独立。
3. 索引表 vs 联系人表：会话维度 vs 用户全局维度；插入为主 vs 更新为主；联系人表只存最新一条消息。
4. 发送通道两种实现：HTTP API、TCP 长连接 + 私有协议封装。
5. 接收通道本质是服务端推送：TCP/WebSocket 长连接全双工 + 系统级辅助通道（APNs/GCM/厂商通道）提升离线触达。
6. 可靠长连接 = 精确感知断线并快速重连 + 投递消息不丢。
7. 未读数两级：总未读（用户维度）+ 会话未读（会话维度）；多终端漫游要求服务端存储。

## 思考题（课程留题）

1. 消息存储中，内容表和索引表如果需要分库处理，应该按什么字段来哈希？索引表可以和内容表合并成一个表吗？
2. 能从索引表里获取到最近联系人所需要的信息，为什么还需要单独的联系人表呢？
