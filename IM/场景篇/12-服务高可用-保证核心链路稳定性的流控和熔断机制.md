# 12｜服务高可用：保证核心链路稳定性的流控和熔断机制

> 课程主页：https://time.geekbang.org/column/intro/225
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

扩容来不及完成、外部依赖变慢是线上常态——用流控（漏桶/令牌桶，单机到 Redis+Lua 全局）把系统保护在压力阈值内、保持"柔性可用"，用熔断（手动开关降级 + 自动 Fail-fast）防止微服务依赖拖出雪崩；"限流、熔断、缓存"并称高并发工程实现的三板斧。

## 为什么只有扩容还不够

- 流量增长过快时，**扩容流程还来不及完成**，服务器可能就已经抗不住了。
- IM 业务对外部接口/资源依赖多：发消息依赖"垃圾内容识别" API 做内容过滤；下推图片消息时，推送服务依赖图片服务获取缩略图。依赖的接口/资源不可用或变慢 → 业务整体失败或被拖慢超时，影响整体可用性。

## 流控两大算法

类比机场"流量控制"：承载超极限负荷时限制后续航班排队，保护机场正常运转；IM 中则通过流控"扔掉"或"排队"来保护系统能力范围内的运转（如第 10 讲直播场景，流控扔掉进出场消息、点赞消息等非核心消息）。

- **漏桶算法**：控制数据注入网络的速率、平滑突发流量——外部的水先进桶，桶以匀速均匀往外漏，桶满则进不了水。外部的水 = 原始请求，漏出的水 = 平滑后的请求；能**精确控制（固定）流量的处理速度**。
- **令牌桶算法**：控制一个时间窗口内通过的数据量。规则：每 1/r 秒放入一个令牌（r 为用户配置的平均发送速率，即每秒 r 个令牌）；桶最多放 b 个令牌，桶满则新令牌被丢弃；来 n 个请求消耗 n 个令牌；可用令牌数小于 n 时，这 n 个请求被丢弃或等待新令牌。
- 两者区别：令牌桶桶身有一定容量，**允许一次把桶里的令牌全取出来** → 在限制请求**平均速率**的同时允许**一定程度的突发流量**。典型场景：明星粉丝群平时请求量小、令牌桶处于"满"状态；明星突然空降、粉丝瞬间活跃，快速消耗掉缓存的 b 个令牌，后端出现一定峰值流量。
- 工程实例：Google 开源 **Guava** 用令牌桶实现了单机版 **RateLimiter**；其 **SmoothBursty** 特性支持累计 N 个时间窗口产生的令牌，应对突发流量能力更好。

## 全局流控（Redis + Lua）

单机瓶颈用单机流控组件即可；分布式场景瓶颈常在**全局的资源或依赖** → 需要分布式全局流控。通用方案：中央式资源（**Redis、Nginx**）配合脚本实现全局计数器或更复杂的漏桶/令牌桶，如 Redis INCR + Lua 实现限制 QPS 的流控组件。精简版逻辑：

```lua
-- KEYS[1]=限流Key；ARGV[1]=每秒最大QPS许可数；ARGV[2]=本次申请的许可数
local current = tonumber(redis.call('get', rate_limit_key)) or 0
local remain_permits = tonumber(max_permits) - current   -- 剩余可分发的许可数
if remain_permits < incr_by_count then
    incr_by_count = remain_permits                        -- 不够时只发剩余部分
end
local result = redis.call('incrby', rate_limit_key, incr_by_count)
if result == incr_by_count then
    redis.call('expire', rate_limit_key, 1)               -- 初次创建Key时设置1秒过期
end
return incr_by_count                                      -- 返回实际申请到的许可数
```

- 关键细节：创建限流 Key 后必须设置过期时间，且整个操作**原子化**（Lua 内完成）——避免分布式操作中"设置过期时间失败"，导致限流 Key 一直无法重置、限流功能不可用。

### 两个进阶问题

1. **细粒度控制**：流控粒度太粗，QPS 没均匀分摊到每个毫秒、边界处理不平滑——上一秒最后一个毫秒和下一秒第一个毫秒都出现最大流量 → 两个毫秒内 QPS 翻倍。解法：把 1 秒分成若干个 N 毫秒的桶，用**滑动窗口**把流控粒度细化到 N 毫秒统计 QPS，同时避免边界不平滑。
2. **流控依赖资源自身瓶颈**：入口流量太大把流控资源（Redis）打挂，反而影响正常业务——微博消息箱业务就发生过流控 Redis 因访问量太大不可用。解法：**本地批量预取**——业务进程每次从远程预取多个令牌缓存在本地，限流逻辑先消耗本地令牌，耗尽再触发远程获取；远程配额已不够时本次请求被抛弃。每次预取 10 个令牌 → 对资源的压力降到 **1/10**。代价：跨秒使用预取令牌会有**限流误差**（上一秒预取的令牌下一秒才用完，下一秒实际请求量偏多）——需要精准控制访问量的场景不适合。

## 自动熔断机制

- **雪崩效应**：微服务经 RPC 相互依赖，API 1 和 API 2 关联部署、共同依赖服务 A/B/C；服务 B 因资源或网络原因变慢 → API 1 整体被拖慢 → 关联部署的 API 2 也整体性能被拖累 → 依赖 API 1/API 2 的上层服务级联变差 → 系统整体性能雪崩。
- 服务间调用可用**超时控制**降低被影响程度，但很多情况下单靠超时难以避免依赖服务性能恶化 → 需要能快速"熔断"性能出问题的依赖调用。
- **手动降级**：通过开关对依赖降级（微博很多场景和业务都用开关实现业务或资源依赖的降级）。
- **自动熔断**：持续收集被依赖服务/资源的访问数据和性能指标，当性能恶化到一定程度或失败量达到阈值 → 自动触发熔断，让当前依赖**快速失败（Fail-fast）**，并降级到备用依赖、或暂存到其他地方便于后续重试恢复；熔断过程中**不停探测**被依赖服务/资源是否恢复，恢复后自动关闭熔断。
- 成熟框架：Netflix 出品的 **Hystrix**、社区火热的 **Resilience4j**。

## 关键要点（复习用）

1. 流控的目的：突发超高流量时避免服务器被流量打死，让业务大部分保持"柔性可用"。
2. 漏桶平滑流量并固定处理速率；令牌桶只限平均速率、允许一定突发（桶容量 b 是关键）。
3. Guava RateLimiter 是单机令牌桶实现，SmoothBursty 可累计多时间窗口令牌以增强抗突发能力。
4. 全局流控 = 中央资源（Redis/Nginx）+ 脚本原子操作；限流 Key 必须原子地设置过期，否则 Key 无法重置、限流失效。
5. 滑动窗口 + N 毫秒分桶，解决 QPS 边界两毫秒翻倍的问题。
6. 本地批量预取把中央资源压力降一个量级（预取 N 个 → 1/N），但引入跨秒限流误差，不适合精准控量场景。
7. 熔断 = Fail-fast + 降级（备用依赖/暂存重试）+ 探测恢复；手动开关降级与自动熔断互相配合。
8. "限流、熔断、缓存"是高并发应用工程实现的三板斧。
