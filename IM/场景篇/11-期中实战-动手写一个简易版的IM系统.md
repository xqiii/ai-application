# 11｜期中实战：动手写一个简易版的 IM 系统

> 来源：极客时间《即时消息技术剖析与实战》袁武林 · 场景篇
> 课程主页：https://time.geekbang.org/column/intro/225
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

期中实战 Demo：用"消息内容表 + 消息索引表 + 联系人列表"三张表、Redis 双结构未读数（总未读 K-V + 会话未读 Hash）和 Web 端 3 秒短轮询，搭一个能登录、文本聊天、未读与新消息自动更新的简易 IM——并与期末实战的 WebSocket 长连接 + ACK + 心跳形成对比。

## 实战定位与计划

- 期中/期末实战以**自己动手实现为主**，Demo 仅作参考，设计层面不能直接用于线上。
- 期中关注点：**消息的存储、未读数的设计**，并以**短轮询**实现消息实时触达——从使用场景出发理解消息存储设计思路、未读数独立两套存储的必要性。
- 期末实战将换成 **WebSocket 长连接**，并加上 **ACK 机制、应用层心跳**：通过两次实战对比，理解长连接相比短轮询的优势，以及 ACK 为什么能解决"数据丢失"、应用层心跳为什么能解决"连接可靠性"。
- 示例代码在 GitHub（coldwalker/Sample）下载。

## 需求梳理

系统只要求构建简单的 Web 界面（没有界面用命令行实现也可以）。具体要求：

支持用户登录；双方简单文本聊天；消息未读数（**总未读 + 会话未读**）；联系人页和未读数有新消息自动更新；聊天页有新消息自动更新。

## 库表设计（单库单表）

- **用户表 IM_USER**：uid 主键 + username/password/email/avatar；用邮箱 + 密码登录；课程聚焦 IM，用户信息维护不作要求，启动时内置几个默认用户即可。
- **消息内容表 IM_MSG_CONTENT**：mid 自增主键（单库单表），含 content、sender_id、recipient_id、msg_type、create_time。
- **消息索引表 IM_MSG_RELATION**：以"归属人 owner_uid + mid"为**联合主键——避免重复写入**；另建 (owner_uid, other_uid, mid) 索引 `idx_owneruid_otheruid_msgid` 做查询加速。
- **联系人列表 IM_MSG_CONTACT**：字段与索引表一致，主键为 (owner_uid, other_uid)——避免同一会话出现超过一条联系人记录。
- 演示未做分库分表；**分库 Sharding 规则**需结合"用户消息收发和查看"的场景，自行考虑库表设计（第 2 讲内容的延伸）。

## 未读数：两套独立存储

总未读虽是会话未读之和，但使用频率很高，每次由会话聚合性能较差 → **冗余总未读单独存储**（第 7 讲"分布式锁和原子性"话题的落地）：

- 总未读：Redis 简单 K-V，如 `owneruid_T, 2`；
- 会话未读：Redis Hash，如 `owneruid_C → {otheruid1: 1, otheruid2: 1}`。

## 短轮询实现与两个注意点

第 3 讲的三种实时性方案（短轮询/长轮询/长连接）任选其一，简版代码采用**短轮询**：Web 端 `setInterval(queryNewcomingMsg, 3000)`，每 3 秒 GET `/queryMsgSinceMid`（携带 ownerUid、otherUid、lastMid）；服务端按"ownerUid + otherUid + mid 大于 fromMid 升序"查增量消息索引，逐条拼接消息内容表返回；返回前清理未读——Hash 删除该会话未读，总未读 increment 减去对应值，**总未读为负则 delete 修正**。

**两个注意点**：

1. 业务"消息对象"与存储层不是一一对应 → 在实体层之上为展现层创建 **VO 对象**（Demo 中的 MessageVO 承接消息展示数据）。
2. 未读数实现没有做到两个未读的**原子变更**，可能不一致 → 用"总未读为负后修正"简单兜底；"未读原子化变更"列入可自行扩展的特性（对应第 7 讲主题）。

## 工程习惯要求

- **代码分层**：表现层（输入/输出的校验与格式，不涉业务）、业务层（只负责业务逻辑组合，不涉展现）、持久化层（只负责数据写入/变更/获取，不涉业务逻辑）——职责清晰、隔离实现细节、便于多人协作。
- **依赖资源**：Web 服务器、DB、Redis 尽量以 **Embedding** 方式提供，便于在 IDE 中执行和代码迁移使用。
- Demo 未覆盖全部课程内容，可自行加入更多特性：**长连接、心跳、ACK 机制、未读原子化变更**等。

## 关键要点（复习用）

1. 消息存储三表：内容表（自增 mid）+ 索引表（owner_uid+mid 联合主键防重写）+ 联系人列表（owner_uid+other_uid 主键防重）。
2. 未读数冗余两套存储：总未读 K-V（高频读，避免每次聚合会话未读）+ 会话未读 Hash。
3. 短轮询 = 定时带 lastMid 拉增量消息，实现最简单；实时性和开销都不如长连接（期末实战对比验证）。
4. 展示对象与存储实体解耦：为展现层建 VO（MessageVO）承接数据。
5. 两套未读非原子变更会不一致，Demo 用"为负修正"兜底，正解是原子变更。
6. 分层清晰 + Embedding 依赖，决定教学代码在 IDE 的可运行性和可迁移性。
