# 09｜分布式一致性：让你的消息支持多终端漫游

> 来源：极客时间《即时消息技术剖析与实战》袁武林 · 场景篇
> 课程主页：https://time.geekbang.org/column/intro/225

## 一句话总结

多终端漫游 = 用户在任意一个设备登录后都能获取到历史聊天记录：靠"设备维度在线状态 + 用户维度离线消息存储"两个前置条件，再用版本号机制实现多终端与服务端的增量同步（最终一致性）；存储超限或写入失败时，用最近联系人列表和消息索引表做"有损"补救。

## 多终端漫游的两个前置条件

多终端漫游是 IM 中相对比较高级的功能：用户交叉使用多个手机聊天后，若不能在多终端间自动同步所有聊天记录，体验会很差。

- 现状对比：微信支持多端登录但**不能在多端同步历史消息**（被诟病的小问题）；Telegram 和 QQ 很好地支持了漫游，任意端登录都能获取所有最近收发的消息。
- **设备维度的在线状态**：多端同时在线时，服务端收到消息后推给接收方的多台设备，也推给发送方的其他登录设备——要求按"用户 + 设备"维度记录在线状态（这也是支持多端登录的前提）。多终端同时在线的情况实现相对简单，维护好这套在线状态就能同时推多台设备。
- **离线消息存储**：消息发送时接收方/发送方只有一台设备在线，之后其他设备上线要能从服务端存储拉取离线期间收发的消息——复杂点全在这里。

## 离线消息怎么存：不能直接复用消息索引表

普通消息存储（第 2 讲）= 消息内容表 + 消息索引表，索引表按**收发双方会话维度**设计。离线消息存储不能直接复用它，原因有二：

1. 离线存储不只存消息，还要存**操作信令**——例如"用户 A 在设备 1 删除了与用户 B 的某条消息"，设备 2 上线时要靠这条信令同步删除本地消息。信令没有消息 ID 概念、不含内容信息、是一次性动作没必要持久化，不适合放进消息索引表。
2. 索引表是会话维度，而拉取离线消息是**单个用户（UID）维度**取数据，没必要按会话存，按 UID 存即可。

成本约束：离线消息存储成本高，且不知道用户到底有几个设备，因此一般有**时效和条数限制**（如保留 1 周、最多 1000 条）；在不超大小/时效限制的前提下采用 **FIFO（先进先出）淘汰**。某个终端同步完成后**并不删除**离线消息（后续可能还有该用户其他设备上线拉取）。

## 版本号同步机制（核心）

全量下推离线消息的两大问题：浪费流量资源；大量消息终端已存在，全部下推会导致**消息重复出现、信令重复执行**。所以必须按需拉取——业界常见方案是版本号机制：

- 每个用户拥有自己的一套版本号序列空间，版本号在该用户空间内唯一，一般是 **64 位**。
- 每条消息/信令推送给该用户时生成一个版本号，连同内容存入离线存储，同时更新服务端维护的该用户最新版本号。
- 客户端收到消息/信令后，把本地最新版本号更新为最后一条消息/信令的版本号。
- 离线用户上线时提交本地最新版本号，服务端与该用户的服务端最新版本号比对；不一致则从离线存储获取"比客户端版本号新"的增量消息和信令，推给当前上线的客户端。

### 三个工程细节（坑）

1. **存储超限**：增量消息被淘汰，按客户端版本号取增量失败。处理：直接下推所有离线消息，或从消息的联系人列表和索引表获取最近联系人的部分最新消息，客户端浏览时再按"时间相关"的消息 ID 分页获取剩余消息，重复消息靠消息 ID 去重。索引表只存消息不存操作信令 → 可能丢部分信令，但**不会丢消息**（有损补救）。资源充足且对一致性要求高的场景，应尽量提升离线存储容量来提升命中率。
2. **写离线存储失败**：版本号纯自增时，某条写失败、下一条成功，客户端拿版本号来比对"仍存在"，会**漏推**写失败那条。方案：存储时不仅存当前版本号，还存**上一条消息/信令的版本号**，拉取时要求每条消息的"上一版本号 + 当前版本号"能整体串联上；服务端发现版本号不连续，即走超限同样的补救路径。
3. **发送方设备的同步问题**：发送设备不需要收自己发出的消息，无法通过消息下推更新版本号，下线再上线时上报的仍是旧版本号 → 服务端误判而重复下推。方案：给发送方设备仍下推一条**只携带版本号的单独消息**，该设备收到后仅更新本地最新版本号即可与服务端同步。

## 上线体验优化：打包 + 压缩

长时间不上线的用户上线要拉的离线消息多，一条条下推会"消息一条条蹦出来"、过程很长、体验差 → 离线消息整体**打包**成大包合并下推，并对大包进一步**压缩**：既降低网络传输时间，也节省用户流量消耗。

## 关键要点（复习用）

1. 多终端漫游的前提：设备维度在线状态（多端在线推送）+ 用户维度离线消息存储（离线设备上线拉取）。
2. 离线存储 ≠ 消息索引表：要多存操作信令、按 UID 维度存；有时效/条数限制（如 1 周、1000 条），FIFO 淘汰、同步后不删。
3. 版本号机制保证多终端与服务端的数据最终一致性：每用户唯一序列空间（64 位），上线比对版本号只拉增量。
4. 每条消息额外携带"上一版本号"做串联校验，才能感知离线存储写失败，避免漏推。
5. 超限/版本号不连续的补救：联系人列表 + 索引表——可能丢操作信令但不丢消息，属有损补救。
6. 发送方设备靠单独下推的版本号消息保持版本同步，防止重复下推。
7. 离线消息打包 + 压缩下推，优化上线体验并省流量。
