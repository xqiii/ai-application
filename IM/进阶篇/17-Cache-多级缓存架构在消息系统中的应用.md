# 17｜Cache：多级缓存架构在消息系统中的应用

## 一句话总结

缓存是高并发最有效的性能手段（内存比磁盘读取快近百倍），但要左右互搏地在"缓存命中率"与"缓存使用量"间均衡：分布式算法选一致性哈希 + 虚拟节点，热点问题按主从 → L1+主从 → 本地缓存+L1+主从逐级演进。

## 为什么用缓存 & 分布式算法

Jeff Dean 公布的硬件指标中，同样读 1MB：内存 250,000 ns vs 磁盘 30,000,000 ns，相差近 100 倍——所以业界常说"处理高并发的三板斧是缓存、降级和限流"。但缓存资源成本高，IM 系统要在**缓存命中率**和**缓存使用量**两大指标间不断均衡。

- **取模求余**：消息 ID 对缓存实例数量取模，余数为几就缓存到哪个节点。实现极简，但节点宕机或扩容后节点数变化，取模结果与以前不一样，**加减节点后命中率下降严重**。
- **一致性哈希**（1997 年 MIT 提出）：把全量缓存空间分成 2^32 个区域组成环形结构；消息 ID 哈希为 32 位二进制映射到环上，缓存节点也用同样哈希（如按节点 IP）映射；消息 ID 顺时针找到最近的节点即为其缓存节点。好处：新增节点只让落入新节点区间的那部分消息 miss，其余消息归属不变；宕机同理，只有小部分消息归属变化——命中率波动远小于取模求余。
- **数据倾斜与虚拟节点**：节点少时容易节点间数据不均衡（节点多则分布均匀，但线上机器有限）。解法：为每个物理节点分配**多个虚拟节点**，消息哈希落到任一虚拟节点即落在对应物理节点上——人为创造更多节点把数据打散。例：原本 4 条消息（mid4~mid7）都落在节点 3，加入节点 1 的虚拟节点后 mid4、mid5 落到虚拟节点 1-2，被分到物理节点 1。

## 缓存热点：三种架构演进

热点场景：超级大 V 给粉丝群发长文章，瞬间上万阅读请求涌入；文章是富文本存储、有的超 1MB，且用户可随时修改，不好走 CDN 分发。

### 主从模式（最常见）

主库只写/更新，从库只读（不绝对：写多读少场景主库也可承担部分读取；读 QPS 大时加从库提升抗读取能力）。问题：按文章唯一 ID 哈希后，一篇热点文章只会映射到**一个**从库节点——文章大，即使加多从库副本，千兆网卡带宽也扛不住。**关键数字**：单台机器 120MB 带宽、1MB 文章、QPS 1000 时至少需要 8 个实例。且多从库副本是对主库数据的完整拷贝，成本不划算；单主单从结构下从库宕机，瞬间大量请求穿透到 DB，可能直接导致资源不可用。

### L1 + 主从模式

参考 CPU 和主存结构，在主从缓存前加一层小容量、缓存极热数据的 L1 层。请求先查 L1，未命中再查主从，查到后**回种一份到 L1**。与主从的关键区别：L1 有**分组**概念——一组 L1 可有多个节点，每一组都是一份全量热数据，系统可提供多组 L1，同一数据的请求轮流落到各组；穿透回种后每组都缓存到同一篇文章，相当于多个 L1 节点共同抗读取。L1 一般用 **LRU** 淘汰，既减少内存用量又保证热点不被淘汰；且两层结构下任一层节点宕机都不会让请求直接穿透到后端存储。

### 本地缓存 + L1 + 主从（多层模式）

极热峰值需要多组 L1 才能扛住带宽，但内存昂贵。应用服务器部署数量通常不少，让应用机器用自身少量内存 + 带宽承担部分缓存：请求先查**本地缓存**（应用部署机上），未命中再远程查 L1，最终数据回种本地缓存。依托应用多节点基本彻底解决热点带宽问题，且本地缓存离应用更近、性能更好。代价是**一致性**：应用服务器随扩缩容数量不固定，数据修改后如何同步到各本地缓存很复杂。业界折中方案：本地缓存用**短过期时间**平衡命中率与一致性——如长文章本地缓存 5 秒过期，淘汰后从中央缓存获取新数据，产品层面大多可接受。

## 关键要点（复习用）

1. 缓存的价值依据：内存读 1MB（25 万 ns）比磁盘（3000 万 ns）快近百倍；三板斧 = 缓存、降级、限流。
2. 缓存使用的核心矛盾：命中率与使用量（成本）的均衡。
3. 取模求余简单但加减节点命中率暴跌；一致性哈希（2^32 环 + 顺时针就近）把波动限制在相邻区间。
4. 节点少会数据倾斜，虚拟节点（每物理节点映射多个虚拟点）是标准解法。
5. 热点带宽估算示例：120MB 网卡 + 1MB 文章 + QPS 1000 → 主从模式至少 8 个实例，且副本是全量拷贝、成本高。
6. L1 分组轮询 + 穿透回种：多组小容量全量热数据并行抗热点，LRU 控制内存，双层防穿透。
7. 本地缓存层用应用机器的闲余内存和带宽，是低成本的带宽终极解，一致性靠短过期时间（如 5 秒）折中。

## 思考题（课程留题）

L1+主从模式下，如果热点数据都被 L1 缓存层拦截命中，会导致主从缓存层相应的这个热点数据，由于长时间得不到读取而被 LRU 淘汰掉。这样，如果下线 L1 缓存，还是会有不少的请求直接穿透到 DB 存储层。那么有没有办法，能够让主从缓存在有 L1 缓存层的情况下，依旧能保持数据热度？
