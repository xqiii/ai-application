# 18｜Docker容器化：说一说IM系统中模块水平扩展的实现

## 一句话总结

快速扩缩容（第 10 讲直播峰值应对）的前提是服务和资源能水平扩展；垂直扩展只能解短期瓶颈，要让接入层、业务层、资源层各层都能"随时随地进行无差别的扩容"，实施上借助 Docker 容器化屏蔽部署机器差异、提升扩容效率。

## 垂直扩展：两种手段与共同局限

- **提升单机硬件性能**：CPU 瓶颈加核数和主频；网卡瓶颈升级万兆网卡并接入万兆交换机；内存吃 Swap 则升级内存配置——能快速解决短期系统瓶颈。
- **增加单机服务处理能力**：增加处理线程数榨干硬件；扩大应用内存（如 Java `-Xmx` 增大堆、使用机器本地缓存）；带宽瓶颈业务可对收发数据压缩降低传输量。
- **局限**：单机性能总有极限，垂直扩展只能解决短期资源和服务器瓶颈；长远方案是水平扩展（Scale out）。

## 接入层如何水平扩展

链路回顾（第 1 讲架构）：客户端经 DNS Server / HttpDNS 查询接入服务公网 VIP → VIP 通过 Keepalived 绑定到多台 LVS（单台故障自动切换）→ LVS 在内核态按负载均衡策略分发 IP 包到接入网关机 → 网关机透传给业务处理服务（读写缓存、消息存储）。

- **瓶颈一：单 VIP 建连失败**。LVS 只做 TCP/IP 层转发、不解析应用层，单机转发 PPS 可达千万级，一般不会成为瓶颈；但直播互动场景瞬时上万级长连建连可能压垮单 VIP。方案：**DNS 轮询单域名多 VIP**——DNS 配置多个 VIP 的 A 记录，访问时按轮询等策略选一个供连接（微信长连接域名即返回多条 A 记录）。
- **瓶颈二：应用层接入服务**。大型聊天室/直播间的压力主要来自消息扇出后的下推，其他链路环节对成员增长不敏感。两个手段：
  1. **服务拆分**：把易随热度突升的环节从主链路剥离（呼应第 10 讲），峰值时对拆分后较轻量的接入服务扩容。
  2. **无状态化**：任意用户随时可连任意一台接入服务器。消息精准推送靠**中央的"用户 → 所在网关机 IP"映射**（如 Redis：上线后记录用户在哪台网关机；业务层下推时查映射、通过网关机 API 定向投递），或**网关机 IP 维度的 Topic + 消息队列**（如离线消息拉取）。

## 业务层如何水平扩展

- 业务层对流量波动不如接入层敏感，但日访问量有明显潮汐（凌晨/上午低、晚上高）：低峰保持低部署规模、高峰扩容，提升资源利用率。
- **关键问题**：接入层对业务层是强依赖，业务层扩缩容后如何被接入层及时感知？
- 方案：**服务化改造 + 自动服务发现**。用 Thrift、gRPC、Dubbo、Motan 等 RPC 框架结合服务发现与健康检查组件：业务服务器上线先到"服务注册中心"注册；注册中心通过"主动检测"或"业务服务器主动上报"做定期健康检查，不可用机器摘除；网关机调用前经服务发现获取业务服务器地址，直连某台做 RPC 调用。业务层由此完全无状态，扩缩容对接入层透明。

## 资源层如何水平扩展

资源层 = 缓存 + 存储（消息内容/索引缓存、未读数、离线消息存储等），高并发突发流量下容易出现读写瓶颈。

- **读压力**（第 17 讲多级缓存）：增加从库、增加 L1 缓存、应用层本地缓存。
- **写压力**（主库单主）：**分片（Sharding）**。例："最近联系人"缓存按用户分散到不同缓存实例，靠加实例缓解单实例写入压力。直播间场景消息收发频繁时主库缓存更新压力尤其大。
- **存储层**：同样通过增加从库 + 数据分片水平扩展。

## 容器化部署：水平扩展的实施手段

- 成熟方案是 Docker 等容器化技术：扩容时先把服务打包为 Docker 镜像，通过运维系统或 Kubernetes 等容器管理服务动态分发镜像到目标机器，部署镜像、启停容器。
- Docker 镜像可理解为"**包含服务运行代码和运行环境的最小操作系统**"，分发到机器后启动容器即快速部署运行。
- 典型痛点（例：图片/视频转码服务）：扩容前要在部署机安装一堆本地化工具，工具对内核版本和依赖有要求，常出现装不上、需另装依赖的情况，扩容效率很低。容器化后以固定版本操作系统镜像为基础构建应用镜像、依赖工具固化进去，不再依赖部署机本身的操作系统版本。
- 架构自检问句：业务增长时，"业务支撑能力"能否随服务"水平扩容"线性提升？——水平扩展能力决定架构的"高可扩展性"和生命周期。

## 关键要点（复习用）

1. 垂直扩展（Scale up）= 硬件升级 + 单机服务优化，只能解短期瓶颈；水平扩展（Scale out）才是长远方案，也是快速扩缩容的前提。
2. 接入层入口：DNS 轮询"单域名多 VIP"解决单 VIP 建连瓶颈（LVS 单机 PPS 千万级本身很少是瓶颈）。
3. 接入服务无状态化 = 服务拆分（剥离易突升环节）+ 中央"用户→网关机"映射或网关机维度 Topic 定向推送。
4. 业务层水平扩展靠 RPC 服务化改造：服务注册中心 + 健康检查 + 自动服务发现，扩缩容对调用方透明。
5. 资源层：读压力用多级缓存/从库，写压力（单主）用分片 Sharding，存储层加从库 + 分片。
6. Docker 镜像 = "含服务代码和运行环境的最小操作系统"，把依赖固化进镜像，扩容不再受部署机环境制约。
7. 设计系统时先问：业务支撑能力能否随水平扩容线性提升？
