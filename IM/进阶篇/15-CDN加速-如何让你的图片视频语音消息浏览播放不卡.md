# 15｜CDN加速：如何让你的图片、视频、语音消息浏览播放不卡？

> 来源：极客时间《即时消息技术剖析与实战》袁武林 · 进阶篇
> 课程主页：https://time.geekbang.org/column/intro/225
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

多媒体消息的"播放不卡" = 让用户离资源更近（CDN + 预热 + 流加密保私密）、按需获取（边下边播 + Range 分片）、减小体积（缩略图、WebP、渐进式 JPEG、H.265）、提前触达（预加载秒开 + 长连推小资源）。

## CDN加速与私密性

CDN 原理：把上传的图片/音视频发布到分布各地的 CDN 节点，用户访问时经 DNS 负载均衡就近取资源；节点没有则先从源站同步到当前节点再返回。资源冗余既显著提高响应速度，也缓解源站的读写压力和带宽压力（直播、短视频、图片业务是重度用户）。

- **CDN 预热**：默认是"拉模式"（节点无缓存时回源下载并更新缓存）。超高热度大型聊天室用拉模式会命中率低、高并发全回源，源站带宽和存储压力大。改为"预热"：通过 CDN 服务 API 提交资源地址和区域，触发边缘节点提前回源获取最新文件；也可在业务高峰期预热热门视频图片。
- **私密性怎么办**：CDN 对外公开访问，难做精细化权限（如点对点图片仅收发双方可见、群图片仅群内可见）。判断顺序：① 私密性极高的场景先想有没有上 CDN 的必要——点对点聊天仅一人查看，上 CDN 既浪费资源，多级回源的延迟开销还可能降低体验；② 超级大群、直播间、聊天室等用户量大的场景用"**流加密**"：视频用 **HLS 协议**分片（苹果主导，把媒体流切成基于 HTTP 的小文件分块下载），由 M3U8 索引文件 + 众多 TS 视频片段组成，对 TS 做 **AES 对称加密**，第三方拿到 TS 也播放不了；M3U8 支持为每个 TS 设置"获取密钥的地址"，作为业务鉴权接口（请求时自动携带 Cookie/客户端缓存的认证 Token，鉴权通过才返回密钥），整个解密播放器默认自动支持，无需改造。③ 非 HLS 视频（如系统只支持 MP4）：RC4 流加密 MP4 + 业务接口下发密钥 + 定制播放器"边解密边播放"，成本是需定制播放器、开发成本略高。

## 边下边播和拖动播放

视频消息产品上一般限制在几分钟以内或百兆以内的短视频，但等全部下载完要 10s 以上。方案：播放器下载完**格式信息、关键帧信息**后即开播，后续结合 HTTP 的 **Range 头**按需分片获取，实现边下边播和拖动快进。两个前提：

1. **格式信息和关键帧信息在文件流头部**（在尾部就没法边下边播；可在转码完成时改写入头部位置）。
2. **服务端支持 Range 分片获取**：a. 存储本身支持，如阿里 OSS、腾讯 COS，可真正"按需下载"；b. 存储不支持时用负载均衡层，如 Nginx 的 HTTP Slice 模块——收到 Range 请求后从后端取整个文件暂存到 Nginx 本地 Cache，下一片直接从 Cache 取。缺点：首次获取速度慢、Cache 命中率问题，但仍是可选优化策略。

## 图片压缩和视频转码

保证清晰度的前提下降低文件大小，提升下载性能、降低网络开销。

- **分辨率自适应**：会话内图片先用低分辨率缩略图（一般只有几十 KB），点击后再加载大图；服务端提前压缩几种常见低分辨率缩略图，按终端分辨率按需下载。
- **WebP**：Google 推出，支持有损/无损压缩，同质量比 PNG/JPEG 小 30% 左右。报道称 YouTube 缩略图用 WebP 后网页加载提速 10%，Chrome 网上应用店每天节省几 TB 带宽。短板：iOS 支持性不好，需内置 WebP 解析库，有开发成本。（另有 Google 2017 年的 Guetzli、腾讯自研 TPG 等格式。）
- **渐进式 JPEG**：基线 JPEG 自上而下逐行加载；渐进式 JPEG 分多个扫描区域，首次扫描以模糊/低质量显示、后续逐步提高质量（从模糊到清晰），能提供低分辨率"预览"，且图片超过 10KB 时压缩比更高。Facebook 2015 年在 iOS 应用改用后节省 10% 数据流量、图像加载性能快 15%。代价：编码速度比基线 JPEG 慢 60%，需权衡。
- **H.265 转码**：码率是单位时间传送的数据 BPS，同编码下码率越高越清晰，但带宽成本和流量随之增加。H.265（HEVC，2013 年标准）同画质同码率下比 H.264 占用存储空间少 50%，可降码率保画质省带宽。但编码复杂度约为 H.264 的 **10 倍**，服务端转码耗时和机器成本高很多——很多公司只对部分热点视频做 H.265 编码。

## 预加载与推流

- **预加载**：短视频核心体验指标是"一秒内成功开播率"（秒开），不优化时常需秒级以上网络 IO。通用策略是"部分提前加载"：如 WiFi 下打开聊天会话页自动预加载当前页小视频的部分片段，为平衡流量与体验，按时间或大小限制（如预加载 3s 或 512KB），用户继续看再走边下边播。
- **推流**：借助 IM 自身长连接优势，把带宽占用小的资源实时推给接收方——语音流、图片缩略图、视频封面图。注意：消息收发通道尽量只传小音频/缩略图避免阻塞；确需推视频流或原图的，长连通知客户端另起一个临时连接传输。

## 关键要点（复习用）

1. CDN 的本质是"让用户离资源更近"的资源冗余：DNS 负载均衡就近访问 + 未命中回源。
2. 热点场景用 CDN 预热替代拉模式，避免缓存命中率低导致高并发回源压垮源站。
3. CDN 精细化权限难做：点对点私密内容不上 CDN；大群/直播间用 HLS（M3U8 + AES 加密 TS + 密钥地址鉴权）。
4. 非 HLS 视频可用 RC4 加密 + 业务下发密钥 + 定制播放器边解密边播放。
5. 边下边播两前提：格式/关键帧信息在文件头部 + 服务端支持 Range（OSS/COS 原生支持或 Nginx Slice 模块）。
6. 图片三板斧：分辨率自适应（缩略图几十 KB）、WebP（小 30%，iOS 需内置解析库）、渐进式 JPEG（省 10% 流量快 15%，编码慢 60%）。
7. H.265 同画质省 50% 存储但编码复杂度 10 倍，只对热点视频转码。
8. 秒开靠预加载（3s 或 512KB）+ 长连推小资源（语音流/缩略图/封面图），大流另起临时连接。
