# 22｜答疑解惑：不同即时消息场景下架构实现上的异同

> 来源：极客时间《即时消息技术剖析与实战》袁武林 · 进阶篇
> 课程主页：https://time.geekbang.org/column/intro/225
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

进阶篇收尾，从讨论区摘录 5 个代表性问题集中回复：服务端要不要存消息、长连接如何精准找到连接、TCP ACK 之外为何还要应用层 ACK、海量离线消息怎么推、群聊与直播互动消息下推的区别——共同启示是"从问题和业务形态的本质出发"。

## 第一问：消息一定要在服务端存储吗？

主要权衡**存储成本与数据安全**，并受产品定位和监管约束：

- 消息不在服务端存储时，服务器只是消息的中转路由服务——存储成本低很多，数据安全性也更好。
- **产品定位**：不需要支持消息多终端同步的产品（如微信），核心消息可以不在服务端存储；但好友关系等数据仍需存储在服务端。
- **离线消息例外**：大部分 IM 支持离线消息，即使不支持多终端同步，也需要在服务端对离线消息暂存（哪怕时间较短）。
- **监管**：若监管有要求，所有消息数据需在服务端存储一定时间供监管调看——只是存储的使用方不是普通用户，而是监管部门。

## 第二问：长连接如何精准找到用户对应的网络连接？

关键在长连建立后的**"上线"操作**：

1. 上线时把当前登录用户信息上报到服务端，服务端维护"**用户 → 连接**"维度的映射（存中央资源或网关机本地内存）；
2. 下推时两种模式：消息下推服务查中央映射、获取该用户的连接定点下推；或把消息下发给**所有网关机**，由网关机查本地映射，有该用户连接在本机就经本机连接下推；
3. 用户断连下线时，从中央映射或网关机本地删除该映射。

## 第三问：有了 TCP 的 ACK，为什么还要应用层 ACK？

- TCP ACK 只保证**传输层**的可靠：连接异常断开时，TCP 发送/接收缓冲区里的数据都可能丢失。
- 即使消息成功交到应用层，也**不保证业务层可靠**：手机 Crash、突然没电关机、客户端把消息写入本地数据库失败——这些都会导致 TCP 层已 ACK 但业务层消息仍丢失。
- 业务层 ACK 的时机是"应用层接收到数据**并成功执行完必要的存储等逻辑后**"才回给服务端，因此能保障消息收发在业务层的真正可靠性。

## 第四问：离线消息特别多时怎么下推？

长时间未登录或接收频繁的用户上线时面临海量离线消息下推：

- **批量打包 + 压缩**：大幅降低传输数据大小，还能减少大量离线消息对应的 ACK 回包数量。
- **推拉结合**：面对上万条离线消息，单纯批量+压缩不够——上线时服务端只**推**最近 N 条消息，其余由用户向上翻页触发自动**拉**取，客户端再从服务端获取会话剩余消息。
- **存储成本**：绝大部分 IM 不永久缓存离线消息，一般按条数或时间周期，只保留最近 N 条或最近一段时间内的离线消息。

## 第五问：群聊和直播互动的消息下推有什么不一样？

核心差异：**房间隔离 vs 群不隔离**，决定扇出发生在哪一层。

- **直播**：房间之间是隔离状态，用户进入新房间只与当前房间有关联。用户通过"加入房间""切换房间"等信令（携带用户 + 房间信息）告诉网关机当前连接的房间，网关机据此标记"**用户 → 房间 → 连接**"映射；消息只需按**房间维度**下发到网关机——所以直播互动场景中**消息扇出可以推迟到网关机层**。（针对留言中"切房后网关层数据未更新导致收不到新房间消息"的疑虑：正是靠加入/切换房间信令来更新这个映射。）
- **群聊**：群和群之间不隔离，没有"进入群聊/切换群"的行为——App 建立长连后的"上线"操作只上报用户信息，网关机只能建立"用户 → 连接"映射。因此群消息发出时，**必须在业务层把消息从群维度扇出成 UID 维度**，再下发给网关机。
- 能否让网关机查群成员后自行扇出？实现上可以，但为了**解耦网关机与业务层逻辑**，建议不在网关机做业务维度逻辑，仍在业务层扇出后再提交网关机处理。

## 关键要点（复习用）

1. 消息是否存服务端 = 成本/安全 + 产品定位（多终端同步与否）+ 离线暂存 + 监管要求，四个维度综合决策。
2. "上线"操作的本质：建立并维护"用户 → 连接"映射（中央或网关本地），下线时删除；下推可查中央定点推，或全网关机广播、本地匹配。
3. TCP ACK 保传输层，业务层 ACK 保"接收 + 存储逻辑执行完"的业务可靠性——两者不可互相替代。
4. 海量离线消息：批量打包压缩（省带宽、省 ACK）→ 仍不够则推拉结合（推最近 N 条 + 上翻页拉取）。
5. 直播房间隔离，网关机维护"用户→房间→连接"映射，扇出可推迟到网关层；群聊不隔离，必须在业务层扇出到 UID 维度再给网关机。
6. 设计原则：网关机尽量不做业务逻辑，保持与业务层解耦。
7. 方法论收束：技术没有银弹、形而上学难有的放矢——从问题和业务形态的本质出发思考实践，才能找到适合自身业务的架构。
