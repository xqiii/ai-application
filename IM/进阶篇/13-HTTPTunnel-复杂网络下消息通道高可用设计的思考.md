# 13｜HTTP Tunnel：复杂网络下消息通道高可用设计的思考

> 来源：极客时间《即时消息技术剖析与实战》袁武林 · 进阶篇
> 课程主页：https://time.geekbang.org/column/intro/225
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

消息通道承载上行（用户发消息/触发行为）与下行（服务端推消息/信令）全部流量，通道高可用要同时解决三个问题：**连得上**（多端口、HTTP Tunnel、多接入点）、**连得快**（跨网优化、跑马竞速）、**保持稳定**（通道与业务解耦、上下行隔离、多媒体独立通道）。

## 让消息通道能连得上

用户网络情况复杂：2G 网络、HTTP 代理上网、DNS 解析被封，加上移动运营商各种奇怪的限制，"连得上"做起来并不容易。

- **多端口访问**：端口 0~65535 分三类——公认端口（0~1023）、注册端口（1024~49151）、动态或私有端口（49152~65535）。由于移动网管代理的端口限制和网管软件的安全管控，大部分端口存在连通性风险，业界确认比较安全的端口基本只有 **80、8080、443、14000**。外网服务应尽量选用这几个端口，并可同时暴露其中几个互为 Failover 备用端口。
- **HTTP Tunnel**：部分公司/酒店网络代理只允许 HTTP 协议出网（早期 CMWAP 接入点也有此限制，2011 年后 CMWAP 与 CMNET 融合已解决），TCP/UDP 私有协议过不了代理校验。HTTP Tunnel = 用 HTTP 协议封装其他网络原因不兼容的协议，且只在私有协议最外层做最轻量封装（HTTP Body 就是二进制私有协议），协议解析基本没有额外代价。
- **多接入点 IP 列表**：借助 HttpDNS 返回多个接入点 IP，一个连接失败就尝试下一个，形成接入点 Failover；再在客户端**预埋**一个域名 + 几个常用接入点 IP 作为最后兜底（预埋 IP 需保证稳定，有变动要及时随新版 App 预埋）。

## 让消息通道连得快

- **解决跨网延迟**：让某运营商的用户通过托管了该运营商专线的机房接入点接入。要求一：多运营商机房接入点（基本只是成本投入，多数 IDC 支持多线接入）；要求二：避免运营商 DNS 解析转发和 NAT 把接入 IP 解析到其他运营商——用 HttpDNS 直接获取用户出口网关 IP，调度更精准且绕过 LocalDNS。
- **跑马竞速**：多个接入点 IP 因用户上网地点和路由规则不同，连接延迟不一样。客户端对返回的 IP 列表全部并发测速（如访问一个固定大小的静态页面，按整体响应耗时排序），测速结果上报服务端，服务端结合接入服务器负载动态调整 IP 列表顺序，让用户优先连最快的接入点。例：客户端启动时经 HttpDNS 拿到 VIP1/VIP2/VIP3，并发测速后选耗时最少的 VIP2 正式接入。

## 让消息通道保持稳定

- **通道和业务解耦**：消息存储、加未读、版本兼容等业务逻辑随需求频繁变更，若通道层跟着变就要频繁上线重启，导致用户连接断开（虽有断线重连，频繁断连仍降低收发成功率）。架构上让通道层只做网络连接管理和通用逻辑：用户与连接的映射维护、通信协议编解码、建连/断连处理、ACK 包和心跳包处理；变化大的业务逻辑下沉到后端业务处理层。
- **上下行通道隔离**：直播等场景下行扇出大，大促时下行压力大（即便限流/降级/扩容，整体负载仍高）。可将上行消息和行为走**短连通道**发送：既避免客户端维护多个长连接的开销，又解决上行被下推影响。进一步优化：短连发完不立刻断开，支持一段空闲时间（如 2 分钟）不断开，用户连续发消息时省去重复建连开销。上下行通过**消息队列**隔离解耦：上行短连网关 → 上行业务处理服务（存储/加未读）→ 消息队列 → 下行分发逻辑服务（查在线状态、版本兼容等推送准备）→ 接收方所在长连网关 → 设备。
- **独立多媒体上传下载**：图片/视频传输量大，与文本消息共用连接会造成通道阻塞；开辟独立连接传二进制文件流，既保护核心消息通道，又缩短上传下载链路（详见 14、15 讲）。

**踩坑案例**：作者业务中曾因对外暴露的接入端口不是常见端口，导致很多用户连不上。

## 关键要点（复习用）

1. 通道高可用三问：连得上（连通性）、连得快（延迟）、保持稳定（架构解耦）。
2. 端口连通性：安全端口基本只有 80、8080、443、14000，多端口暴露互为 Failover。
3. HTTP Tunnel 用最轻量的 HTTP 封装私有协议（Body 即二进制协议内容），解析几乎无额外代价。
4. HttpDNS 一招三用：防 DNS 劫持、多接入点 Failover、按出口网关 IP 精准调度避开 LocalDNS 解析转发。
5. 跑马竞速：客户端并发测速多个 VIP + 服务端结合负载动态调整 IP 列表顺序。
6. 通道层只做连接管理和通用逻辑（映射、编解码、建断连、ACK/心跳），业务逻辑下沉。
7. 上下行隔离：上行走短连（空闲保持约 2 分钟），经消息队列与下行长连解耦，适合下行扇出大的场景。
