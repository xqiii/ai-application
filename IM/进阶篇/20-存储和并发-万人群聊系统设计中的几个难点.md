# 20｜存储和并发：万人群聊系统设计中的几个难点

> 来源：极客时间《即时消息技术剖析与实战》袁武林 · 进阶篇
> 课程主页：https://time.geekbang.org/column/intro/225
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

群聊与直播不同：单个群峰值没那么高但总量大（可能上百万个群同时收发消息），靠上云短期扩容不现实，必须从架构设计层面优化——存储从写扩散改读扩散、未读数合并变更、离线 Buffer 只存消息 ID + 批量 ACK、在线状态网关机本地自治。

## 群聊消息存储：写扩散 → 读扩散

- **点对点**（第 2 讲）：一条消息针对收发双方各存一条用户维度索引，便于会话查看、删除、撤回、离线获取。
- **群聊不能照搬**：一万人的群，一条消息要为每人存一条——写入并发量巨大 + 存储浪费。
- **读扩散**：一条消息只按**群维度存储一次**，群里用户查询都通过群维度的消息索引获取。查询流程：先查用户加入的所有群 → 按各群最新一条消息的 ID（消息 ID 与时间相关）或产生时间做"最近联系人"维度排序 → 按群 ID 获取每个群的消息。
- **新成员只看新消息**：加群时记录"用户加群信息"（加群时间、加群时该群最新一条消息 ID），查询时据此限制消息范围。
- **单人删除消息**：群消息共享，不能直接删群维度索引；把被删消息加入"**用户 + 群维度**"的删除索引，查询时对群维度消息与删除索引做**聚合剔除**。同样思路适用于"只有自己能看到"的私有消息（如系统提示类）。

## 未读数合并变更

- 每个用户维护两个未读数（某群的未读数 + 所有未读数，第 7 讲）；群里有人发言就要对群内**每个人**执行"加未读"。
- **量级估算**：5000 人群、平均每秒 10 人发言 → 每秒针对未读资源的变更 QPS = 5 万；100 个这样的群 → 500 万。压力随群人数和发言频率成倍上升。
- **方案：应用层合并变更**。未读变更服务把加未读请求按群 ID 归类，暂存到群 ID 维度的多个"暂存队列"；由两个组件触发刷新：**Timer**（定时，如每秒从队列取数据）和 **Flusher**（按队列长度，如达到 100 就取数据），交给 **Aggregator** 合并——把同一用户在同一个群的多次加未读合并成一个请求再提交底层资源（示例：gid1 里 uid1/uid2 的 4 次 incr 合并为各自 1 次，QPS 降一半；理论上消息 QPS 为 10 时可降到 1/10）。
- **代价**：内存暂存带来加未读延迟；服务器掉电/重启可能丢一部分加未读操作。
- **增强合并效果**：按群 ID 哈希路由，让同一个群的所有未读变更都落到同一台服务器。
- 该方案普适性强：凡有写入瓶颈的业务（如 DB 写入）都可参考，微博线上大范围使用。

## 离线 Buffer 与批量 ACK

离线 Buffer 是用户维度的（第 9 讲），群聊每条消息扇出后要为每个成员暂存——5000 人群一条消息暂存 5000 次，压力大且浪费。

- **优化一：合并暂存**——参考未读数合并变更的思路。
- **优化二：限速/丢弃暂存**保护后端资源。借助"版本号的链表机制"，用户上线时能发现离线消息不完整，再从后端消息存储重新分页获取——把一部分写入压力**延迟转移为读取压力**。注意：会丢失操作信令，是**有损降级**，非必要不用。
- **优化三：只暂存消息 ID**，不暂存内容；真正下推离线消息时再按消息 ID 取内容，避免同一内容重复暂存占用离线 Buffer。
- **离线消息批量 ACK**：微博超大规模粉丝群场景，明星空降激活大量离线用户，同一时间触发大量下推和 ACK 回包处理。但离线消息下推发生在用户刚上线、连接刚建立时，稳定性好、下推成功率高，ACK 及时性要求不高——参照 **TCP Delay ACK（延迟确认）**，等一定时间把多个 ACK 回包合并，降低服务端处理压力。代价：ACK 延迟可能加剧服务端超时重传、重复下推，用**接收端去重**解决，不影响体验。

## 不记录全局在线状态：网关机自治

- **点对点常规做法**：上线时在中央资源记录"用户连接所在的网关机"，下推时查中央在线状态、投递给目标网关机。
- **群聊规模大时的两个瓶颈**：上线时对在线状态的**写入**；消息下推时对在线状态的**高并发查询**。
- **方案（类似直播互动，第 10 讲）**：不维护全局中央在线状态，各网关机"自治"——建连时在本机内存维护当前登录用户信息；业务层查出消息归属群的全部用户，扇出到接收人 UID 维度，投递到**全局消息队列 Topic**；每台网关机启动后订阅该 Topic，收到消息后查询**本地**"在线用户"信息，只把归属本机用户的消息经长连下推。
- **效果**：消息下推从"全局的远程依赖"变成"分片的本地内存依赖"，性能快很多，免去服务端维护全局在线状态的资源开销。

## 关键要点（复习用）

1. 群聊 vs 直播：直播峰值高但持续时间短、可上云临时扩容；群聊总量高、峰值不明显、群数量巨大，靠扩容不现实，要靠架构优化。
2. 群消息存储用"读扩散"：群维度存一份，替代点对点的"写扩散"，解决写入并发和存储浪费。
3. 新成员可见范围靠"加群时间 + 当时最新消息 ID"限制查询范围；单人删除靠"用户+群维度"删除索引 + 查询时聚合剔除。
4. 未读数合并变更：按群 ID 暂存队列 + Timer/Flusher 触发 Aggregator 合并；5000 人群 10 条/秒即产生 5 万 QPS 加未读，合并理论上可降一个数量级；代价是延迟和宕机丢数据。
5. 群聊离线 Buffer 三招：合并暂存、限速丢弃（有损，靠版本号链表上线补拉）、只存消息 ID。
6. 离线消息批量 ACK 学 TCP Delay ACK；副作用（重复下推）靠接收端去重。
7. 万人群聊下推弃用"中央在线状态"，网关机本地自治 + 订阅全局 Topic，把远程依赖变成本地内存依赖。
8. "合并变更"方案可迁移到一切有写入瓶颈的业务（如 DB）。
