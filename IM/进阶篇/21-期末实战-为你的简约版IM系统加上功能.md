# 21｜期末实战：为你的简约版IM系统加上功能

> 来源：极客时间《即时消息技术剖析与实战》袁武林 · 进阶篇
> 课程主页：https://time.geekbang.org/column/intro/225
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

期中实战用 HTTP 短轮询实现了登录、文本收发、消息存储、未读数等基本功能；期末实战把消息收发升级为 WebSocket 长连接，并加上 ACK 重推、应用层心跳、断线重连、idle 超时断连，体会升级前后对使用方体验和服务端压力的改善。

## 功能清单

1. 支持基于 WebSocket 的长连接；2. 消息收发均通过长连接通信；3. 支持消息推送的 ACK 机制和重推机制；4. 支持客户端心跳机制和双端 idle 超时断连；5. 支持客户端断线后的自动重连。

## WebSocket 长连接（客户端 + 服务端）

- **客户端（HTML5 原生 API）**：连接地址 `ws://`（加密为 `wss://`），不再是 `http://`。核心事件监听：`onopen`——连接建立后做用户信息上报绑定（bind）并启动心跳（heartBeat.start）；`onmessage`——处理该连接上收到的所有数据，是最核心的消息推送处理逻辑；`onerror` / `onclose`——异常和关闭时触发 reconnect 自动重连。发送消息只需调 WebSocket 对象的 `send` 方法（JSON：type、senderUid、recipientUid、content、msgType）。
- **服务端（推荐 Java NIO 框架 Netty，对 WebSocket 支持完善）**：三步——创建 **ServerBootstrap**（监听端口、接受连接）；通过 **ChannelInitializer** 初始化管道处理器链：`HttpServerCodec` → `HttpObjectAggregator(65536)` → `LoggingHandler` → `WebSocketServerProtocolHandler`（WebSocket 编解码与协议处理）→ `websocketRouterHandler`（业务总处理器）→ `IdleStateHandler` + `closeIdleChannelHandler`（一段时间无消息传输则服务端强制断开，即 idle 超时断连）；最后挂到 ServerBootstrap 并 `bind().sync()` 启动监听。

## 核心消息收发逻辑

- **上行（发送）**：`WebSocketRouterHandler` 实现 `channelRead0`，收到的都是 `WebSocketFrame`（前面管道加过编解码器）；判断 `TextWebSocketFrame` → 取文本 → JSON 解析出 senderUid/recipientUid/content/msgType → 调业务层 `messageService.sendNewMsg` → 用 `writeAndFlush` 把结果写回发送方客户端。
- **下推（接收）**：网关机内存维护 `ConcurrentHashMap<Long, Channel> userChannel`"用户 → 连接"映射（处理上线请求时 put）；`pushMsg` 时按 recipientUid 查映射，`channel.isActive() && isWritable()` 才 `writeAndFlush` 下推。
- **跨网关分发**：基于 **Redis 发布/订阅**——`sendNewMsg` 完成消息存储、加未读后，把待推送消息发布到 Redis 的 Topic（`convertAndSend`）；`NewMessageListener` 监听该 Topic，感知到消息后解析出接收人 otherUid，提交给 `websocketRouterHandler.pushMsg` 真正下推。

## 消息推送的 ACK 与重推

（呼应第 4 讲：下推后一段时间没收到 ACK 就认为没投递成功，触发重推。）

- **序号 tid**：上线后在该连接维度初始化起始为 0 的序号，每推送一条消息 tid 加 1，消息携带 tid 一起下发。
- **待 ACK Buffer**：推送后把消息加入 `ConcurrentHashMap`（Key = tid，Value = 消息），同时用 `executorService.schedule` 创建**5 秒后**的定时检查。
- **判定**：客户端回 ACK（携带 tid）则从 Buffer 移除（`nonAcked.remove(tid)`）；没回 ACK 则 `checkAndResend` 触发重推，**最多重推 2 次、每次间隔 2 秒**。

## 应用层心跳

（呼应第 8 讲智能心跳：解决网络不确定性导致的"连接不可用"——TCP 没断但已是死链。）

- **客户端**：定时器每 **2 分钟**（120000 ms）通过长连发一次心跳包（type 0，携带 uid 和 timeout）；期间收到服务端消息或响应则清零重置计时；心跳发出 2 分钟内没有收到服务端响应，客户端主动断开连接并尝试重连。
- **服务端**：收到心跳包只回一个普通响应消息（type 0 + timeout）。
- **线上进阶**：改用"智能心跳"——服务端根据心跳情况计算新的心跳间隔，返回给客户端动态调整。

## 关键要点（复习用）

1. 期中短轮询 → 期末长连接：实时性提升的同时也改变了服务端的压力形态。
2. WebSocket 客户端四事件：onopen（绑定+启心跳）、onmessage（核心推送处理）、onerror/onclose（重连）。
3. Netty 服务端 pipeline 顺序：HTTP 编解码 → 聚合器 → WebSocket 协议处理器 → 业务 Handler → IdleStateHandler（idle 超时强制断连）。
4. 网关机用内存 Map 维护"用户 → Channel"映射；跨网关机分发靠 Redis 发布/订阅 Topic。
5. ACK 三件套：递增序号 tid、待 ACK Buffer（ConcurrentHashMap）、定时检查（5s）+ 重推 2 次（间隔 2s）。
6. 心跳 = 周期发包 + 收到响应即重置 + 超时断连重连；线上用智能心跳动态调间隔。
7. 作者提醒：线上级 IM 代码量庞大、同功能因场景不同设计差异大，示例代码"挂一漏万"，重在理解最核心思想；可自行扩展离线消息、群聊等功能。
