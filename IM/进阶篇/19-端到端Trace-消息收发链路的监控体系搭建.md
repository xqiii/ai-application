# 19｜端到端Trace：消息收发链路的监控体系搭建

> 来源：极客时间《即时消息技术剖析与实战》袁武林 · 进阶篇
> 课程主页：https://time.geekbang.org/column/intro/225
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

"服务上线，监控先行"——否则业务上线后就是"蒙眼狂奔"。IM 监控分两大模式：基于数据收集的被动监控（系统层 / 应用层 / 全链路 Trace）和基于回环探测的主动监控；两者协同构成监控双保险。

## 被动监控：系统层与应用层

- **系统层监控**（最基础）：用 Nagios、Zabbix 等工具收集机器维度的 CPU、内存、IO、负载、带宽、PPS、Swap 等性能数据。
- **应用层监控**：监控消息收发接口的 QPS、耗时、失败数、消息在线推送到达率——耗时/失败率增长或到达率降低就要引起注意（微博用的是基于 Graphite 的监控体系）。三层扩展：
  1. **依赖资源监控**：业务 API 所依赖的其他 API/资源，如离线 Buffer 的 Redis 使用量、读写 QPS、耗时——便于接口出问题时快速定位是哪个依赖导致。
  2. **单机维度监控**：整体失败率升高可能只是某一两台机器的问题（吃 Swap、网络抖动），需对单机应用状态分别监控以便快速处置。
  3. **数据收集架构**：应用进程经本地套接字把 Metrics 发给本机"数据收集代理器"Agent（或写本地日志，Agent 流式获取）→ Agent 上报远程数据收集集群（缓存 + 预聚合）→ 存储集群用**时序数据库**（OpenTSDB、InfluxDB）多精度存储，靠高压缩比和聚合计算解决数据规模大、查询效率低 → Web 界面按时间维度查询。
- 成熟方案：Statsd + Graphite + Grafana、ELK（Elasticsearch + Logstash + Kibana）。

## 全链路 Trace 监控

微服务独立部署互相隔离，排查消息收发失败时很难定位是哪个依赖服务/资源引起；且 IM 严重依赖网络可用性，需要从用户体验角度全局监控。方案是基于 Trace 服务做"全链路监控数据收集"。

- **理论源头**：Google 论文 Dapper，a Large-Scale Distributed Systems Tracing Infrastructure，定义分布式跟踪三大设计要点：**低开销、对应用透明、高可扩展性**。
- **三个核心概念**：
  - **Trace**：一次请求完整调用链的跟踪，全局唯一 TraceID 标识；一条 Trace 是多个 Span 组成的**有向无环图（DAG）**。
  - **Span**：调用与被调用服务间的一次请求/响应过程，支持父子关系（如服务 A→B 调用 Span 的父 Span 是用户→A 的 Span），同一 TraceID 串联。一个 Span 记录 4 个时间戳：Client Send、Server Receive、Server Send、Client Receive。整体调用耗时 = CR - CS；服务端处理耗时 = SS - SR；**网络耗时 = 整体耗时 - 服务端处理耗时**。
  - **Annotation**：用户自定义事件的 KV 数据，辅助业务维度查询（如直播发弹幕的 Span 里记房间 ID、发送人 UID）。
- **业界系统**：Twitter Zipkin、Uber Jaeger、阿里鹰眼、美团 Mtrace。Zipkin 架构六模块：**Reporter**（AOP 探针/硬编码嵌入业务，生成并上报 Span）→ **Transport**（HTTP/Kafka/Scribe）→ **Collector**（接收并写入存储）→ **Storage**（默认 In-Memory，支持 Cassandra/Elasticsearch/MySQL）→ **API 层** → **UI**。
- **微博实战**：基于 Zipkin 优化定制的 Trace 系统定位故障点。案例：群聊消息查询失败，原因是调用"富文本"解析服务 spage 接口 1 秒超时；还发现群聊对富文本消息是**串行调用**——一个待优化点。
- **采样率**：调用链 Span 数多，访问量大时全量 Trace 数据太大。做法如 App 启动时服务端下发采样率，客户端按约定采样。微博线上：上行请求 100% 采样，下行普通用户 1%，VIP 用户上下行全量。
- **痛点**：各系统多语言 Reporter 完善度差别大，基于 AOP 的"无感知"探针中间件支持不够，探针有一定开发量；异构系统对接可用"本地日志 + Agent 上报"解耦对 Trace SDK 的强依赖。

## 主动监控：回环探测

被动监控本质依赖数据上报，服务故障时（如系统负载很高）监控数据本身也会上报延迟甚至失败。主动监控作为独立第三方，模拟用户行为探测：

- **做法**：用固定的两三个测试用户 UID 互相收发消息形成回环。机房 1 的探测程序设自己为 UID1、对方为 UID2，机房 2 相反；两机房各自监控本机房消息收发接口可用性。
- **两种失败报警场景**：
  1. 探测程序调用本机房发送消息 API 失败或超时；
  2. 探测程序发送数字 N 后，下次发送前检查是否收到对方发来的 N+1——没收到说明对方探测程序或应用服务接口异常，**连续出现**才报警。
- 连续数字序列还能间接探测对方机房可用性，避免两机房间网络异常时漏掉消息收发失败。
- **局限**：可模拟的用户有限，不能覆盖所有用户，存在以偏概全风险——所以主动 + 被动协同使用，做 IM 服务的监控双保险。

## 关键要点（复习用）

1. 原则："服务上线，监控先行"；没有监控就无法评估故障影响范围、无法快速定位问题。
2. 被动监控三层：系统层（Nagios/Zabbix）、应用层（QPS/耗时/失败数/到达率 + 依赖资源 + 单机维度）、全链路 Trace。
3. 监控数据链路：进程 → 本机 Agent（本地套接字/日志）→ 收集集群（缓存 + 预聚合）→ 时序数据库多精度存储 → Web 查询。
4. Dapper 三大设计要点：低开销、对应用透明、高可扩展性；Trace（TraceID/DAG）→ Span（4 时间戳，可算网络耗时）→ Annotation（业务 KV）。
5. Zipkin 六模块：Reporter / Transport / Collector / Storage / API / UI。
6. 采样率按请求方向和用户分级（微博：上行 100%、下行普通 1%、VIP 全量）；异构系统用本地日志 + Agent 解耦 SDK 强依赖。
7. 回环探测用固定测试 UID 互发连续数字 N/N+1，能同时探测本机房接口和对方机房可用性；但覆盖面有限，需与被动监控协同。

## 思考题（课程留题）

全链路 Trace 系统中，如果被 Trace 服务依赖了其他还没有接入 Trace 的 API，是否追踪还能正常运转？
