# 16｜APNs：聊一聊第三方系统级消息通道的事

> 来源：极客时间《即时消息技术剖析与实战》袁武林 · 进阶篇
> 课程主页：https://time.geekbang.org/column/intro/225
> 本笔记为学习总结，版权归原作者所有。

## 一句话总结

App 被关闭或后台被系统杀进程/断网时自建长连接必然断开，依托系统级公共长连接（iOS 的 APNs、Android 的厂商通道）可让消息触达设备并点击唤醒 App；但系统通道可靠性不足，只能作为自建长连接的补充/备选。

## 第三方系统下发通道

iOS 和 Android 都提供标准的系统级下发通道——系统提供商维护的与设备的公共长连接，App 关闭时也能经通知栏下发消息，点击通知还能唤醒 App（提升到达率 + 增加活跃度）。

- **iOS：APNs**（Apple Push Notification service）：独立于应用之外，依托系统常驻进程维护与苹果服务器的公共长连接，负责全局系统推送。
- **Android：GCM 在国内基本消失**——技术原因（NAT 超时太长、暴露的 5228 端口连通性差）+ 非技术原因（需与 Google 服务器建连），被厂商定制化去掉，替换为各自的系统通道。国内已知 5 家厂商通道：**小米、华为、vivo、OPPO、魅族**。

## APNs 机制要点

推送链路：Provider（IM 服务器）经长连接把消息发给 APNs → APNs 推送到接收方 iOS 设备并在通知栏展示 → 用户点击通知唤醒 App。

- **DeviceToken**：APNs 用于区分识别不同 iOS 设备上同一个 App 的唯一标识。Provider 与 APNs 建长连时，证书需包含 App 的 Bundle Identifier（App 唯一标识）；每次推送都必须连同消息携带目标设备的 DeviceToken，APNs 据此找到对应连接设备。
- **DeviceToken 会变吗**：同一台设备上一般不变，例外：iOS 系统升级后；APNs 出于安全等原因禁用。对策：每次 App 启动都向 APNs 注册获取；客户端首次获取后缓存本地，下次获取没变化就不必调用 IM 服务端更新（小技巧）。
- **失效 Token 清理**：新版 APNs 协议基于 **HTTP/2**，每条推送都返回状态码——DeviceToken 失效时返回 **400** 状态码，IM 服务端据此删除失效 Token。旧版协议更麻烦：判断失效时直接断开连接，需要另用 **Feedback 接口**定时获取失效 DeviceToken 再删除。

## 消息格式与静默推送

每条消息有 Payload（负载）结构，一般是 JSON 字符串：通知标题/子标题/正文、角标数、声音，以及自定义字段（群消息常携带群 ID 和消息 ID，便于点击唤醒后跳转到对应会话）：

```
{
   "aps": {
       "alert": {
           "title": "新消息",          // 标题
           "subtitle": "来自：张三",   // 副标题
           "body": "你好"              // 正文内容
       },
       "badge": 1,                     // 角标数字
       "sound": "default"              // 收到通知时播放的声音
    },
    "groupID": "123",
    "mid": "1001"
}
```

- **大小限制**：iOS 8 之前 256B，iOS 8 之后 2KB，iOS 10 之后 4KB；iOS 10 之前只能推文字，之后支持主标题、副标题和附件。
- **静默推送**：iOS 7 之后推出，无弹窗、无声音、无角标，不打扰用户地唤醒 App 做更新操作。例：每天定点推送让 App 在后台静默更新订阅号文章内容，用户打开即可直接看到。

## APNs 的缺陷（为什么要自建长连接）

- **可靠性低**：不保证推送到达率，也不保证不延迟——消息可能几分钟后才到用户设备（苹果出于维护成本考虑）。
- **离线消息支持差**：设备离线/关机时无法马上送达；此时若有多条推送，APNs 的 QoS 机制**只保留最新一条**，存在丢失离线消息的问题——根源是接收量基数太大，大量存储转发成本太高。
- **角标累加问题**：不支持未读数累加 +1，只支持覆盖，每条推送都要把用户总未读数带下去，增加后端未读数服务调用压力（Android 厂商通道更友好，很多支持角标自动累加）。

## Android 厂商通道与统一推送

- **厂商通道**：App 后台保活是提升在线推送到达率的重要手段（有 App 间互相拉起进程的取巧方式，以及超级 App 的保活白名单），但大部分 App 仍需在进程被杀/被限制时依赖厂商系统通道。5 家厂商都提供专门 SDK，功能大致与 APNs 类似；各家 SDK 使用各异、接入成本高，因此催生了整合多家厂商 SDK、统一接入的第三方 Push 服务：**个推、信鸽、极光、友盟**。
- **统一推送联盟**：2017 年工信部主导成立安卓统一推送联盟，推出"**推必达**"（对标 APNs 和 GCM）。特色：除传统 TCP 长连下推外，还与运营商合作支持**信令通道**下推——没有 WiFi 和移动网络、只要有手机信号也能收到系统推送。架构：IM 服务端直接或经第三方推送服务把消息交给各厂商部署的 UPS 服务器，UPS 经与客户端 SDK 维护的长连接推送。官网反馈：全国 34 个省市测试消息到达率 **99.999%**。华为、小米、OPPO、vivo 等已加入；工信部要求 2019 年 12 月 31 日前现有各推送通道兼容统一推送标准。

## 关键要点（复习用）

1. 系统级通道的价值：App 关闭/后台断网时仍可触达设备，点击通知还能唤醒 App。
2. APNs 推送三要素：Provider 证书（含 Bundle Identifier）+ 消息 + DeviceToken（设备+App 的唯一标识）。
3. DeviceToken 例外会变：iOS 系统升级、APNs 禁用；每次启动重新注册 + 本地缓存比对是省调用的技巧。
4. 失效清理：新协议（HTTP/2）按推送返回 400 状态码即时清理；旧协议靠 Feedback 接口定时拉取。
5. Payload 限制：256B（iOS 8 前）→ 2KB（iOS 8+）→ 4KB（iOS 10+）；iOS 10 起支持副标题和附件。
6. APNs 三缺陷：不保到达/延迟高、离线 QoS 只留最新一条、角标只覆盖不累加——只能作自建长连接的补充。
7. Android 国内是 5 家厂商通道（小米、华为、vivo、OPPO、魅族），SDK 各异，第三方 Push（个推/信鸽/极光/友盟）整合接入。
8. "推必达"：TCP 长连 + 运营商信令通道双途径，测试到达率 99.999%，是 Android 系统推送的期待方向。
